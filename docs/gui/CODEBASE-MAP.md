## 1. How this map was made

**Units.** The engine package was split into 15 units. Each unit agent read every file in its scope in full, used the codebase-memory graph only to find callers and callees, and reported modules, defects, needs without an API, and errors in the first-pass inventory. Units: seam-engine, seam-rest, mcp-clients, registry-ledger, parts-lightrag, parts-hipporag, stores, runner, foreign, validator, evidence-pkg, eval, parity-a, parity-b, tests.

**Probes.** Ten probes checked behaviour instead of reading it:

- tests-run: ran the full engine test suite twice.
- rest-live: about 130 calls to all 15 REST routes through `fastapi.testclient.TestClient` on temporary store roots.
- mcp-live: 120 calls to all 9 MCP tools in-process and over JSON-RPC (`mcp.Client`, SDK 2.2.0).
- contract: CONTRACT §18 (`docs/system-model/CONTRACT.md:747-810`, plus §4:264-280 and §19.8:854) against `databasise/seam` and `databasise/mcp`.
- other-surfaces: every entry point in the repository (CLIs, v1 server, scripts).
- doc-audit-1 to doc-audit-5: sections 1-2, 3.0-3.1, 3.2-3.3, 3.4-3.5 and 4-6 of the first-pass inventory, claim by claim.

**Adversarial verification.** Every defect and every inventory error from every unit and probe was handed to a separate verifier, which re-read the code and, where possible, reproduced it (scratchpad scripts, live TestClient calls, live v1 runs). Each item received a verdict: `confirmed`, `partly` (the verifier supplied corrected text), or `refuted`. Section 4 lists only confirmed and partly items, using corrected text for partly items. Refuted items are listed at the end of section 4 so they are not raised again.

**Coverage.** Missing units: `[]`. Missing probes: `[]`. 126 Python files outside `databasise/tests` and `databasise/.venv` were counted; section 2 lists all of them. `databasise/tests` holds 105 `test_*.py` files.

**Completeness re-check (2026-10-14).** Section 2 was matched path by path against the 126-module list (all present; the four fixture parts share one row) and against the 90 non-Python files under `databasise/` (excluding `.venv` and `tests`). `databasise/README.md`, `databasise.egg-info/` and `uv.lock` were missing and are added in 2.1. All nine MCP tools were re-probed one by one (in-process `call_tool`, `clients=None`, temporary store root, v1 corpus ops stubbed); the results agree with section 3.3 and are recorded per tool in API-INVENTORY.md section 4. The re-check added G-36 and G-37 and corrected three defect cross-references in 3.2, the refusal count in 2.2 and the M-06 claim that no ledger operation can succeed without clients.

**Excluded from scope.** `v1/` internals (read only where the engine calls into them), `.planning/spikes/**` (MelodyScribe, moved to another repository), `reference/`, `graphify-out/`, and `.claude/worktrees/agent-aa9dde19a41b39acb` (a stale full copy of `databasise/` and `v1/`; text searches that do not exclude it report duplicate surfaces). `v1/.env*` files were never read.

**Side effects of the probes, for the owner.**

- The rest-live probe left the temporary store `/tmp/restprobe-izdqrzxw` (a hook blocked its recursive delete). It also created `/tmp/etc` through the evidence path-escape defect (M-10 below); that directory was removed.
- The mcp-live probe ran one unstubbed ingest that wrote into the shared `v1/.corpus_working_dir` and made 2 real LLM calls. The document was deleted through the MCP `delete` tool; the 2 LLM cache entries in `v1/.corpus_working_dir/kv_store_llm_response_cache.json` remain.
- The doc-audit-5 probe ran MCP `ingest {raw_base64: "!!!!"}`, which reached real v1 and left one failed doc-status entry, `dup-15f6f452b1ea8f4a9c36928aa0d86588` (track `ba6b68b7ddab4276bdb1a1292d8163a8`), in `v1/.corpus_working_dir`. It can be removed with `DELETE /documents/dup-15f6f452b1ea8f4a9c36928aa0d86588`. Corpus counts read failed=3, total=3 after that probe; the count before it was not measured.

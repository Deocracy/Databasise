# Databasise API Inventory for the Operator Console

Updated 2026-10-29 by Phase 17 (GUI mockup): new needs recorded per 17-CONTEXT D-05, D-10, D-12, D-14.

Second pass 2026-10-14: independently re-checked; see CODEBASE-MAP.md. Completeness re-check the same day added per-tool MCP live checks (section 4), the shipped-client behaviour for empty text and missing `model` fields (sections 1 and 3.0), the cross-process graph lock (section 1) and a server-log gap row (section 5.1).

Date: 2026-10-14

This document lists every API surface of the Databasise 2.0 engine that an operator console GUI can call, what each one does, what the GUI needs in order to use it, and which console needs have no API yet. It is the starting point for the GUI. The next two steps are (1) a mockup GUI built against the request and response shapes recorded here, using static fixtures, and (2) connecting the mockup to the running REST app. The operator is the person running the engine: ingesting documents, running queries, comparing modalities side by side, inspecting evidence and traces, managing the promote/rollback/retire ledger, and browsing the graph and vector stores. The GUI is a REST client. All paths below are relative to the repository root, and every line citation was checked against the source on this date. Where an earlier draft and a verifier disagreed, the source was re-read and this document follows the code.

## 1. How the GUI reaches the API

**App construction.** The REST app is built by the factory `create_app(*, store_root, workspace, registry=None, clients=None) -> FastAPI` (databasise/seam/rest.py:235-250). It constructs one `Databasise` instance (rest.py:247), stores it on `app.state.engine` (rest.py:249), and registers one exception handler for `SeamRefusalError` (rest.py:250). One app instance is bound to one `store_root` and one `workspace`; the GUI cannot choose a workspace per request. `ledger.db` and `trace.db` live at the store root, not per workspace (ledger.py:138, trace_store.py:71, engine.py:560, 1201, 1334, 1474): two apps with different workspaces under one store root share one alias namespace and one trace store. The rule (Phase 14, D-10): one store_root is one tenant. The launcher locks per store_root, aliases name wirings and not data, and `trace.db` and `ledger.db` carry no workspace key.

**Where data exists.** The only complete populated v2 store is `store_root=v1/.parity_v2_store` with `workspace=shared-4fab18fef508b7bc3dda1cc2d8f12e36`. It holds the five LightRAG namespaces (`chunks`, `entities`, `relationships`, `text_chunks`, `chunk_entity_relation`) and the five `hipporag-*` namespaces, plus `trace.db` (directory listing; CROSS-MODALITY-EVIDENCE.md:197-253). `v1/.parity_v2_store.pre-graph-refit` holds a partial backup (chunks, text_chunks, chunk_entity_relation only). Engine stores resolve to `<store_root>/<workspace>/<namespace>` (engine.py:319-347), so a launcher pointed anywhere else serves empty LightRAG and HippoRAG retrieval.

**Starting it.** No launcher exists. There is no `[project.scripts]` table in databasise/pyproject.toml and no `__main__.py` in databasise/seam/ or databasise/mcp/. Outside tests nothing calls `create_app` or `create_server`, and nothing calls `uvicorn.run` or `MCPServer.run` (grep; section 7). FastAPI, uvicorn and python-multipart come from the optional `rest` extra (databasise/pyproject.toml:76-89), installed with `uv sync --extra rest`. Because `create_app` takes required keyword-only arguments, `uvicorn --factory databasise.seam.rest:create_app` cannot pass them; a small launcher script that calls `create_app(...)` and `uvicorn.run(...)` is required (see section 5.1).

**Model clients.** `create_app` passes `clients` straight to `Databasise`, and the default is `None` (rest.py:240, 247; engine.py:550, 555). Parts read `clients["llm"]`, `clients["embedding"]` and `clients["rerank"]` through `CapabilityScopedClients.require`, which raises `ClientNotWiredError` when the key is absent (`databasise/clients/__init__.py`:33-48, 63-75). The scheduler wraps that into `NodeExecutionError` (databasise/runner/scheduler.py:468-473), records the node as halted with `partial` and `stop_reason` (scheduler.py:586-617) and stops further batches (scheduler.py:671-677), so a query against an app built without clients returns HTTP 200 with `partial: true`, `answer: ""`, `evidence: []` and a `stop_reason` naming the missing client and the internal node id (section 3.0), not a 422 or 500. HippoRAG ingest also surfaces as `ForeignEngineRefusalError`, but its `cause` is the synthesized text "the 'ingest' node produced no result and no exception", not the missing client: `_node_result_or_refuse` inspects only the `provides` node (engine.py:385-394, 688). The LightRAG corpus and job routes do not use these clients; `run_corpus_op` copies the server process's own environment, overlays `v1/.env.parity`, and defaults `ENABLE_LLM_CACHE=false` (v1_corpus_adapter.py:123-125); v1 also loads `v1/.env` at import with `cwd=v1` (v1/lightrag/lightrag.py:159). The only existing client builder is `_build_clients` in databasise/parity/run_arm.py:161-183. It takes a dict parsed from `v1/.env.parity` by `_load_env_file` (run_arm.py:89-114, 296-299), requires six keys (`LLM_BINDING_HOST`, `LLM_MODEL`, `LLM_BINDING_API_KEY`, `EMBEDDING_BINDING_HOST`, `EMBEDDING_MODEL`, `EMBEDDING_BINDING_API_KEY`; run_arm.py:117-124) and raises `MissingParityEnvKeyError` naming any missing key (run_arm.py:168-170), optionally reads `OPENAI_LLM_EXTRA_BODY` as a JSON provider-routing body and raises `UnparseableProviderRoutingError` on invalid JSON (run_arm.py:129-158), and returns only `{"llm", "embedding"}` (run_arm.py:183). No rerank client implementation ships in the package (only the `RerankClient` Protocol, clients/base.py:71-75); no shipped wiring sets `live_rerank`, so a missing rerank client affects no current query (parts_core/lightrag/rerank.py:28-34). `OpenAICompatibleClient` reports `call_count=0` when a provider response has no `usage` object (openai_compat.py:159-161). It raises `ModelIdentityMissingError` (a `RuntimeError`, openai_compat.py:48-60, 154-156) on any chat or embedding response that carries no `model` field, after the call was made and billed, so a provider that omits `model` turns every query into a 200 partial run whose `stop_reason` names this error; a launcher smoke test should run one query and check `partial`. The launcher must build and pass clients, and no route reports which clients are wired.

**Base URL and port.** No port is configured anywhere in databasise/. Uvicorn's own default (8000) applies unless the launcher sets one. Port 9621 is the default port of the v1 API server (v1/lightrag/api/config.py:263); v1/lightrag_webui/vite.config.ts:91 uses it only as the default dev-server proxy target, active when `VITE_API_PROXY === 'true'` and `VITE_API_ENDPOINTS` is set (vite.config.ts:86-97). Routes are mounted at the root, with no prefix (rest.py:252-378).

**CORS.** None. `create_app` adds no `CORSMiddleware` (rest.py:235-250). A browser `fetch` with `Content-Type: application/json` triggers a CORS preflight, so a GUI served from another origin fails on every POST. Options: serve the GUI's static build from the same origin, use a Vite dev-server proxy during development (as v1 did, vite.config.ts:91), or add `app.add_middleware(CORSMiddleware, ...)` with an explicit origin list. The thin-adapter AST test checks only calls to selector, redaction and envelope functions (databasise/tests/seam/test_rest_transport.py:182-200), and the import guard at 159-179 checks that the package `__init__` modules do not import rest.py; a second copy of the AST proof is at tests/seam/test_rest_corpus_endpoints.py:314-342. No test inspects middleware, so adding middleware inside `create_app` would not fail them. Live check: `OPTIONS /query` with an Origin header returns 405 and no `access-control-allow-origin` header is sent.

**Authentication.** None, by design. The module docstring states the app ships with no authentication, no authorization, no TLS and no rate limiting, and that access control is the operator's own boundary (rest.py:38-46). The GUI must be served and bound on localhost only. Any request can set `debug: true` on `POST /trace/resolve` and receive internal identities (rest.py:127-129, engine.py:1106-1108).

**Error model.** The GUI must handle three distinct error shapes:

1. **Refusal 422.** Every `SeamRefusalError` raised after the body is parsed returns HTTP 422 (rest.py:94) with body `{refusal_type: <class name>, message: str, ...the refusal's public attributes}` built by `_refusal_response` (rest.py:206-232). Pydantic-model attributes are serialized with `model_dump` (rest.py:224-225), and exception-valued attributes are stringified (rest.py:229-230), which is how `ForeignEngineRefusalError.cause` reaches the body. Attributes held on underscore names are skipped, so `UnbudgetableParticipantError` carries only `refusal_type` and `message` (databasise/seam/tokens.py:67-69, rest.py:221-223). Every refusal uses 422, including not-found lookups (`UnknownTraceReferenceError`, `UnknownJobError`, `UnresolvableEvidenceReferenceError`, `UnknownGenerationVersionError`), so the GUI must branch on `refusal_type`, never on status code. `ForeignEngineRefusalError` is a machine fault mapped to 422 despite the "never a machine fault" comment at rest.py:90-93; its `message` and `cause` both embed `str(cause)` (refusals.py:502, rest.py:229-230), which for a v1 subprocess failure is "v1 corpus driver subprocess exited N: " plus the first 2000 characters of v1 stderr (v1_corpus_adapter.py:63-65), so the same text (tracebacks, file paths, env-var names) can appear twice, about 4 KB. Because v1 logs to stderr and the driver writes the traceback last (v1_corpus_driver_script.py:353-355), the head-2000 cut often drops the actual exception line.
2. **Validation 422.** FastAPI request validation returns `{detail: [{type, loc, msg, input, ctx}]}` with no `refusal_type`. Because `SeamRefusalError` subclasses `ValueError` (databasise/seam/refusals.py:20), a refusal raised inside a pydantic `model_validator` while FastAPI parses the body is wrapped into this shape. This affects `ForbiddenSelectorInputError` and the selector at-most-one-member rule on every JSON body that carries a `Selector` (databasise/seam/selectors.py:104-127), and `AmbiguousIngestPayloadError` / `OversizedDocumentError` on `POST /documents` (databasise/seam/corpus.py:77-89). Only `AmbiguousIngestPayloadError` embeds its class name in `detail[].msg` (`"Value error, AmbiguousIngestPayloadError: ..."`). The others are identified by the key set of `detail[].ctx.error`, which carries the refusal's attributes but never its type name: `{set_members}` = ambiguous payload, `{actual_bytes, limit_bytes}` = oversized, `{member_name, value}` = hash-shaped selector value, `{}` plus "at most one of" in `msg` = multi-member selector. The multi-member rule is a plain `ValueError`, not a refusal class (selectors.py:107-110). `loc` is `['body','selector']` on single-selector routes and `['body','selectors',<index>]` on `/compare`. An oversized text body echoes the whole input (about 25 MB) back in `detail[].input`. The rest.py module docstring (rest.py:32-36) says one handler maps every `SeamRefusalError` subclass so none falls through to a generic error; that is false for refusals raised inside validators.
3. **Unhandled 500.** Any exception that is not a `SeamRefusalError` returns a plain-text 500 ("Internal Server Error") with no structured body; exception messages stay in the server log. Known paths are listed per route below. Examples: an oversized file on `/documents/upload` (rest.py:326-332); a bad caller-supplied `document_id` on both ingest routes (engine.py:678-682); graph-store lock contention between overlapping calls (graph.py:102-108); any v1 subprocess failure on `/corpus`, `/corpus/counts` and `/jobs/{job_id}` (databasise/foreign/v1_corpus_adapter.py:42, 56, 68, 149). On `/health` a subprocess failure is caught (engine.py:954-956); on ingest and delete it occurs inside an opaque node and becomes 422 `ForeignEngineRefusalError` (engine.py:385-387).

Recommended GUI rule: if the status is 422 and the body has `refusal_type`, render a typed refusal banner keyed on `refusal_type` with its attributes, and treat `ForeignEngineRefusalError` as a server-side failure with `cause` collapsed behind a details toggle; if the status is 422 and the body has `detail`, render field-level form errors; for any 5xx, render a generic error state.

**OpenAPI.** FastAPI's default `/docs`, `/redoc` and `/openapi.json` are served (rest.py:248). They list all 15 paths. Limits: the 422 schema is FastAPI's `HTTPValidationError` only, so the refusal body appears nowhere in the spec; `/compare`'s 200 schema is empty because the route returns `Any` (rest.py:256-258); `/evidence/resolve` and `/trace/resolve` return untyped `dict[str, Any]` (rest.py:292, 296); `verb` and `change_origin` on the ledger routes are plain `str`, not enums (rest.py:146-182). A client generated from the spec therefore needs hand-written types for these. `GET /health` and `GET /corpus/counts` document only a 200 response. `info.version` is the literal `"0.1.0"` (rest.py:248), not read from `databasise.__version__` (`databasise/__init__.py`:38), so the two can drift. The refusal hierarchy is split across modules: `UnknownTraceReferenceError` (trace_store.py:52), `UnresolvableEvidenceReferenceError` (evidence.py:82) and `UnbudgetableParticipantError` (tokens.py:52) are outside refusals.py, and `refusals.__all__` omits `NoRawUploadPathForModalityError` (refusals.py:149, 505-533), so a refusal catalogue built from `refusals.__all__` misses four types.

**Pagination.** `GET /corpus` and `GET /jobs/{job_id}` take `limit` (default 50) and `offset` (default 0, `ge=0`) (rest.py:342-343, 361-362). `MAX_PAGE_SIZE = 100` (databasise/seam/corpus.py:42); a larger `limit` returns 422 `PageSizeExceededError {requested, limit: 100}` through `_checked_page` (rest.py:185-203). There is no lower bound on `limit`: `limit=0` returns an empty page with `next_offset == offset`, which makes a naive paginator loop, and a negative `limit` slices `document_ids[offset:offset+limit]` in the v1 driver and can return more than 100 entries (databasise/foreign/v1_corpus_driver_script.py:299-301, engine.py:895-900). The GUI must clamp `limit` to 1..100 itself. Paged responses carry `next_offset` (null on the last page). Live check: `GET /corpus?limit=0` and `?limit=-1` both return 200 with `next_offset` equal to `offset`; with three documents, `limit=-1` returned two.

**Server-Sent Events.** `POST /query/stream` returns `text/event-stream` (rest.py:277-289). The browser `EventSource` API only issues GET, so the GUI must use `fetch()` with a `ReadableStream` SSE parser. Each event is a `data:` line with no `event:` name and no `id:` (databasise/.venv/lib/python3.12/site-packages/fastapi/routing.py:524, fastapi/sse.py:165); keep-alive comments `: ping` are sent only after 15 s with no event (fastapi/sse.py:236-241), and because the envelope is resolved in a dependency before the response starts (rest.py:260-279) and all events are then yielded at once, they do not occur in practice. The whole run completes before the first event (section 3.1.2).

**Latency and concurrency.** Every call to `/health`, `/corpus`, `/corpus/counts` and `/jobs/{job_id}` runs the v1 corpus driver in a subprocess with a 60-second ceiling (databasise/foreign/v1_corpus_adapter.py:39, 101-150), so these must be polled slowly or on demand. Ingest blocks until the document is processed (engine.py:732), with a wall-clock ceiling of 900 s for LightRAG ingest (parts_core/lightrag/full_ingest.py:41, 223) and 300 s for LightRAG delete (full_delete.py:40, 223); a breach raises `CorpusOpTimeoutError` (v1_corpus_adapter.py:143-144), returned as 422 `ForeignEngineRefusalError`. HippoRAG ingest runs in-process with no ceiling. The graph store is an embedded RocksDB database: a second open of the same graph namespace directory in the same process fails with "RocksDB error: IO error: lock hold by current process" (databasise/stores/graph.py:102-108). Every query, compare, stream, ingest, delete, evidence resolve and health probe opens the graph store for one namespace and holds it for the whole call (engine.py:342-346, 730, 822, 987, 1089, 932); a LightRAG ingest holds it for the whole v1 subprocess (engine.py:730-754). Concurrent calls on the same namespace collide: LightRAG `/query`, `/compare`, LightRAG ingest and delete, `/evidence/resolve` and `/health` all share `chunk_entity_relation`; HippoRAG query and ingest share `hipporag-graph`. A colliding call returns 500; a colliding `/health` returns 200 with `stores.graph: false` (engine.py:938-943). LightRAG and HippoRAG calls do not block each other, except that `/health`, `/evidence/resolve` and delete always open `chunk_entity_relation`. Because `_build_stores` opens kv before graph outside any try (engine.py:342-346), a lock failure also leaves the kv connection unfinalized until garbage collection. The GUI must serialize engine calls per graph namespace and disable Query while an ingest is running. Separately, each LightRAG ingest and delete spawns its own v1 process against the same `v1/.corpus_working_dir` with no cross-process lock (v1_corpus_adapter.py:134-142; no lock in engine.py); v1's storage locks are in-process, so two overlapping writes can lose each other's changes with the JSON backends (not reproduced). The GUI must allow one LightRAG write in flight at a time. `/health` also runs its kv and graph constructors synchronously on the event loop (engine.py:938-941). The RocksDB lock is also exclusive across processes (a second process opening a held `graph.cozo` fails with `rocksdb::kIOError`, reproduced in the completeness re-check), so the launcher must run exactly one uvicorn worker, and the parity CLIs, which all default to `v1/.parity_v2_store` (parity/import_index.py:85; run_comparison.py:557; run_cross_modality.py:302; storage_audit.py:179; build_hipporag_index.py:201), collide with in-flight app calls when run against the store the console serves; `import_index` and `build_hipporag_index` also rewrite those stores under the running app (CODEBASE-MAP G-36).

**Fixed v1 working directory.** The corpus list, the counts, the job status, the engine half of `/health`, and LightRAG ingest and delete all use the fixed v1 working directory `<repo>/v1/.corpus_working_dir` through `<repo>/v1/.venv/bin/python` (v1_corpus_adapter.py:28-31, 118-131). The engine never passes a working directory (engine.py:862-867, 887-892, 907-912, 949-951; full_ingest.py:219-224; full_delete.py:219-224). These values are the same for every app instance in the repository and are not per-workspace. The LightRAG query arms instead read the v2 stores under `<store_root>/<workspace>/` (`chunks`, `entities`, `relationships`, `text_chunks`, `chunk_entity_relation`; parts_core/lightrag/chunk_vector.py:21, entity_lookup.py:28, relation_lookup.py:27, engine.py:987), which only the parity importer writes, from a different directory, `v1/.parity_working_dir` (parity/import_index.py:84, 498-512). A document ingested through `/documents` under a LightRAG selector is therefore never queryable or resolvable through `/query` or `/evidence/resolve`, and a LightRAG delete does not remove it from query results. Only `/corpus` and `/jobs` reflect LightRAG writes. The function `import_v1_index(v1_working_dir, store_root, workspace)` (import_index.py:231-235) accepts any v1 working directory, so a bridge needs only a new caller.

**Status routes need v1 configuration.** The v1 status ops build the full LightRAG facade and read `EMBEDDING_DIM`, `EMBEDDING_MODEL`, `EMBEDDING_BINDING_HOST`, `EMBEDDING_BINDING_API_KEY` and the four `LIGHTRAG_{KV,GRAPH,VECTOR,DOC_STATUS}_STORAGE` keys with `os.environ[...]` (v1_corpus_driver_script.py:150-168), even though no model is called. If the server environment, `v1/.env.parity` and `v1/.env` together lack one, `/corpus` and `/corpus/counts` return 500, `/jobs/{job_id}` returns 500, and `/health` reports `degraded` with no reason. A missing `v1/.env.parity` is silently treated as empty (v1_corpus_adapter.py:86-87).

**Side effects of read routes.** `/health` and `/evidence/resolve` construct stores, which create directories and database files on a fresh store root (kv.py:51-60, graph.py:104-108, vector.py:115-116); the v1 health op creates `v1/.corpus_working_dir` (v1/lightrag/lightrag.py:1002-1004). Every raw upload leaves `<store_root>/corpus-inbox/<id>.bin` on disk permanently, shared by all workspaces on that store root (engine.py:707-710). Refused ledger operations still create `ledger.db` with its schema on a fresh store root (engine.py:1201, 1334, 1474; ledger.py:137-143).

## 3. Routes

### 3.0 Shared models

These models appear in several routes. Each route section refers back here.

**Request base.** Every JSON request model extends `_RequestModel` with `ConfigDict(extra="forbid", frozen=True)` (rest.py:97-111). Unknown keys return a validation 422. Exception: `POST /evidence/resolve` takes a bare `EvidenceRef`, a `_StrictModel` with the same config (rest.py:292, `_base.py`:25-26). Despite its docstring ("the shared strict base", rest.py:98) `_RequestModel` does not set `strict=True`, so pydantic lax coercion applies: for example `debug: "yes"` is read as `true`.

**QueryObject** (databasise/seam/query.py:49-60; related constants 37-46). Frozen, `extra="forbid"`. Five members, all optional, default null; at least one must be set (no bare-string shortcut). Any non-null value counts as set (query.py:76): `text: ""` passes the seam and runs the wiring. With stub clients that is a full run with an LLM call; with the shipped `OpenAICompatibleClient`, `embed()` refuses empty or whitespace-only text with `EmptyEmbeddingInputError` (clients/openai_compat.py:134-144), so naive and HippoRAG return a 200 partial run at the first query-embedding node with no LLM call (parts_core/lightrag/embedder_query.py:36, parts_core/hipporag/fact_score.py:38), local after spending its keyword LLM call, and only bypass sends the empty question to the LLM; `embedding: []` counts as set and refuses as unconsumable.

| Field | Type | Consumable today |
|---|---|---|
| `text` | string \| null | yes (the only one) |
| `embedding` | list[float] \| null | no: checked against capability `reads_space` (query.py:41-46) |
| `predicates` | object \| null | no: checked against `predicate-query` |
| `profile_ref` | string \| null | no: checked against `profile-ref-resolution` |
| `formal_query` | string \| null | no: checked against `formal-query-language` |

None of the four capability strings is a member of the 17-member `Effect` literal (parts/schema.py:31-49) and `check_consumable` reads only registered parts' `effects` (query.py:63-69), so no type-conforming part can enable these members without a schema change; the GUI should show them as disabled with no planned enablement path. The literal is not enforced at runtime (`Part` is a plain dataclass and `register()` does not check effects, schema.py:115-141, registry.py:123-149), so a non-conforming registration would enable them. The query.py docstring (22-25) claim that a part or store declaration flips the member is inaccurate; stores are never consulted.

Setting a non-consumable member returns 422 `UnconsumableQueryMemberError {member_name}` (only the first is named); setting none returns 422 `EmptyQueryObjectError {query_object}`, where `query_object` is the full five-member dict with nulls (query.py:72-86, rest.py:224-225).

**Selector** (databasise/seam/selectors.py:93-127). Frozen, `extra="forbid"`. At most one member set (validator selectors.py:104-111); an all-null or omitted selector means the default selector.

| Member | Type | Behaviour |
|---|---|---|

### 3.1 Screen: Query & Compare

#### 3.1.1 POST /query

**What it does.** Runs one `QueryObject` against the one fitted modality the optional selector resolves to and returns a `ResponseEnvelope`. The route only deserializes the body, awaits `Databasise.query(query_object, selector=None)` and returns (the `debug` keyword was removed in Phase 13, D-09; `_execute_resolved` in engine.py). Every run that dispatched persists one `RunRecord` to the trace store before anything that can refuse after dispatch (Phase 13 D-04), so a post-dispatch refusal (a store fault, two answering provides nodes, malformed evidence, an unbudgetable participant, a guard signal missing at run time) still leaves a resolvable run, and its refusal body carries that run's `trace_token`. A refusal raised before dispatch (an unparseable or cyclic wiring, an invalid node setting, a misdeclared guard, an unavailable environment digest) persists none, and no node ran.

**Request.** `QueryRequest` (rest.py:114-116):
- `query`: QueryObject, required.
- `selector`: Selector \| null, optional, default null.

There is no `debug` field, and `Databasise.query` takes no `debug` keyword (Phase 13 D-09); the per-node trace comes only from `POST /trace/resolve` with `debug: true`. Example: `{"query":{"text":"..."},"selector":{"capability":["reads_graph","calls_llm"]}}`. That example resolves to HippoRAG, not a LightRAG graph arm (section 3.0, Selector).

**Response.** 200 `ResponseEnvelope` (section 3.0). Typed in OpenAPI (return annotation rest.py:253).

**Refusals.**
- Refusal 422: `EmptyQueryObjectError {query_object}`; `UnconsumableQueryMemberError {member_name}`; `UnsatisfiableSelectorError {selector_kind, requested}`; `UnbudgetableParticipantError` (no extra attributes; a node reported `counted_by: "unbudgetable"`, no envelope produced, tokens.py:52-60). `UnbudgetableParticipantError` occurs on `/query`, `/query/stream` and `/compare` (the stream and compare routes run the same `_execute_resolved`). It is not reachable with the shipped `OpenAICompatibleClient` over a usage-bearing response (a usage-less response reports the sentinel, see below); an injected client that reports `counted_by: "unbudgetable"` triggers it on a HippoRAG run, through openie and entity-fact-embed (parts_core/hipporag/openie.py:121-122, entity_fact_embed.py:62-63), and as a 422 over REST. Both legs are pinned by tests/seam/test_refusal_reachability.py (13-07, WIRE-17).
- Refusal 422, before dispatch (Phase 13 WIRE-05, D-07; no `trace_token`): `UnparseableWiringError {violations}` when the resolved wiring's parse report is not ok or its graph is cyclic; `violations` is the sorted list of violation codes only (a cycle is `cyclic-wiring`), never node ids (D-25). `InvalidNodeSettingError {setting}` when a node declares an invalid `max_concurrency` or `token_allowance` (`setting` is that name; the node id and value stay private). `InvalidGuardDeclarationError` (no public attribute) when a guard declaration is malformed: a non-list `config.guards`, an entry that is not a mapping or has missing or extra keys, a non-string name, evaluating node or signal, an inadmissible granularity, or an evaluating node that is neither the guarded node nor one of its dependencies.
- Refusal 422, after dispatch (with `trace_token`, D-04): `AmbiguousAnswerPositionError` (no public attribute) when two `provides` nodes both answered; `InvalidGuardDeclarationError` when a guard's evaluating node emitted no declared signal at run time (D-19, 13 REVIEW B-WR-04); `UnbudgetableParticipantError` (above).
- 502/503 `ForeignEngineRefusalError {operation, failure_class}`: 502 `MalformedDriverOutput` (after dispatch, with `trace_token`) when the evidence node's output has no `items` list, an item is not a mapping, lacks `id` or has a non-finite score (WIRE-14, D-09, 13 REVIEW A-WR-02); 502 `StoreFault` / `StoreCorrupted` (after dispatch, with `trace_token`) for a store error inside a node; 503 `EnvironmentDigestUnavailable` (before dispatch) when the environment digest cannot be computed, for example after an interrupted install left an empty `dist-info` (D-22, 13 REVIEW A-WR-03). The same failure reads `degraded` with "environment digest unavailable" on `/health`.
- Validation 422: selector with more than one member; hash-shaped selector value; unknown keys.
- 500: a graph-store lock collision with a concurrent same-namespace call (section 1). The cyclic wiring, two answering provides nodes and an evidence output without `items` are no longer 500s (above).

**Live check.** Recorded before Phase 13; the expected Phase 13 values are given and were not re-run live. With `clients=None`: `{"query":{"text":"x"}}` → 200, `partial: true`, `answer: ""`, `evidence: []`, `depth_label: null`, `token_accounting: [{counted_by: "none", zeros}]`, `stop_reason: "node_failed"` (the failing node, `embedder-query`, is named only in the debug trace). `{"query":{"text":""}}` → 200, full run with an LLM call (stub clients; with the shipped client this is a partial run, section 3.0 QueryObject). `selector: {capability: []}` → 200 from bypass (`stop_reason: "node_failed"`; node `generate` in the debug trace). `selector: {capability: "reads_graph"}` → 200 from HippoRAG (`stop_reason: "node_failed"`; node `fact-score` in the debug trace). Hash-shaped alias → validation 422 with `ctx.error {member_name, value}`. Alias `hr` promoted from a HippoRAG trace → 200 from HippoRAG (Phase 14); an alias row naming a wiring that does not resolve → 422 `UnsatisfiableSelectorError`. Unknown harness → 422 `UnsatisfiableSelectorError`.

**What the GUI needs.**
- Screen: Query console (primary screen).
- Controls: multiline text area for `query.text`. A collapsed "advanced members" panel showing `embedding`, `predicates`, `profile_ref`, `formal_query` as disabled with the reason "no registered part consumes this member", or as raw JSON inputs for testing refusals. Selector picker: radio Default / Alias / Capability / Harness. Alias = text input (a dropdown needs a ledger listing, section 5). Capability = multi-select chips over the 17 Effect literals. Harness = text input, shown disabled with "no production wiring declares a harness". Client-side checks: only one member; reject 64-hex values.
- Run button with an indeterminate spinner; the call is a full, non-streaming run with LLM latency.
- Display: answer panel; badges for `depth_label` and `partial`/`degraded` with `stop_reason`/`degradation_reason` tooltips; evidence table (rank = array position, `ref`, `namespace`, `kind`, `score` to 3-4 decimals, `tier` as "—") with a row action "Open" that POSTs the EvidenceRef unchanged to `/evidence/resolve`; `trace_token` with "Open trace" (`/trace/resolve`), disabled if null; token table with one row per `counted_by` plus a client-side totals row; seam events table (component, outcome badge, spend).
- States: idle, running, success, partial run (200 with `partial: true`; show `stop_reason` and keep the trace link, since the node table shows which node halted), empty evidence ("no evidence position declared or no items"), refusal 422, validation 422, 500.
- Client-side history: the GUI must store each `{query, selector, trace_token, timestamp}` itself, because no route lists traces and the trace record holds no query text or selector (databasise/runner/trace.py:154-171). The ledger forms need this history (section 3.5).
- Chained calls: `/evidence/resolve`, `/trace/resolve`, `/compare` ("compare this query"), `/promote` ("promote from this result"). Disable "promote from this result" when `partial` is true: a partial run's trace lists only dispatched nodes, so `/promote` returns 500 (section 3.5).
- Client-side checks the server does not make: block an empty capability chip set (it silently runs bypass) and block empty or whitespace-only `text`.

**Gaps.**
- The envelope does not identify which wiring answered, so results can be labelled only by the selector the GUI sent. With the capability rule above, operators cannot label results correctly without a selector dry-run (section 5.1).
- No route lists aliases; capability values must be hard-coded; harnesses are always empty.
- No request id, cancel, or timeout control.
- The alias-to-HippoRAG 500 must be fixed before the alias selector is useful for HippoRAG (section 5.2).
- For hybrid, local and global, the hydrated entity and relation lists never reach the generator: `assemble` reads only reranked chunks (parts_core/lightrag/assemble.py:31) and `generate` reads only `assemble` (generate.py:26-27), and the extracted high- and low-level keywords are not used for retrieval (embedder_query.py:27 embeds the raw query; keywords.py:118, 134). So these arms answer from chunks chosen through the graph, not from KG context, and spend one keyword LLM call whose result is unused. `generate` sends a two-line `Context/Question` prompt, not v1's `naive_rag_response` template (generate.py:30). Do not label these arms as "KG context" answers or as equivalent to v1 modes.
- HippoRAG: the fact filter never receives the query text, because `fact-filter` is missing from `consumes_query` (wirings/hipporag/base.json:124, fact_filter.py:108); on the normal PPR branch the answer is `""` and every evidence ref fails to resolve (section 3.2.1); seven index-side nodes are dispatched as no-ops on every query (base.json:6-57); the query text is embedded three times (fact_score.py:38, reset_vector_join.py:86, dpr_fallback.py:61).
- An empty vector namespace (never imported) returns `[]` silently (stores/vector.py:218-219, 494-501), so the answer is generated from the bare query with no error; the GUI cannot tell "no matches" from "namespace never populated".

#### 3.1.2 POST /query/stream

**What it does.** The same query as `/query`, delivered as Server-Sent Events. The run is resolved eagerly inside the FastAPI dependency `_resolve_streamed_envelope` (rest.py:260-275), so refusals return a normal 422 JSON before any SSE byte. The finished envelope is then split by `stream_envelope_events` (engine.py:470-481). It is not a token-level stream of the answer. The in-process `Databasise.query_stream` (engine.py:576-594) is not called by REST.

**Request.** Identical to `POST /query`: `QueryRequest {query, selector}` (rest.py:114-116, 277-289).

**Response.** 200 `text/event-stream`. Each event is one `data:` line holding JSON, with no `event:` name, so the client branches on the JSON `kind` field:
1. `{"kind":"evidence","evidence":{ref, namespace, kind, score, tier}}`: zero or more, one per envelope evidence item, in envelope order. The inner `evidence.kind` is the ItemKind and is distinct from the outer event `kind`.
2. `{"kind":"final", answer, trace_token, depth_label, partial, degraded, stop_reason, degradation_reason, token_accounting, seam_events}`: exactly one, last. Every envelope field except `evidence`.

`: ping` comments are sent only after 15 s idle (fastapi/sse.py:241); because all events are yielded at once after the run, none occur in practice. The stream ends after the final event.

**Refusals.** Same as `POST /query`, all raised before streaming starts, so they arrive as refusal 422 or validation 422 JSON, not as SSE events. `stream_envelope_events` raises no refusal.

**Live check.** Content type `text/event-stream; charset=utf-8`; events framed as `data: <json>\n\n` with no `event:` line; a run with no evidence emits only the `final` event; no `: ping` line was observed; refusals returned 422 JSON before any SSE byte. The alias-to-HippoRAG path was not called on this route; it shares the `/query` code path (500).

**What the GUI needs.**
- Screen: Query console, with a "stream" toggle.
- Implementation: `fetch()` POST plus a `ReadableStream` SSE parser; check status and content type before parsing (422 JSON means a refusal).
- States: running (no bytes arrive until the run finishes, so show an indeterminate spinner, not progress), receiving evidence (append rows), final (fill answer, badges, token table, seam events, trace link), error, disconnected (stream closed without a final event). Ignore `: ping` lines.
- Chained calls: same as `/query`.

**Gaps.** No incremental answer tokens and no node-level progress, so the stream gives no latency benefit over `/query`. No event ids, so no resume. No count of total evidence items before `final`. No cancel. MCP has no streaming equivalent.

#### 3.1.3 POST /compare

**What it does.** Runs one query object against N selectors and returns the per-selector envelopes for side-by-side inspection. No verdict, aggregate or winner is computed. Arms run sequentially in the caller's order through the same `_execute` path as `/query` (rest.py:256-258, engine.py:596-650, databasise/seam/compare.py:62-84). Each arm persists its own trace.

**Request.** `CompareRequest` (rest.py:119-124):
- `query`: QueryObject, required.
- `selectors`: list[Selector], required, no default. Length 0 refuses; length 1 is a plain run; length 2 or more is a comparison.

Response key per selector (`render_selector_key`, compare.py:42-59, using `CAPABILITY_KEY_SEPARATOR` at line 39): alias → the alias string; harness → the harness string; capability → values joined by `+` in caller order (no sort, no de-duplication, no case folding); `capability: []` → `""`; no member set → `default`. Example: `[{"capability":"reads_vector"},{"capability":["reads_graph","calls_llm"]}]` gives keys `reads_vector` and `reads_graph+calls_llm` (naive and HippoRAG respectively). Keys carry no kind prefix, so they collide across kinds: alias `default` vs the default selector, alias `a+b` vs capability `["a","b"]`, alias `x` vs harness `x` (a cross-kind collision needs both selectors to resolve first).

**Response.** 200, route type `Any` (empty OpenAPI schema). Two shapes:
- One selector: a bare `ResponseEnvelope`, not a one-key map (engine.py:642-643).
- Two or more: `{<selector_key>: ResponseEnvelope, ...}` in caller order (engine.py:644-650).

All-or-nothing: any arm's refusal aborts the whole comparison and returns no partial map.

**Refusals.** Evaluation order (engine.py:638-650, compare.py:78-83):
1. `check_consumable` runs first: `EmptyQueryObjectError`, `UnconsumableQueryMemberError`. So `{query:{}, selectors:[]}` returns `EmptyQueryObjectError`.
2. `EmptyComparisonRequestError` (no attributes) when `selectors` is `[]` (refusals.py:248-261).
3. With one or more selectors, every selector is resolved before any arm runs: `UnsatisfiableSelectorError {selector_kind, requested}`; `MutableStoreComparisonExcludedError {component}` when a resolved wiring's effects include `mutates_store`; `component` is the capability `mutates_store`, never the part `name@version`, and the message names no part either (13 REVIEW A-WR-01, the D-15 rule; the part name goes to the server log only). The `mutates_store` check runs for exactly one selector too (13-07, WIRE-17, D-11: CONTRACT.md section 14.4 point 3), and a one-selector call that passes it returns the bare envelope. `MutableStoreComparisonExcludedError` is unreachable with the shipped wirings: no candidate in `all_wirings()` has `mutates_store` in its part-effect union; the wirings that declare it (wirings/lightrag/corpus-delete.json and the cbm wiring) are not query candidates. The cbm wiring is a test fixture, `databasise/tests/fixtures/codebase-memory-mcp.json`, and the `codebase-memory-mcp` part is not in `default_registry()` (Phase 14, D-13); tests reach the refusal by registering `CODEBASE_MEMORY_MCP_PART` with `registry=` and adding the fixture wiring to the candidate pool (tests/seam/test_mutable_store_exclusion.py).
4. `DuplicateComparisonKeyError {key}` when two selectors render the same key (for example two defaults, or a cross-kind collision). Raised inside `compare_arms` after earlier arms have already run, spent tokens and persisted traces (compare.py:79-83); the up-front loop checks only `mutates_store` (engine.py:644-649).
5. `UnbudgetableParticipantError` from any arm (an injected client that reports `unbudgetable`, or the shipped client over a response without `usage`, triggers it, see `/query`), and every other `/query` refusal from any arm: `UnparseableWiringError {violations}`, `InvalidNodeSettingError {setting}`, `InvalidGuardDeclarationError`, `AmbiguousAnswerPositionError`, and `ForeignEngineRefusalError` with `MalformedDriverOutput`, `StoreFault`, `StoreCorrupted` (502) or `EnvironmentDigestUnavailable` (503). The post-dispatch ones carry the failing arm's `trace_token` (D-04); earlier arms' traces stay persisted.

Validation 422: multi-member selector, hash-shaped value (`loc: ['body','selectors',<index>]`), unknown keys, missing `selectors`. 500 paths: as `/query`. An alias row naming an unresolvable wiring is a 422 `UnsatisfiableSelectorError` raised in the pre-resolution loop (engine.py:644-645) before any arm runs, and a HippoRAG alias resolves.

**Live check.** `selectors: [{},{}]` → 422 `DuplicateComparisonKeyError {key: "default"}` after the first arm had executed and written a trace. `[{}, {alias: "hr"}]` with `hr` promoted from HippoRAG → the alias resolves to the HippoRAG wiring (Phase 14, D-05; not re-run live). `[{}, {capability: "writes_graph"}]` → 200 with keys `default` and `writes_graph` (naive and HippoRAG). `[{capability: []}, {capability: "calls_rerank"}]` → 200 with keys `""` and `calls_rerank`. One selector → bare envelope. `{capability: "mutates_store"}` (one or two selectors) → 422 `UnsatisfiableSelectorError`, not `MutableStoreComparisonExcludedError`, because no shipped wiring declares it; with the codebase-memory-mcp part registered through `registry=` and its fixture wiring added to the candidates, one or two selectors → 422 `MutableStoreComparisonExcludedError`.

**What the GUI needs.**
- Screen: Compare (side by side).
- Controls: shared query editor (same as Query console); a selector list builder with add/remove/reorder rows, each row a Default/Alias/Capability/Harness picker; a live preview of each row's rendered key with a client-side duplicate-key warning; a warning that 0 rows is invalid and 1 row is a plain run.
- Run button with one spinner (total time is the sum of the arms; no per-arm progress).
- Display: N columns (tabs on narrow screens) keyed by selector key, each with answer, badges, evidence list, token table, seam events and trace link. Optional client-side diff aids: evidence `ref` overlap between columns; token totals per column (rows align by `counted_by` because they are sorted).
- Response handling: decide by the number of selectors sent (1 → bare envelope, 2+ → keyed map; engine.py:642-650). Checking for an `answer` key is ambiguous, because an alias literally named `answer` is a valid key.
- Pre-submit checks: render keys with the same un-prefixed rule as the server and reject duplicates, including cross-kind ones; reject an empty capability set (the server refuses it as `EmptyCapabilitySelectorError`). Every arm, hybrid and global included, can be a column (section 3.0, D-01).
- Error state: refusal banner naming `refusal_type` and `key` / `component` / `requested`. A node failure in one arm does not abort the comparison: that column arrives as a 200 partial envelope with its own `stop_reason` (section 3.0), so each column needs its own partial-run state.
- Chained calls: `/evidence/resolve` and `/trace/resolve` per column; `/promote` per column ("promote this arm", using that column's `trace_token`), disabled for partial columns (the server refuses a partial trace on promote, section 3.5).

**Gaps.** Polymorphic response with no generated type. No per-arm streaming, parallelism or cancel. A late `DuplicateComparisonKeyError` discards completed arms. No way to check before submitting which selectors would be excluded for `mutates_store` (unreachable today). Columns are labelled only by the caller's selector key. A naive-versus-graph-arm comparison compares chunk-selection strategies, not KG-context answering, and a LightRAG-versus-HippoRAG comparison sets a generated answer beside a passage dump (section 3.0). Graph-arm retrieval also differs from v1: relations are not sorted by (rank, weight) before truncation (parts_core/lightrag/entity_hydrate_expand.py:72-91 vs v1/lightrag/operate.py:5259-5261) and entity and relation chunks are selected in one pass (chunk_sel_kg.py:157 vs operate.py:4758-4795), so a v1 parity view reflects these differences, not only the decomposition.

### 3.2 Screen: Evidence & Trace

#### 3.2.1 POST /evidence/resolve

**What it does.** Takes one `EvidenceRef` from an envelope and returns the vector-store record it points to. The envelope holds references only, never content (evidence.py:22-27), so this is the only way to see the text behind a piece of evidence. `Databasise.resolve_evidence` (engine.py:1083-1094) calls `resolve_evidence_ref(ref, stores["vector"])` (evidence.py:114-125), which does `vector_store.select(ref.namespace).get_by_id(ref.ref)`. It opens the kv, vector and graph stores with default (LightRAG) namespaces and finalizes them in a `finally` block, although only the vector store is read, so it takes the `chunk_entity_relation` RocksDB lock even for `hipporag-chunks` evidence. The docstring's "the same way query does" (engine.py:1086-1087) is inaccurate: query passes the resolved wiring (engine.py:987), resolve passes none (engine.py:1089). Each call builds a new store, which reads the JSON sidecar and SHA-256-checksums the entire Faiss index file (vector.py:126-137), so latency grows with index size.

**Request.** Body is a bare `EvidenceRef`, not wrapped (rest.py:291-293). Only `ref` and `namespace` affect the lookup; `kind`, `score` and `tier` are ignored (evidence.py:121-125), but `kind` is a required field with no default (evidence.py:56), so omitting it gives a validation 422. The GUI should send the object exactly as the envelope returned it.

**Response.** 200 `dict[str, Any]` (rest.py:292), the value of `FaissVectorStore.get_by_id`: `{"id": doc_id, **metadata}` with no score (databasise/stores/vector.py:327-338). Shape by namespace:
- `hipporag-chunks`: `{id, document_id: str, ordinal: int, content: str}` (databasise/parts_core/hipporag/chunk_embed.py:97-115).
- `chunks` (LightRAG): `{id, ...every key of the imported v1 Faiss metadata record except __id__, __vector__, __created_at__}` (databasise/parity/import_index.py:163-192). The v2 code does not list these keys; the chunk_embed.py:105-108 docstring states the v1 metadata carries `content`. v1 registers chunk metadata as `full_doc_id`, `content`, `file_path` (v1/lightrag/lightrag.py:1181), so there is no `document_id` key on LightRAG records. A metadata key named `id` overrides the real id in this response, and a metadata key `score` appears as a spurious field (vector.py:338); in `query()` both override the real id and score, and `EvidenceRef` is minted from the overridden values (vector.py:235, 267, 312). No current writer uses these keys.

**Refusals.**
- Refusal 422 `UnresolvableEvidenceReferenceError {ref: {ref, namespace, kind, score, tier}}` when the namespace holds no committed entry for `ref`, including a namespace that does not exist (evidence.py:82-92, 123-124). An index file whose sidecar is missing (a crash between the two `os.replace` calls on the first commit, vector.py:427-428) opens silently as an empty store (vector.py:126 requires both files), so this case also returns this 422 instead of a corruption error, contrary to the module docstring (vector.py:28-37).
- Validation 422: missing field, wrong type, extra field.
- 500: `VectorStoreCorruptedError` on an index checksum mismatch (vector.py:68, 126-133); a pycozo lock exception when a LightRAG query, ingest, delete or health probe holds the `chunk_entity_relation` graph store (section 1, "Latency and concurrency").
- HippoRAG PPR-branch evidence never resolves: PPR emits item ids equal to graph vertex names `chunk:<chunk_id>` (parts_core/hipporag/ppr.py:84-88, passage_edges.py:40-41), while chunk-embed writes vector and KV records under the bare `chunk_id` (chunk_embed.py:96-119). When the fact filter keeps at least one fact (the normal path), the answer is `""` and every evidence ref returns `UnresolvableEvidenceReferenceError`. tests/seam/test_hipporag_write_path.py:59-69 documents this and forces the DPR branch to avoid it.

**Live check.** `{ref:"chunk-1", namespace:"../../etc", kind:"text_chunk"}` → 422 `UnresolvableEvidenceReferenceError`, and the directory `/tmp/etc` was created outside the store root during the call (removed afterwards). An unknown plain namespace `zzz` → 422 and left an empty `<workspace>/zzz` directory. `kind: "entity"` for a text chunk → 200 with the record (kind ignored).

**What the GUI needs.**
- Screen: Evidence Inspector, opened from the evidence list of a Query result and of each Compare column.
- Controls: no free-form form needed. Row action "Open". An optional advanced manual lookup with `ref` (text), `namespace` (select restricted to `chunks` / `hipporag-chunks`, never free text; see Gaps), `kind` fixed to `text_chunk`.
- Display: `content` as readable text; `document_id` and `ordinal` as metadata chips when present; every remaining key in a generic key/value table, because the keys are open-ended. Keep the `score` from the envelope; resolve returns none.
- States: loading (per row), resolved, refusal ("record no longer present; the store changed since the query"), validation error, 500.
- Cache results per `(namespace, ref)` for the session.
- Chained calls: from `document_id` to the Corpus screen; back to `/trace/resolve` with the same envelope's `trace_token`.

**Gaps.**
- No batch resolve; one round trip, with a full store open and close and a full index checksum, per reference. Client-side caching and lazy resolution are necessary.
- No route lists valid namespaces. Note that `/evidence/resolve` already accepts any vector namespace (`entities`, `relationships`, `hipporag-entities`, `hipporag-facts`) and returns that record's stored metadata (vector.py:327-338).
- No response schema.
- `ChunkRef` provenance members (corpus_id, recipe@version, ordinal, content_hash) are not populated on EvidenceRef (evidence.py:6-20). Without a content hash the GUI cannot detect that a resolved chunk was overwritten after the run: HippoRAG chunk ids are `sha256(f"{document_id}:{ordinal}")` (chunk_embed.py:80), so re-ingesting the same `document_id` with different text replaces the record behind an old ref, and higher ordinals from the old text stay.
- Path validation defect: `select()` on an unknown namespace builds a `FaissVectorStore`, whose constructor runs `mkdir(parents=True)` on `<store_root>/<workspace>/<namespace>` (vector.py:112-117, 494-501). `namespace` is not validated, so `../x` or an absolute path creates a directory outside the workspace before the 422 returns (an absolute namespace replaces the whole path). If the target already holds a valid index, that index is loaded and its records can be read (for example another workspace's chunks). Fix: validate against `_NAMESPACE_TOKEN_RE` `^[A-Za-z0-9-]+$` (databasise/namespaces.py:37), which accepts every current vector namespace, or a known set (section 5.2).
- LightRAG freshness: LightRAG ingest and delete run v1 in a subprocess against `v1/.corpus_working_dir` and do not touch the v2 `chunks` namespace (v1_corpus_adapter.py:31, 129; engine.py:744-749; full_delete.py:226-232). The importer CLI writes it only from `v1/.parity_working_dir` into `v1/.parity_v2_store` under the corpus-hash workspace (parity/import_index.py:84-85, 498-511), so LightRAG evidence reflects the last parity import of the fixed parity corpus, never documents ingested through REST, and deleted documents stay resolvable. HippoRAG writes `hipporag-chunks` during ingest (chunk_embed.py:96-114).
- `hipporag-chunks` puts a modality name in a consumer-visible field (CONTRACT §18.3, docs/system-model/CONTRACT.md:785); see open question 7.

#### 3.2.2 POST /trace/resolve

**What it does.** Exchanges the opaque `trace_token` from an envelope for the stored `RunRecord` of that run. With `debug: false` the result is reduced by an allow-list to run-level fields. With `debug: true` the full record is returned, including internal identities and the per-node trace. The record is written once per `_execute` call (engine.py:1068), so each `/compare` arm gets its own token, and never changed (trace_store.py:17-18). Since Phase 13 (D-04) the record is written right after the nodes run, before any post-dispatch refusal, so a run that ended in a store fault, two answering provides nodes, `MalformedDriverOutput`, `UnbudgetableParticipantError` or a run-time `InvalidGuardDeclarationError` is resolvable through the `trace_token` on that refusal's body. No record is written for a refusal raised before dispatch (section 3.1.1). `trace.db` sits at `<store_root>/trace.db` with no workspace column (trace_store.py:71, 84-89), so apps on one store root with different workspaces resolve each other's tokens, and rows are never deleted. Engine method `Databasise.resolve_trace(trace_reference, *, debug=False)` (engine.py:1096-1109), backed by `TraceStore.resolve` (databasise/seam/trace_store.py:106-114).

**Request.** `TraceRequest` (rest.py:127-129):
- `trace_reference`: str, required. A `secrets.token_urlsafe(32)` string, 43 characters, no structure (trace_store.py:47-49, 98).
- `debug`: bool, default false. Not access-controlled. A strict JSON boolean (Phase 14, D-10): a string, a number or null is a 422 validation error whose body carries no run record field.

**Response.** 200 `dict[str, Any]` from `RunRecord.to_dict()` (runner/trace.py:154-171).

`debug: false`: only `_NON_DEBUG_TRACE_FIELDS` (engine.py:265-284; filter engine.py:1109):

| Field | Type / value today |
|---|---|
| `partial`, `degraded` | bool; `degraded` is also true on a completed run whose guard fired (section 3.0) |
| `stop_reason`, `degradation_reason` | closed code \| null, the same values as on the envelope (section 3.0, Phase 13 D-05) |
| `bundle_ref` | sentinel `"sentinel:no-eval-bundle-until-phase-2"` (trace.py:42, 112) |
| `corpus_snapshot_hash` | sentinel `"sentinel:no-corpus-snapshot-until-phase-2"` (trace.py:43, 113) |
| `executor_version` | `"databasise@0.1.0"` (engine.py:255) |
| `determinism_setting` | `"cache-bypassed"` (engine.py:256) |
| `concurrency_setting` | `"sequential"` (engine.py:257). Since Phase 13 (D-17) the scheduler also runs it truthfully: each ready batch is sorted by node id and its nodes are awaited one at a time, so no two nodes of a run execute in parallel (a part's own internal concurrency, such as openie's semaphore, is unaffected). |
| `arm_execution_order` | int, `0` for seam runs (engine.py:1022) |

`stop_reason` and `degradation_reason` on the `debug: false` allow-list are closed node-free codes since Phase 13 (D-05); a failed node's id and cause appear only in the `debug: true` NodeTrace (`cross_process_failure_cause`).

`debug: true` adds (engine.py:1008-1031): `run_id` (uuid4, 1018), `wiring_id` (1010-1012), `wiring_instance_hash` (`sha256:<64 hex>`, 1009), `arm_id` (the candidate arm name, `"seam"` when none), and `nodes`, a flat list of NodeTrace dicts (trace.py). Since Phase 13 (D-03) these identify the arm: each patched LightRAG arm has its own `wiring_id` (`lightrag-<arm>`; naive keeps `lightrag-base`), and `wiring_instance_hash` is computed from the full resolved wiring before the query, token-allowance and max_total_tokens injections, so two queries on one arm record one hash. Its `sha256:<64 hex>` form is exactly the shape the selector refuses, so the GUI must never place it in a selector field. NodeTrace fields:

`node_id`, `instance_hash`, `depth`, `effective_depth`, `tier: null`, `feed_tier: null` (Phase 13 D-12), `status` (`completed`, `failed`, `cancelled` or `not-scheduled`, D-13), `execution_mode` (stamped on every node), `wall_clock_ms: int`, `cache_hit: bool | null` (null unless the part reports it, D-14), `guards_fired: list[str]`, `budget_state: str`, `spent: int | null`, `allowance: int | null`, `realised_budget_share: float` (0..1), `cross_process_failure_cause: str | null`, `resumable: bool`, `tokens: {prompt_tokens, completion_tokens, cached_read_tokens, call_count, counted_by}` (runner/trace.py `NodeTrace`). Every node of the pruned run wiring gets exactly one trace (WIRE-10).

Notes for display: the meter emits only `within_budget` or `halted` (`degraded` is in the Literal but never produced, runner/budget.py:42, 138). `halted` is also written for a node whose execution failed, with `realised_budget_share: 0.0` and `cross_process_failure_cause` set (scheduler.py:600-615), so the GUI must read `cross_process_failure_cause` before calling a halt a budget halt. A budget halt's `stop_reason` is the bare literal `"budget_halt"` with no node id (scheduler.py:655), and `realised_budget_share` is capped at 1.0 (runner/budget.py:118); overspend can be computed client-side as `tokens.prompt_tokens + tokens.completion_tokens` minus the 1,000,000 seam allowance (budget.py:134-135, engine.py:263).

Further display caveats:

- `nodes` lists only dispatched nodes. Siblings cancelled in the failing batch and nodes in later batches get no entry (scheduler.py:626-634, 671-677), so the node table is incomplete for partial runs and cannot be assumed to contain the full wiring.
- A failed node's `wall_clock_ms` is stamped 0 even if it ran until a timeout (scheduler.py:603).
- `cache_hit` is always false in production; only the test part `parts_core/fake_llm_caller.py`:63 reports it (scheduler.py:403).
- `guards_fired` can be non-empty only for HippoRAG `fact-filter` (wirings/hipporag/base.json:70-77). The LightRAG local/global keyword fall-through guards are declared in a top-level patch `guards` array that `resolve_arm` ignores (arm-local.json-patch.json:29, arm-global.json-patch.json:29; resolve.py:107-109). Guard evaluation compares the whole node output to a scalar (runner/guards.py:83), which works for fact-filter only through a dict subclass with custom equality (fact_filter.py:64-84).
- `tier` and `feed_tier` are the placeholder `"T3"`, which CONTRACT §4 reserves for a performed intervention plus a verified re-run (runner/trace.py:44, 79-80); show them as placeholders.
- The per-node `execution_mode` (in-process or subprocess) is derived at scheduler.py:422 but discarded (scheduler.py:638), so placement is not shown.
- The trace has no run start timestamp (trace.py:101-117); the GUI must record it.

**Refusals.** Refusal 422 `UnknownTraceReferenceError {trace_reference}` when the token is not in `trace.db` (trace_store.py:52-62, 113). No expiry mechanism exists. Validation 422 for missing or wrongly typed fields.

**Live check.** `{trace_reference: "nope"}` → 422 `UnknownTraceReferenceError`. `{trace_reference: <token>, debug: "yes"}` → 200 with `run_id`, `wiring_id: "lightrag-base"`, `wiring_instance_hash` and `nodes`. Debug node keys observed: `budget_state, cache_hit, cross_process_failure_cause, depth, effective_depth, feed_tier, guards_fired, instance_hash, node_id, realised_budget_share, resumable, tier, tokens, wall_clock_ms`; no node output, config or deps. With `clients=None` the naive arm traced 2 of 7 nodes (`embedder-index`, `embedder-query`) and HippoRAG 2 of 13 (`chunk-embed`, `fact-score`).

**What the GUI needs.**
- Screen: Trace Inspector, reached from the `trace_token` of a Query or Compare result, and from the trace picker in the ledger forms.
- Controls: `trace_reference` prefilled, with a paste box; a "Debug (internal identities + node trace)" toggle that re-requests with `debug: true`.
- Summary header (both modes): status badge (clean / partial), `stop_reason`, `degradation_reason`, `executor_version`, `concurrency_setting`, `determinism_setting`, `arm_execution_order`; `bundle_ref` and `corpus_snapshot_hash` shown as "not yet recorded" when they start with `sentinel:`.
- Debug view: identity panel (`run_id`, `wiring_id`, `wiring_instance_hash`, `arm_id`) with copy buttons; node table with every NodeTrace field, `tier`/`feed_tier` marked as placeholders, halted and failed nodes highlighted; per-run sums of `wall_clock_ms` and tokens; an optional bar chart of `wall_clock_ms` in array order.
- States: loading; non-debug result (expect no `nodes` key, not an empty list); debug result; 422 unknown reference; validation error.
- Promote helper: first exclude traces with `partial: true` (readable without debug). Then fetch each selected trace with `debug: true` and compare `arm_id`. Promotion takes the record's own `arm_id` when it names a wiring (D-01, `_arm_name_for_record`, promotion.py:144-152); only a record whose `arm_id` names no wiring (one persisted before `arm_id` was recorded, or `"seam"`) falls back to matching the set of completed `nodes[].node_id` against every wiring (promotion.py:109-141, 153-154). So differing `arm_id` values, or differing node sets for such older records, predict `DisagreeingPromotionTraceIdsError`. A partial trace is refused on promote as `PartialRunEvidenceError`, before arm matching; rollback and retire identify a partial trace by its `arm_id` (section 3.5). The six candidate node sets are distinct (naive 7, bypass 1, hybrid 17, local 15, global 15, hipporag 14), so an older complete trace still maps to one arm. The arm name is returned only in the debug view's `arm_id`.
- Chained calls: copy the token into the ledger forms; open the same query's evidence.

**Gaps.**
- No trace list or search; `trace.db` has a `created_at` column (trace_store.py:84-89) that is never returned (trace_store.py:110).
- The record holds no query text, selector or answer, so the GUI must keep the query-to-token mapping.

### 3.3 Screen: Documents & Jobs

Write-path availability (from the wiring files): `databasise/wirings/lightrag/` ships `corpus-ingest.json` and `corpus-delete.json`; `databasise/wirings/hipporag/` ships only `corpus-ingest.json`, whose target node is kind `embedder`, not `opaque` (wirings/hipporag/corpus-ingest.json:8). So HippoRAG accepts text ingest and delete (HIPP-16) and refuses raw upload (`NoRawUploadPathForModalityError`). The mockup can hard-code this until an endpoint exposes it. HippoRAG text ingest needs both `embedding` and `llm` clients (chunk_embed.py:93, openie node), except for empty text, which returns zero chunks before any client is touched (chunk_embed.py:69-70, 90-91). The raw-upload gate reads the wiring node's declared `kind` (engine.py:690), which is never checked against the registered part's kind (validator/parse.py has no kind check).

LightRAG writes and LightRAG queries use different stores (section 1, "Fixed v1 working directory"): a document ingested here is visible in `/corpus` and `/jobs` but never in `/query` or `/evidence/resolve` on a LightRAG selector, and a LightRAG delete does not remove the document from query results. Ingest and delete under a LightRAG selector ignore the arm: every LightRAG alias, capability or default runs the same corpus wiring (engine.py:349-362).

#### 3.3.1 POST /documents

**What it does.** Ingests one document given in a JSON body into the index of the modality the selector resolves to (default modality when omitted). The route awaits `Databasise.ingest(document, selector)` (rest.py:299-301, engine.py:652-769). On the LightRAG path the v1 driver awaits enqueue and processing (databasise/foreign/v1_corpus_driver_script.py:185-198), so the HTTP call returns only after the document has been processed. On LightRAG "the index" is `v1/.corpus_working_dir`, which `/query` does not read (section 3.3 intro). The call returns 200 even when v1 marks the document failed or rejects it as a duplicate: processing failures are recorded in doc status, not raised, and when nothing is new v1 returns without enqueuing (v1/lightrag/pipeline.py:648, 683-700, 797-800). The driver also processes v1's whole pending queue, not only this document (v1_corpus_driver_script.py:192). On HippoRAG, `ingest()` flushes every store before checking for node failures (engine.py:750-751 before 761), so a failure after `chunk-embed` (for example openie with no `llm` client) commits the chunk vectors and KV records and then returns 422; HippoRAG has no delete path to remove them. HippoRAG OpenIE parse failures silently yield zero triples with no counter (parts_core/hipporag/openie.py:72-108), and the ingest still reports success.

**Request.** `IngestRequest` (rest.py:132-134):
- `document`: IngestDocument, required (corpus.py:61-89, `extra="forbid"`):
  - `text`: str \| null
  - `raw`: bytes \| null (in a JSON body pydantic v2 reads this as a UTF-8 string, not base64)
  - `document_id`: str \| null; null → server mints `uuid4().hex`; a caller value must match `^[A-Za-z0-9_-]+$` (corpus.py:56, engine.py:678-682); an empty string is treated as absent (engine.py:678)
  - `file_name`: str \| null. Discarded: the engine never reads it (only rest.py:330-331 and mcp/tools.py:122-124 set it); v1 records `unknown_source` as the file path for text ingest (v1/lightrag/pipeline.py:374-376). The corpus.py:6-9 docstring claim that it is carried into the job payload is false.
  - `content_type`: str \| null. Discarded, as `file_name`.
  - Exactly one of `text` / `raw` must be set; only `None` counts as absent, so `text: ""` is accepted (corpus.py:79-81). Size cap `MAX_DOCUMENT_BYTES = 25*1024*1024 = 26,214,400` bytes, measured on `len(raw)` or `len(text.encode("utf-8"))` (corpus.py:44, 83-88).
- `selector`: Selector \| null.

Re-ingesting an existing `document_id` on LightRAG is not an update: v1 rejects it as a duplicate and writes a failed `dup-<hash>` row (pipeline.py:648, 708-735). Delete first. A caller id ending in a single newline (`abc\n`) passes the pattern check, because `re.match` with `$` matches before a trailing newline (corpus.py:56, 217), and becomes part of the on-disk file name.

**Response.** 200 `IngestJob` (corpus.py:92-99): `job_id: str`, always the engine-minted uuid hex track id (engine.py:683, 719, 769; v1 keeps a non-empty track id), `enqueued: int`. For LightRAG `enqueued` is always 1 (the driver returns `len(documents)`, v1_corpus_driver_script.py:198), even when v1 enqueued nothing; for HippoRAG it is 1 because the terminal node reports none (engine.py:765-769). `enqueued` is not a success signal; poll `/jobs` and read the row status.

**Refusals.**
- Refusal 422: `NoRawUploadPathForModalityError {operation:'ingest'}` (raw set and the target node is not opaque, engine.py:690-698); `UnsatisfiableSelectorError`; `ForeignEngineRefusalError {operation:'ingest', cause: str}` when a node fails (engine.py:365-379, 761), including `CorpusOpTimeoutError` after 900 s. For HippoRAG the `cause` is often the synthesized "the 'ingest' node produced no result and no exception", because only the provides node is inspected (engine.py:385-394). Before dispatch (Phase 13 WIRE-05, D-07, D-22): `UnparseableWiringError {violations}`, `InvalidNodeSettingError {setting}`, `InvalidGuardDeclarationError` and the 503 `ForeignEngineRefusalError {failure_class: 'EnvironmentDigestUnavailable'}`; the same four apply to `DELETE /documents/{document_id}` and `POST /documents/upload`. `NoWritePathForModalityError {operation:'ingest'}` is a kept mapping that no shipped wiring reaches: both selectable families ship `corpus-ingest.json` (wirings/resolve.py:35). It does occur on `POST /documents/{document_id}/retry` (no section in this inventory) as `{operation:'retry'}` for any HippoRAG selector, because only LightRAG has a v1 pipeline to resume.
- Validation 422: `AmbiguousIngestPayloadError` (both or neither of text/raw) and `OversizedDocumentError` (`detail[0].ctx.error` carries `actual_bytes`/`limit_bytes` or `set_members`); multi-member and hash-shaped selectors.
- 500: a caller `document_id` that fails `^[A-Za-z0-9_-]+$` (for example `../x`) raises a bare `ValueError` in `generated_on_disk_name` (engine.py:682); delete maps the same check to 422 `UnknownDocumentError` (engine.py:800-803). A graph-store lock collision: stores are built before the `try` (engine.py:730), so a concurrent same-namespace query, ingest or delete returns 500.

**Live check.** `{document:{text:"x", document_id:"../evil"}}` → 500. `{document:{}}` → validation 422 with msg `"Value error, AmbiguousIngestPayloadError: ..."` and `ctx.error {set_members: []}`. Oversized text → validation 422 echoing the whole input. `{document:{text:""}, selector:{capability:["writes_graph"]}}` → 200 `{enqueued: 1}`. HippoRAG text ingest via `{capability:["writes_graph"]}` → 200 with a `job_id` the status op never sees. `{document:{raw:"hello"}}` in a JSON body → 200 (UTF-8 bytes, not base64). Alias `hr` promoted from HippoRAG → 500. HippoRAG ingest without clients → 422 `ForeignEngineRefusalError` with the synthesized cause.

**What the GUI needs.**
- Screen: Ingest, "Paste text" tab.
- Controls: text area (block empty text); optional `document_id` with client-side pattern check `^[A-Za-z0-9_-]+$` (no trailing newline) and an auto-generate hint; do not offer `file_name` / `content_type` as stored metadata (they are discarded); selector control (Default / Alias / Capability / Harness); a UTF-8 byte counter against 26,214,400. Serialize with other engine calls (graph lock) and disable Query on the same namespace while an ingest runs.
- Submit disabled while in flight; long-running spinner (LLM extraction on the LightRAG path).
- Success: show `job_id` (copyable) and `enqueued`; store the job id client-side; chain to `GET /jobs/{job_id}`.
- Error rendering: refusal 422, validation 422, 500.
- Chained calls: `GET /jobs/{job_id}`, `GET /corpus`, `GET /corpus/counts`.

**Gaps.** No route lists valid selectors or which modalities accept raw or delete. Invalid `document_id` is a 500. No progress events, timeout field or cancel. Ingest produces no trace token and no token accounting (corpus.py:92-99), so the budget panel cannot cover writes; internally the LightRAG ingest node always reports `counted_by: "unbudgetable"` because the driver returns `usage: None` (v1_corpus_driver_script.py:198; full_ingest.py:226-238), so write-side spend is unbudgetable, not zero. Ingest produces no seam events (no recorder, engine.py:732-739; full-ingest declares `writes_artifact` rather than `mutates_store`, parts_core/declared_only.py:72-81). Documents ingested under HippoRAG do not appear in `/corpus` or `/jobs` (section 3.4.2). HippoRAG ingest also: gives new entities no synonymy edges in their own ingest (self_knn reads only committed entries, synonymy_edges.py:53-54, vector.py:288-289); overwrites edge weights and fact chunk ids instead of merging across ingests (graph.py:291-296, kv.py:84-87); gives no graph vertex to chunks without triples (passage_edges.py:50-63). No HippoRAG index statistics are returned; graph-augment-persist's node and edge counts are discarded (engine.py:765-769).

#### 3.3.2 POST /documents/upload

**What it does.** The same ingest, delivered as `multipart/form-data` so a binary file can be uploaded. The route reads the whole file into memory, builds `IngestDocument(raw=..., document_id, file_name=file.filename, content_type=file.content_type)` (rest.py:327-332), parses the optional selector form field (rest.py:333-336), then awaits `engine.ingest` (rest.py:303-337). Raw bytes are written to `store_root/corpus-inbox/<document_id>.bin` (engine.py:706-710), but v1 never reads that file. The engine stamps `text: ""`, `file_paths=[inbox path]` and `docs_format=pending_parse` (engine.py:711-713); the driver always passes explicit `ids` (v1_corpus_driver_script.py:180-191), and v1 gives `ids` priority over `docs_format` and enqueues the empty text body as a RAW document (v1/lightrag/pipeline.py:561-572). So file upload on the LightRAG path does not index the file: the route returns 200 with `enqueued: 1` while v1 stores an empty document (in a live v1 run the first such upload ended `failed` with "Set of Tasks/Futures is empty."). Every later upload has the same empty-content hash and is rejected by v1 as a duplicate, producing a failed `dup-<md5>` row under that job's track id with "Identical content already exists under another filename" (pipeline.py:504-531, 683-700, 758-781). The existing tests mock the driver and only assert the config value (tests/parts_core/lightrag/test_full_ingest.py:285-303). The inbox file is never deleted, on success, refusal or document delete, and the directory is shared by all workspaces on the store root (engine.py:707).

**Request.** Form fields (rest.py:304-308):
- `file`: UploadFile, required. Its filename becomes `file_name` and its part Content-Type becomes `content_type`; neither is settable separately.
- `document_id`: str, optional (same pattern rule; empty → minted).
- `selector`: str, optional, a JSON-encoded Selector such as `'{"alias":"main"}'`, parsed with `Selector.model_validate_json`. An empty string is treated as no selector (rest.py:334). The JSON literal `"null"` (and `"[]"`) is refused as `MalformedSelectorPayloadError`, so the GUI must omit the field for the default selector, not send null.

Cap: 26,214,400 bytes on `len(raw)`, checked only after the full body is in memory.

**Response.** 200 `IngestJob {job_id, enqueued}`.

**Refusals.**
- Refusal 422: `MalformedSelectorPayloadError {field:'selector'}` for any pydantic error from the selector field, including invalid JSON, `null`, a multi-member selector and a hash-shaped value (rest.py:333-336, refusals.py:231-246); `UnsatisfiableSelectorError`; `NoRawUploadPathForModalityError` (every upload under a HippoRAG selector, refused before the inbox file is written); `ForeignEngineRefusalError` (including `CorpusOpTimeoutError` after 900 s). `NoWritePathForModalityError` is unreachable on ingest (see `/documents`). `AmbiguousIngestPayloadError` cannot occur on this route: `file` is required and `text` is never set.
- Validation 422: missing `file`.
- 500: an oversized file (`OversizedDocumentError` is raised inside `IngestDocument` built in the route body, wrapped into a `ValidationError` that no handler maps; rest.py:326-332), contrary to the route docstring at rest.py:312-313. Because the document is built before the selector is parsed, an oversized file returns 500 even when the selector is also malformed. Also 500 for a bad `document_id`, an alias promoted from HippoRAG, and a graph-store lock collision.
- An empty (0-byte) file is accepted, because `raw=b""` is not None (corpus.py:79-81).

**Live check.** 26,214,401-byte file → 500. 0-byte file → 200 `{enqueued: 1}` and a 0-byte `corpus-inbox/<uuid>.bin` written. `document_id: "../evil"` → 500. `selector: "null"` → 422 `MalformedSelectorPayloadError`; omitting the field → 200. Hash-shaped selector → 422 `MalformedSelectorPayloadError {field: "selector"}`. HippoRAG selector → 422 `NoRawUploadPathForModalityError`. Alias `hr` promoted from HippoRAG → 500. File names containing `../` are accepted and never used as paths.

**What the GUI needs.**
- Screen: Ingest, "Upload file" tab.
- Controls: file picker / drop zone (one file per request); optional `document_id`; selector control, serialized to a JSON string in the `selector` field. Disable the tab, or warn, when the selector targets HippoRAG.
- Client-side pre-checks (required, because the server answers with 500): `0 < file.size <= 26,214,400`; `document_id` pattern.
- Display: upload progress (XHR/fetch upload progress), then an indeterminate "processing" state; on success `job_id`, `enqueued`, chain to `/jobs/{job_id}`.
- Batch: one request per file; track N job ids.

**Gaps.** File upload does not work for LightRAG (the file is never parsed; see above) and is refused for HippoRAG, so the Upload tab has no working target today. Oversize and bad `document_id` are 500s. No list of accepted content types. No multi-file endpoint. Selector shape errors collapse into one refusal with no detail on which rule failed. No processing progress or cancel. No listing or cleanup of `corpus-inbox`.

#### 3.3.3 GET /jobs/{job_id}

**What it does.** Polls one ingest job: one page of per-document status entries for documents tagged with the job's track_id, plus whole-corpus status counts. It runs the v1 driver `status` op in a subprocess with `STATUS_WALL_CLOCK_CEILING_SECONDS = 60.0` (rest.py:339-345, engine.py:853-879, v1_corpus_adapter.py:39).

**Request.** Path `job_id: str`. Query `limit: int = 50` (no lower bound), `offset: int = 0` (`ge=0`) (rest.py:342-343).

**Response.** 200 `JobStatus` (corpus.py:156-167): `job_id: str`, `documents: list[DocumentStatusEntry]` (at most `limit`), `counts: dict[str, int]` (whole corpus, not this job; engine.py:872-878), `next_offset: int | null`. No `total`. Rows are sorted by `document_id`, not by time (v1_corpus_driver_script.py:299). Duplicate attempts appear as rows with `document_id: "dup-<md5>"`, `status: "failed"` and `error_message` "File name already exists..." or "Identical content already exists..." (v1/lightrag/pipeline.py:745-781), so the id in a row may not be the caller's `document_id`.

**Refusals.**
- Refusal 422: `UnknownJobError {job_id}` when the driver reports total 0 for that track_id, including an id that never existed (engine.py:867-870); `PageSizeExceededError {requested, limit: 100}`.
- Validation 422: `offset < 0`, non-integer values.
- 500: `CorpusOpSubprocessError`, `CorpusOpTimeoutError`, `MissingV1InterpreterError` (`RuntimeError` subclasses, v1_corpus_adapter.py:42-75, 118-120), most likely from missing v1 configuration keys (section 1); non-JSON driver output (`json.JSONDecodeError`, v1_corpus_adapter.py:149).

**Live check.** `GET /jobs/job-abc?limit=0` and `?limit=-1` → 200 `{documents: [], next_offset: 0}`; the corpus op received `{'track_id': ..., 'limit': -1, 'offset': 0}`. Corpus op raising `MissingV1InterpreterError` → 500. `GET /jobs/nope` → 422 `UnknownJobError`. A HippoRAG ingest's `job_id` is never seen by the status op, so polling it returns `UnknownJobError` (engine.py:862-870).

**What the GUI needs.**
- Screen: job detail panel / jobs drawer.
- Controls: `job_id` (from the ingest response or pasted); page size 1..100; Next enabled when `next_offset != null`; manual refresh.
- Display: document table (`document_id`, status badge, `updated_at`, expandable `error_message` on failed rows); a counts bar clearly labelled "whole corpus, not this job".
- States: loading, polling (slow interval or manual; each poll is a subprocess), empty page, unknown job, error.
- Client-side job list: no route lists jobs, so the GUI keeps job ids from its ingest responses.
- Chained calls: row action `DELETE /documents/{document_id}`.

**Gaps.** No job list, no `total`, no job-level status, created_at, modality or file name. No selector: status is always read from the v1 doc-status store, so a HippoRAG job is expected to return `UnknownJobError` (engine.py:853-870). No push or SSE.

#### 3.3.4 DELETE /documents/{document_id}

**What it does.** Deletes one document from the index of the modality the selector resolves to by running that modality's `corpus-delete.json` wiring with a store-touch recorder. A well-formed but absent id is a normal `not_found` outcome (rest.py:347-353, engine.py:771-851).

**Request.** Path `document_id: str`, must match `^[A-Za-z0-9_-]+$`. Ids containing `/` (including `%2F`, decoded before routing) do not match the path segment and return 404, not 422. An id ending in a single newline (`%0A`) passes the check (corpus.py:56, 217) and is passed to v1. Optional JSON body `DeleteRequest {selector: Selector | null}` (rest.py:137-143); no body is valid and targets the default modality. A DELETE with a body needs `Content-Type: application/json`; without it FastAPI validates the body as raw bytes and returns a validation 422.

**Response.** 200 `DeletionOutcome` (corpus.py:102-119): `document_id: str`, `status: 'success' | 'not_found' | 'not_allowed' | 'fail'` (`fail` when the node reports none), `message: str` (`""` when none), `seam_events: list[SeamEvent]`. On `success`, `seam_events` holds exactly one event `{component: "mutates_store", spend: {counted_by: "unbudgetable", zeros}, outcome: "completed"}`; on `not_found`, `not_allowed` or `fail` it is empty (full_delete.py:226-239; engine.py:421-467). That event comes from the node's own self-report after v1 returned `success`, not from a store mutation the machine observed: v1 deleted the document inside `v1/.corpus_working_dir`, and the v2 stores the console queries and resolves evidence from are unchanged, so the deleted document's chunks stay resolvable (v1_corpus_driver_script.py:201-218; engine.py:822). The delete node can call the LLM on v1's partial-rebuild path but declares no `calls_llm` effect, so that spend is never metered (wirings/lightrag/corpus-delete.json; full_delete.py:86-87).

**Refusals.**
- Refusal 422: `UnknownDocumentError {document_id}` when the id fails the pattern, checked before any wiring loads (engine.py:800-803); `UnsatisfiableSelectorError`; `ForeignEngineRefusalError {operation:'delete', cause}` (raised in `_node_result_or_refuse`, engine.py:385-390, reached from 842), including `CorpusOpTimeoutError` after 300 s.
- Validation 422: malformed body, multi-member or hash-shaped selector.
- 500: a graph-store lock collision (stores built before the `try`, engine.py:822).

**Live check.** `DELETE /documents/bad.id` → 422 `UnknownDocumentError`. `DELETE /documents/..x` → 422 `UnknownDocumentError`. `/documents/a/b` and `/documents/a%2Fb` → 404. HippoRAG capability selector → 200 `DeletionOutcome` since HIPP-16 (`wirings/hipporag/corpus-delete.json` exists). Body `{selector:{alias:"hr"}}` with `hr` promoted from HippoRAG → 500.

**What the GUI needs.**
- Screen: row action in the Corpus table and the job panel, plus a standalone "Delete by id" field.
- Controls: confirmation dialog naming `document_id` and the target selector (irreversible); optional selector.
- Display: status badge (`success`; `not_found` informational; `not_allowed` and `fail` as errors), `message`, collapsible seam events. Do not present the seam event as proof that the stores the console queries changed; label it "reported by the v1 delete node". Offer delete only for LightRAG selectors.
- States: in flight (may call the LLM on v1's partial-rebuild path), success, refusal.
- Chained calls: refresh `/corpus` and `/corpus/counts`.

**Gaps.** No bulk delete. v1's `DeletionResult.status_code` and `file_path` are returned by the driver but dropped (v1/lightrag/base.py:996-1003, v1_corpus_driver_script.py:212-218). The driver's `delete_llm_cache` flag (default False, v1_corpus_driver_script.py:203) has no REST field. No undo. No HippoRAG delete. `delete_document` builds stores without the resolved wiring and never calls `index_done_callback` (engine.py:822-835), so a future corpus-delete wiring that writes through `ctx.stores` would hit LightRAG namespaces and lose its buffered kv and graph deletes, while vector deletes persist immediately (vector.py:179-211). v1 driver ops `entities` and `entity_info` (per-document entity contribution, v1_corpus_driver_script.py:221-274) exist but no route reaches them, so no delete-impact preview is possible.

### 3.4 Screen: Corpus & Health

#### 3.4.1 GET /health

**What it does.** Fixed-size liveness check. Probes every namespace in the static list `_HEALTH_PROBES` (engine.py:309-320) read-only in one worker thread, then runs the v1 driver `health` op in a subprocess and records its result (engine.py:1219-1255). No store is constructed and no store file is created (Phase 10 D-14, stores/probes.py): sqlite is opened `mode=ro` (`immutable=1` when no writer is open), the graph is read through the shared in-process Cozo client with an immutable `::relations` query, and the Faiss pair is checked through `load_committed`. The v1 health op still creates `v1/.corpus_working_dir` (v1/lightrag/lightrag.py:1002-1004). It never raises for an unreachable store or engine.

**Request.** None.

**Response.** 200 `HealthReport` (corpus.py:195-209):
- `status: 'ok' | 'degraded'`: `ok` only when every store is `ok` and every engine value is true (engine.py:1248). There is no separate not-initialized state.
- `stores: {"<kind>:<namespace>": 'ok' | 'absent' | 'corrupted' | 'busy'}` (corpus.py:285-307, Phase 10 D-14): ten keys, `kv:text_chunks`, `graph:chunk_entity_relation`, `vector:chunks`, `vector:entities`, `vector:relationships`, `kv:hipporag-text-chunks`, `graph:hipporag-graph`, `vector:hipporag-chunks`, `vector:hipporag-entities`, `vector:hipporag-facts`. `absent` means nothing is on disk yet, so a fresh store root reports every store `absent` and `status: degraded`. `corrupted` covers an unreadable sqlite file, an unreadable graph, and a Faiss pair that is half-written or fails its checksum. `busy` means a `graph.cozo` held by another OS process (or a locked sqlite file); a graph held in this process reports `ok`. Keys use only namespace names already public through `EvidenceRef.namespace`; no path, wiring id or node id.
- `engine: {interpreter_present: bool, working_dir_present: bool, v1_reachable: bool}`, plus `clients: {llm, embedding, rerank}` (presence only, never a URL, model name or key) and `engine_reason: str | null` (fixed text naming configuration keys only, joined by `"; "`) on the response (corpus.py:312-342, 11-09 D-14; Phase 17 correction, D-14, because the console shows the reason and the client flags). `status` is `ok` only when the `llm` and `embedding` clients are wired as well; `rerank` stays optional. `interpreter_present` is a path check (engine.py:947); the other two come from the driver (engine.py:949-953) and are both forced to `false` if the subprocess fails for any reason (engine.py:954-956), even when the directory exists. `storages_initialized` is the literal `True` once `_build_rag` returns (v1_corpus_driver_script.py:323-326), so it carries no information beyond "the subprocess exited 0". On success `working_dir_present` reports whether the directory existed before this probe; on a fresh install the first call reports `false` (and overall `degraded`) and the next call `true`, because v1 creates the directory in its constructor after the check (v1_corpus_driver_script.py:321-323, v1/lightrag/lightrag.py:1004).

**Refusals.** None. The probes catch every store error into the map (stores/probes.py).

**Live check.** Phase 10 (D-14), tests/seam/test_health_probe.py: a fresh store root → 200 `degraded` with all ten stores `absent`, and the store root's file listing is unchanged. A garbage `vector.faiss`, or a lone `vector.faiss`, → `vector:chunks: corrupted`. Populated kv, graph and chunks vector → `ok`, with no `kv.sqlite3-wal`/`-shm` left behind and no new Cozo relation. A `chunk_entity_relation/graph.cozo` held by another process → `graph:chunk_entity_relation: busy`; held in this process → `ok`. Corpus op raising `MissingV1InterpreterError` → 200 `degraded` with `working_dir_present: false`, `storages_initialized: false` and no reason. The `engine` and `clients` blocks are unchanged (LRAG-13/14 own them).

**What the GUI needs.**
- Screen: a status indicator in the console header plus a Health panel.
- Display: overall badge labelled "stores openable / v1 reachable", not "healthy"; a stores table with one row per `<kind>:<namespace>` key and its state and one "v1 engine reachable" indicator for the driver pair plus `interpreter_present`, each with a one-line explanation.
- States: loading (subprocess; up to 60 s), ok, degraded, 500 / network error.
- Polling: manual refresh plus optional slow polling (30-60 s). Do not poll during a running query (graph lock, section 1).

**Gaps.** `engine_reason` gives a short fixed failure reason (Phase 17 correction, D-14; earlier drafts said there is none), but there is still no latency and no workspace / version / modality identification on this route. The client check is presence-only: `clients` says whether a client is wired, not whether it responds. Cannot distinguish "v1 crashed" from "timeout" from the boolean fields alone; `engine_reason` names missing configuration keys and missing clients. The engine half reflects the fixed v1 working directory, not the app's workspace. Does not check the environment digest: if any installed distribution's RECORD contains `/nix/store/`, `environment_hash` raises on every scheduler run (identity/env.py:50-57, scheduler.py:324) while `/health` reports ok (not reproduced on this venv).

#### 3.4.2 GET /corpus

**What it does.** Paged list of documents with status, plus whole-corpus counts and total. Never returns document text, chunks, vectors or graph payloads (corpus.py:143-147). Data comes from the v1 driver `status` op with `track_id=None`, listing every document across all statuses, sorted by `document_id` and sliced by offset/limit (rest.py:359-364, engine.py:881-901, v1_corpus_driver_script.py:289-301).

**Request.** Query `limit: int = 50` (no lower bound; > 100 refused), `offset: int = 0` (`ge=0`) (rest.py:361-362). No filter, sort or search.

**Response.** 200 `CorpusStatus` (corpus.py:170-181): `documents: list[DocumentStatusEntry]`, `counts: dict[str, int]` (from v1 `get_processing_status`; the key set depends on the configured v1 doc-status backend, zero-filled for the JSON backend; v1_corpus_driver_script.py:166, 291; v1/lightrag/kg/json_doc_status_impl.py:148-156), `total: int` (unsliced count, v1_corpus_driver_script.py:300), `next_offset: int | null` (engine.py:895-900).

Validation 422 for `offset < 0`. 500 for v1 subprocess failures (most likely missing v1 configuration keys, section 1), non-JSON driver output, or a `DocumentStatusEntry` validation error (engine.py:894).

**Live check.** `limit=0` and `limit=-1` → 200 with `documents: []` (or, with three stubbed documents and `limit=-1`, two of them) and `next_offset: 0`; `limit=101` → 422 `PageSizeExceededError {requested: 101, limit: 100}`; `offset=-1` → validation 422 `greater_than_equal`; corpus op raising `MissingV1InterpreterError` → 500. Unpatched, from a fresh temporary store root, the route returned the shared repository-wide v1 corpus (total 1 at the time), confirming the value is not per workspace.

**What the GUI needs.**
- Screen: Corpus / Documents table, next to Ingest.
- Controls: page size 1..100 (default 50), prev/next by `offset` / `next_offset`, refresh.
- Display: columns `document_id`, status badge, `updated_at`, `error_message` (inline or expandable on failed rows); header with `total` and the `counts` map as status chips (render whatever keys arrive).
- States: loading (up to 60 s), empty (`total == 0` → link to Ingest), refusal, validation error, 500 (suggest `/health`).
- Polling: optional and slow while any document is in `pending`/`parsing`/`analyzing`/`processing`.

### 3.5 Screen: Ledger

All three ledger routes share the operator preconditions in `_resolve_operator_preconditions`, in this order:
- `alias` must be non-empty and must not match `^(sha256:)?[0-9a-f]{64}$` → `InvalidPromotionAliasError {alias}` (422), first, before any trace or ledger access.
- `change_origin` must be `human_edit` or `machine_mutation`; null or any other value → `InvalidChangeOriginError {change_origin}` (promotion.py:46, engine.py:1129).
- Every trace id must resolve in the trace store → `UnknownTraceReferenceError {trace_reference}` for the first unknown id (engine.py:1132).
- Promote only: a trace whose run was partial (`partial: true` in its record) → `PartialRunEvidenceError {trace_ids}` (422), naming only the partial trace ids; no row is written and no `ledger.db` is created. The rule is keyed on `partial`, never `degraded`: a run that took a declared fallback and completed still promotes. This covers a `clients=None` multi-node query, a failed one-node bypass run, an old-format partial record and a HippoRAG partial record.
- `trace_ids` must be non-empty → `EmptyPromotionTraceIdsError {alias}` (promotion.py:160-161).
- All traces must resolve to the same arm: the record's own `arm_id` when it names a wiring (naive, bypass, hybrid, local, global, hipporag), otherwise the set of dispatched node ids matched against every wiring in `all_wirings()` for a record from before `arm_id` was recorded → otherwise `DisagreeingPromotionTraceIdsError {trace_ids}`.
- Rollback and retire accept a partial trace: its arm comes from `arm_id`, and the ledger row stores its `wiring_instance_hash`. A partial record whose arm cannot be identified (old format, `arm_id` `"seam"`, incomplete node set) → `PartialRunEvidenceError {trace_ids}` (422) on rollback and retire; a non-partial trace that matches no wiring keeps `UnknownTraceReferenceError`.
- No verb answers 500 for a trace or an alias row. An alias whose active row names a wiring that no longer resolves → `UnsatisfiableSelectorError {selector_kind: "alias", requested}` (422) on rollback and retire, naming only the caller's alias. Promote does not refuse there: it treats that prior as having no comparable surface, mints a MAJOR bump and so repairs the alias (14-REVIEW A-WR-02). A promote whose own traces' arm names no wiring still refuses with the same 422.

Trace ids are `trace_token` values from `/query`, `/query/stream` (final event), or each `/compare` envelope. Ingest and delete produce no trace. Because the arm cannot be read from a non-debug trace, the GUI must keep the selector it used for each token, or compare node-id sets via debug traces (section 3.2.2). `trace_ids` is not de-duplicated. `proposer_id` is hard-coded `"operator"` (engine.py:1245, 1372, 1501). The ledger is `<store_root>/ledger.db`, append-only with BEFORE UPDATE/DELETE triggers (databasise/ledger/ledger.py:137-139, 204-280). It is scoped to the store root, not the workspace (section 1). Writes use `BEGIN IMMEDIATE` with SQLite's default 5 s busy timeout (ledger.py:140, 195); a contended write raises an unmapped `sqlite3.OperationalError` (500), so the GUI should serialize ledger actions. Each verb opens its `Ledger` connection on the executor thread and closes it before returning, and `_resolve_alias` closes its own (Phase 14, LEDG-06, D-08). A refused rollback or retire on a store root with no `ledger.db` creates none (`Ledger.open_existing`); only a promote that reaches the append creates the file. `_resolve_alias` opens the ledger read-only (`Ledger.open_existing(read_only=True)`, a `query_only` connection): it never creates the file and never changes its journal mode, schema or indexes, and a file with no `ledger` table refuses like a missing one (14-REVIEW A-WR-01). Its close does not checkpoint the WAL into `ledger.db` where Python's `sqlite3` has `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE`; SQLite's hot-journal recovery after a crashed rollback-journal writer can still write the file (14-REVIEW-ITER2 WR-02). `LedgerRecord` omits the table's `id` and `created_at` columns, but `Ledger.history_for_alias` returns `LedgerEntry` rows that carry both (`ledger.py`, D-09); no route calls it yet (section 5).

No route lists aliases, versions or ledger history (section 5). Until one exists, the GUI keeps every `PromotionResult` it receives in a client-side ledger log.

#### 3.5.1 POST /promote

**What it does.** Appends one `promotion` row that points `alias` at the arm the supplied traces ran. The caller does not name the arm, mutation class or version. The engine derives the arm from the traces, the mutation class by diffing against the alias's active generation, and mints the version: `1.0.0` first, then MAJOR if the declared effects/provides surface changed, otherwise MINOR; PATCH is never minted (rest.py:370-372, engine.py:1146-1272, promotion.py:182-201). An unknown alias string is created by its first promote.

**Request.** `PromoteRequest` (rest.py:146-162):
- `alias`: str, required. An empty alias or one matching `^(sha256:)?[0-9a-f]{64}$` is refused (`InvalidPromotionAliasError`, 422) because no selector could name it.
- `trace_ids`: list[str], required. Traces from a HippoRAG run are accepted and the row is written; the alias then resolves on every selector route. A trace from a partial run is refused (section 3.5 preconditions).
- `change_origin`: str \| null, default null (refused when null).
- `verb`: str, default `operator-asserted`. Six literals (promotion.py:56-64): `operator-asserted` (the only one that writes a row), `check` / `preview` / `run` (refuse, not built), `promote-next` / `promote-now` (always refused, no gate is calibrated). A JSON `null` or a number for `verb` returns a validation 422 (`string_type`), not `UnrecognisedPromotionVerbError` as the docstrings at rest.py:152-157 and refusals.py:365-370 state; only a non-member string gives the named refusal.

**Response.** 200 `PromotionResult` with `record_kind: "promotion"` and the newly minted `version`.

**Refusals.** In evaluation order, all 422 unless noted: `UnrecognisedPromotionVerbError {verb}`; `GateVerbNotBuiltError {verb}` for `check`, `preview` and `run`; `GateNotCalibratedError {verb}` for `promote-next` and `promote-now` when `<store_root>/floors.db` is absent or holds no row, the same for every arm; `InvalidPromotionAliasError {alias}`; `InvalidChangeOriginError`; `UnknownTraceReferenceError` (404); `PartialRunEvidenceError {trace_ids}`; `EmptyPromotionTraceIdsError`; `DisagreeingPromotionTraceIdsError`; `UnsatisfiableSelectorError {selector_kind, requested}` when the traces' arm names a wiring that no longer resolves (an alias whose active row names one is repaired, not refused, section 3.5). The gate lifts in two stages. Stage 1 runs first, for a first promotion and for every re-promotion, before alias validation, trace resolution and any ledger access: with no `floors.db` under the store root, or one with no rows, the gate verbs are `GateNotCalibratedError`, so a refused gate verb creates no `ledger.db` on a fresh store root. Stage 2 runs after the checks above, only once a floor exists: the alias's prior row is read read-only, the mutation class is derived, and every instance hash the traces carry needs a persisted floor whose identity matches the engine's (newest committed eval bundle, the tier and metric of the class, `cache-bypassed`, `sequential`). A missing or stale floor is `GateNotCalibratedError` again; with a valid floor a retrieval-side change is `GateVerbNotBuiltError` (the comparison runner does not exist) and an answer-level or index-side change is `MeasurementPostureRefusalError`. Nothing is appended in either stage. `eval.aa_run --spend` is the only writer of `floors.db` (section 7), and an engine reads only the floors under its own store root, so only an engine started on the eval store root sees them. Validation 422 for body-shape errors. 502: `ForeignEngineRefusalError {operation: "promote", failure_class: "StoreFault"}` when `floors.db` cannot be read in stage 1 or stage 2; a fault is never read as no floor. 500: `sqlite3.OperationalError` under ledger write contention. Re-promoting the arm the alias already points to is not refused; it mints a MINOR bump.

**Live check.** `{alias: ""}` or `{alias: "sha256:" + 64 hex}` with a valid trace → 422 `InvalidPromotionAliasError`. A HippoRAG trace → 200 version 1.0.0, and the alias then resolves on `/query`, `/compare` and the document routes. A trace from a `clients=None` partial run or a failed bypass run → 422 `PartialRunEvidenceError` naming that trace id. `verb: "promote-next"` or `"promote-now"` → 422 `GateNotCalibratedError`. `verb: null` or `5` → validation 422 `string_type`; `verb: "zzz"` → 422 `UnrecognisedPromotionVerbError`.

**What the GUI needs.**
- Screen: Ledger / Promotion panel, also reached from a Query or Compare result ("promote from this result").
- Controls: alias text field with autocomplete from the client-side ledger log; trace multi-select from the client-side query history, grouped by the selector that produced each token; `change_origin` radio with exactly two options and none preselected; `verb` fixed to `operator-asserted` (other five hidden or shown disabled with "not built / gated").
- Pre-flight: non-empty trace list, `change_origin` chosen, exclude traces with `partial: true` (the server also refuses them), optional same-arm check via debug traces, warn when selected traces came from different selectors, reject an empty alias and an alias matching `^(sha256:)?[0-9a-f]{64}$` (the server also refuses them).
- Confirm dialog: "repoints the alias; append-only; undo only by a later rollback".
- Display: success card with alias, version badge, `record_kind`, `provenance`, `generation_ordinal`; append to the client-side ledger log.

**Gaps.** No alias, version or history listing. No dry-run returning the derived arm, mutation class or version. The response omits the arm and mutation class. No operator identity field. `arm_instance_hashes` stores per-run hashes that include the query text (engine.py:1137-1143, 976), not per-wiring hashes.

#### 3.5.2 POST /rollback

**What it does.** Appends one `rollback` row that points `alias` back at the wiring of a named earlier generation. A new version is minted for the rollback generation; the requested version is recorded as `targets_version` (engine.py:1274-1399). The mint compares the target wiring's declared surface with the current active wiring's surface: MAJOR when they differ, MINOR otherwise (engine.py:1353-1362, promotion.py:195-201). Versions per alias increase monotonically and always end in `.0`.

**Request.** `RollbackRequest` (rest.py:165-172):
- `alias`: str, required; must have ledger rows.
- `version`: str, required, no default and no "previous" shortcut. Looked up with `Ledger.generation_state`: latest row where `alias = ? AND (minted_version = ? OR targets_version = ?)` (ledger.py:362-376).
- `trace_ids`: list[str], required (same rules). Partial-run traces are accepted when their `arm_id` identifies the arm; a partial record that cannot be identified is refused (section 3.5). The derived arm name is discarded and not required to match the target; only the traces' `wiring_instance_hash` values are stored in `arm_instance_hashes`, while `mutation_id` and `parent` name the target, so a rollback row can carry hashes from a different arm than its `mutation_id`. A rollback or retire row citing a partial or failed run's trace is evidence from that run; the console should label it (Phase 14, D-01).
- `change_origin`: str \| null.

No `verb` field.

**Response.** 200 `PromotionResult` with `record_kind: "rollback"` and `version` = the newly minted version, not the requested target (engine.py:1393-1399). The response does not echo the target.

**Refusals.** The shared preconditions; `UnknownGenerationVersionError {alias, version}` (engine.py:1339; includes a version minted under a different alias); `TombstonedGenerationError {alias, version}` (engine.py:1341), also raised when any version in the target's rollback lineage (`Ledger.lineage`) is tombstoned, so the alias never ends up serving a retired generation (Phase 14, D-06). A ledger row naming a wiring that no longer resolves → `UnsatisfiableSelectorError` (422), never a server error or an assertion failure. `PartialRunEvidenceError {trace_ids}` when a partial record cannot be identified by `arm_id`. Rolling back to the already-active version is not refused and always mints a MINOR bump. A refused rollback creates no `ledger.db` on a fresh store root, including `UnknownGenerationVersionError` (D-08).

**Live check.** After promote naive 1.0.0, promote hybrid 2.0.0: rollback to 1.0.0 → 200 version 3.0.0, `record_kind: "rollback"`. `version: "banana"` → 422 `UnknownGenerationVersionError` (non-semver strings are not rejected earlier). Rollback with a trace from a different arm than the target → 200 (minted 3.1.0 in that run).

**What the GUI needs.**
- Screen: Ledger / alias timeline, "Roll back to" action on each non-tombstoned, non-active row.
- Controls: alias and version prefilled from the row; trace multi-select; `change_origin` radio.
- Confirm dialog naming the current active version and the target, and stating that a new version will be minted.
- Display: new version badge, `record_kind`, `generation_ordinal`; the GUI records "targets <version>" itself.
- States: as `/promote`; render `UnknownGenerationVersionError` / `TombstonedGenerationError` against the version field.
- Chained calls: `/query` with `{alias}` to confirm (every wiring resolves, HippoRAG included).

**Gaps.** No source for the version picker (no generation listing). No dry-run. No warning for rolling back to the active version.

#### 3.5.3 POST /retire

**What it does.** Appends one `tombstone` row, making one `(alias, version)` generation permanently ineligible as a rollback target. Nothing un-retires it. The generation the alias currently points to cannot be retired (engine.py:1401-1528).

**Request.** `RetireRequest` (rest.py:175-182): `alias: str`, `version: str` (required), `trace_ids: list[str]` (recorded, deliberately not matched to the retired generation, engine.py:1411-1419), `change_origin: str | null`.

**Response.** 200 `PromotionResult` with `record_kind: "tombstone"` and `version` = the retired version (a tombstone mints nothing, engine.py:1512, 1522-1528).

**Refusals.** The shared preconditions; `UnknownGenerationVersionError` (engine.py:1479); `TombstonedGenerationError` (already retired, engine.py:1481); `ActiveGenerationRetirementError {alias, version}` when `version` is any version in the active generation's lineage, found with `Ledger.lineage` from the active row's `minted_version` (Phase 14, D-06): after a rollback that minted W while targeting V, retiring V or W is refused, so the alias never keeps serving a generation just retired. Partial-run traces are accepted by `arm_id` as on rollback; an unidentifiable partial record → `PartialRunEvidenceError`. A ledger row naming a wiring that no longer resolves → `UnsatisfiableSelectorError` (422), never a server error. A refused retire creates no `ledger.db` on a fresh store root.

**Live check.** promote prod naive → 1.0.0; promote prod hybrid → 2.0.0; rollback prod to 1.0.0 → 3.0.0; `Ledger.by_alias("prod")` returns the rollback row (minted 3.0.0, `mutation_id: naive`, `targets_version: 1.0.0`) and `/query` with `{alias: "prod"}` → 200 running naive. ## 4. MCP tools

The GUI uses REST. The MCP server (databasise/mcp/server.py) shares one `Databasise` instance (server.py:194) and registers ten tools (server.py:198-324; names pinned in `TOOL_NAMES`, databasise/mcp/tools.py:79-90). Each tool function takes one Pydantic parameter named `args`, so the MCP input is nested as `{"args": {...}}`; the arg models are frozen with `extra="forbid"` (`_ToolArgs`, tools.py:96-101). Every tool publishes a non-empty description with no plan references (`compare`'s carries `COMPARE_RESPONSE_SHAPE_RULE`); every `output_schema` is a generic object. A refusal is mapped in one place, `_DatabasiseServer.call_tool` (server.py:120-128): it finds the first `SeamRefusalError` on the exception's cause chain (a pydantic `ValidationError` is unwrapped through `refusal_from_errors`, so a refusal raised by a model validator is found) and re-raises it as `RefusalToolError`, whose text, in-process and on the wire (`is_error: true`), is the bare JSON `{refusal_type, message, ...attrs}` that REST returns, with no SDK prefix. An argument-schema failure that carries no refusal (an extra field, a missing `args`) keeps the SDK's plain text `"Error executing tool <name>: <pydantic message>"`, and any other exception inside a tool body surfaces as `UnexpectedToolError` with the fixed text `"Error executing tool <name>"` and no detail; the server logs the traceback. The launcher is `databasise-mcp` (`databasise/launcher/serve_mcp.py`, pyproject `[project.scripts]`), with `--transport stdio|sse|streamable-http` (default `stdio`; section 7).

| MCP tool | REST route(s) | Differences from REST |

Priority meanings:
- **needed-for-mockup**: the mockup must design for it now; the decision or a workaround must exist before the mockup is drawn.
- **needed-for-v1-console**: required before the connected console is usable; the mockup uses fixtures or client-side state in the meantime.
- **later**: not required for the first connected console.

Constraints that apply to every new route:
- **Thin adapter (D-17).** Every route body is deserialize, await one `Databasise` method, return; a test walks the module's AST (rest.py:26-36, tests/seam/test_rest_transport.py:182-201). A new route needs a new engine method first and, by the rest.py docstring convention (rest.py:26-36), should not read the ledger, trace store, registry or stores in rest.py; the call ban on `ResponseEnvelope`, `resolve_selector` and redact's exports (test_rest_transport.py:182-200) now runs over both rest.py and `seam/operator_rest.py`. `tests/seam/test_console_surface.py` also checks that every route body in `operator_rest.py` is exactly one `return await engine.<method>(...)` and bans direct ledger, trace-store, registry and store reads there, with a Ledger mutant that the rule must flag (Phase 16, D-04).
- **MCP parity and §18.5.** The MCP tool set holds ten names (`TOOL_NAMES`, tools.py:79-90, tests/mcp/test_tool_growth_invariant.py). A new engine operation either adds an MCP tool with a §18.5 justification (docs/system-model/CONTRACT.md:802-810) and a COVERAGE.md row (a requirement of the test, not of CONTRACT), or is recorded REST-only in COVERAGE.md's "Operations deliberately absent" table. The ten Phase 16 operator operations are recorded that way (D-03), and `test_console_surface.py` asserts a `REST-ONLY` row for each and `len(TOOL_NAMES) == 10`. The COVERAGE.md table tests read the live `databasise/evidence/COVERAGE.md` (RUN-01, D-13), so the earlier `FileNotFoundError` from the archived path no longer occurs. Under `python -m pytest`, the falsifier-4 native-leg test is skipped with a misleading "mcp extra is not installed" reason, because `databasise/mcp/` shadows the SDK (foreign/_mcp_sdk_guard.py:78-90), and the live embedder parity test (tests/parity/test_embedder_index_reproduction.py:36, threshold 0.999) passes or fails between runs with no code change.
- **Test coverage of existing routes.** `POST /compare` is exercised over REST only by tests/mcp/test_dual_transport_parity.py:411 (two-selector success); the one-selector shape and every compare refusal are untested over REST. No test sends a refusing request to the real `/rollback` or `/retire` routes, and the `/evidence/resolve` and `/trace/resolve` refusals are tested over REST only through the synthetic `/_test/raise` route (test_rest_transport.py:479-533), which never goes through body parsing. The `/jobs` page-cap refusal is tested only over MCP (test_dual_transport_parity.py:258-264). No test covers the oversized upload 500, the bad `document_id` 500, a HippoRAG ingest job poll, or HippoRAG PPR-branch evidence. The upload filename test (test_rest_corpus_endpoints.py:345-356) asserts on `job_id`, not on the inbox file, and the round-trip tests never check counts after delete (441-442, 480-481). A new route needs its own refusal-path tests.
- **No privileged client.** CONTRACT §18.3 says no client is privileged over another (CONTRACT.md:777-779), so an "operator-only" route on the §18 app is not an existing contract category. The precedent for showing internal identities is the explicit `debug` flag on `/trace/resolve` (engine.py:1096-1109).
- **Selector input.** Building a `Selector` from flat query parameters in a route body turns a validator error into an unmapped 500 (refusals.py:20). Take the selector in a JSON body (as every existing selector-bearing route does), or catch `ValidationError` and raise `MalformedSelectorPayloadError` as the upload route does (rest.py:333-336).
- **Paging.** Reuse `_checked_page` and `MAX_PAGE_SIZE`, declare `limit` with `ge=1`, and return `next_offset` (plus `total` where cheap), matching `CorpusStatus`.
- **Namespaces are not selectors.** CONTRACT §18.4 (CONTRACT.md:789) forbids naming a wiring, node id or instance hash; the rule that a browse route takes a selector rather than a namespace is an inference from the §18.3 invariance rule (CONTRACT.md:783-785), not §18.4 text.
- **Ledger reads.** `Ledger()` construction runs no-op DDL and a commit (ledger.py:143, 204-279) but, measured on an existing WAL ledger, does not block on a concurrent `BEGIN IMMEDIATE` (0.0 s), so read-only ledger routes are feasible over `Ledger()` as it is; the transaction() docstring that says construction stalls for the busy timeout (ledger.py:184-187) is wrong. Add a `close()` to avoid one leaked connection per call.
- **Store selection.** Browse methods must call `_build_stores(store_root, workspace, resolved)` with the resolved wiring; with no wiring they fall back to LightRAG's default namespaces (engine.py:319-347), which silently browses LightRAG for a HippoRAG selector.

## 6. Open questions for the owner

1. **Where do the operator read routes live?** Options: (a) on the §18 app, gated by an explicit flag like the existing `debug` on `/trace/resolve`; (b) a separate operator app (for example `create_operator_app`) on its own local port. Option (b) conflicts with §18.3 "no privileged client" (CONTRACT.md:777-779). It does not need a change to `create_app`: a launcher can mount extra routers on the returned app using `app.state.engine` (rest.py:249). A second `Databasise` on the same store root adds no new graph-lock contention (stores are opened per call), but adds a second trace-store connection and registry, so reusing `app.state.engine` is simpler. Either way: do these operations get MCP tools and COVERAGE.md rows (§18.5), or stay REST-only?
2. **Alias enumeration.** Listing aliases conflicts with the project's no-enumeration decision D-12/FA-06 (selectors.py:259-263), not with CONTRACT §18.2. Keep the rule and have the GUI keep a client-side ledger log, or relax it for an operator listing?
3. **Trace listing.** A `GET /traces` route removes the bearer-token property of trace references on an unauthenticated app, and so does the proposed `POST /ledger/history`, which would return `promotion_trace_ids` (engine.py:1252, 1379, 1508). Accept that for a localhost-bound console, or keep traces client-side only? Note that `trace.db` is shared by every workspace on a store root (trace_store.py:71).
4. **CORS and serving.** Serve the GUI build from the same FastAPI app (no CORS), use a Vite proxy in development, or add a configurable `allow_origins`?
5. **Auth.** Keep no auth with localhost binding (rest.py:38-46), or put a reverse proxy with auth in front if the console is ever reachable beyond localhost?
6. **Graph payloads.** Returning node and edge `attrs` breaks the API-06 rule that read models carry no graph node payload (corpus.py:15-23). Override API-06 for a browse surface, or return references only and resolve attributes through a separate dereference call? API-06 covers the corpus-introspection models (corpus.py:15-23); `/evidence/resolve` already returns stored metadata for any vector namespace (vector.py:327-338), so a dereference call of that kind already exists.
7. **Modality name in `EvidenceRef.namespace`.** `hipporag-chunks` exposes a modality name to consumers (§18.3, CONTRACT.md:785). Fixing it means `/evidence/resolve` must take a selector and the on-disk directory needs a store migration (namespaces.py:15-17). Fix now, or accept and record?
8. **LightRAG data freshness.** LightRAG ingest and delete do not update the v2 stores that LightRAG queries, evidence and browsing read (engine.py:744-749; parts_core/lightrag/chunk_vector.py:21; full_delete.py:226-232); only a parity import does, and the importer CLI reads only `v1/.parity_working_dir` into the parity workspace (parity/import_index.py:84-85, 498-511). So a document ingested through `/documents` is invisible to `/query`, and a deleted one stays queryable. Options: label LightRAG data as "last import"; add a re-import action that calls `import_v1_index(v1/.corpus_working_dir, store_root, workspace)` (the function already takes these parameters, import_index.py:231-235); or change LightRAG ingest and delete to write the v2 stores.
9. **Fix order.** (The HippoRAG-alias 500, the partial-trace promote 500 and the retire-after-rollback guard were fixed in Phase 14.) Fix the upload and `document_id` 500s, the namespace path validation, the LightRAG upload, and the HippoRAG `chunk:` id mismatch before the connect step, or connect first with client-side guards?
10. **Unreachable arms.** Resolved by Phase 13 D-01 (WIRE-01): a part declares `reads_namespaces` tokens, so `reads_vector:entities`, `reads_vector:relationships` and both together select local, global and hybrid, and every arm is comparable (section 3.0). The tie-break is still node count.

Add a generator node so `answer` means the same for every modality (§18.3), or label the field per modality in the GUI (which §18.2 says a consumer cannot know)?

Resolved in Phase 14 (D-10, G-35): one store_root is one tenant.

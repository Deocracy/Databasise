### §RUN.1 — Namespace derivation and the shared KV

The per-part graph and vector namespace derivation rule is stated as a rule the rig applies, not a storage-keying design it invents: a namespace is derived from the artifact-registry vocabulary `§7` already froze — namespace, sub-recipe stamps (SA-2), corpus, `space_id`, producing instance — plus the arm's own SA-1 recipe identity from `§1`'s `(name@version, config_hash, resolved_dependency_ids)` tuple. [docs-verified] [CONTRACT §7] [CONTRACT §1]

The KV is shared across arms where, and only where, `§3`'s `shared` scope admits it — under `§3`'s blast-radius rule that means effective depth `stage`, computed as the minimum over transitive `deps`. [docs-verified] [CONTRACT §3]

An arm containing an `opaque` node writes `quarantined` and never `shared`, per `§3`'s own scope table and the same rule `§8` restates for opaque-node admission; its index is therefore instance-scoped and readable only by explicit pin from another wiring, never SA-1-shareable. [code-verified] [CONTRACT §3] [CONTRACT §8]

The consequence is named plainly rather than buried: two arms whose index sides are each opaque cannot share an index regardless of how similar their recipes read in prose, so each pays its own build — the cost `SELECTION.md`'s AMENDMENT accepts as the quarantined-scope trade-off, and `## §CM` prices in tokens once it lands. [inference] [CONTEXT D-12] [05-RESEARCH]

### §RUN.2 — The artifact-overlap decision

The decision procedure is an **iff** on index-recipe hashes, not a heuristic similarity judgment: two arms overlap on an artifact if and only if their `recipe` fields — `§1`'s named source for SA-1 recipe identity — are hash-identical under `§1`'s canonicalised `config_hash` computation. [docs-verified] [CONTRACT §1]

All three cases are stated explicitly, because a reader must not have to infer any of them. [inference] [new-synthesis]

- **Hash-identical recipes.** The arms share the artifact: the rig performs one index build, not two, and the shared artifact's registry row (`§7`'s artifact registry) is the same row read by both arms — identical means shared, never a collision, and never two coincidentally-equal copies each separately built and separately registered. [docs-verified] [CONTRACT §1] [CONTRACT §7]
- **Recipes differing in any resolved input.** No overlap on that artifact; each arm builds its own. `§6`'s reindex planner four-way classification (`reuse` / `re-embed` / `re-extract` / `rebuild`) is the mechanism that prices the difference once an artifact already exists under a prior recipe version — this clause names the classifier, not its cost; the costing function belongs to `## §CM` and `## §EV`, not here. [docs-verified] [CONTRACT §6]
- **The worked pair (D-11).** `VT-1`'s `chunk → embed → upsert` index recipe and `GR-1`'s LightRAG ingest core are structurally different recipes sharing no resolved input at all, so the rig runs them with **zero** artifact overlap and two full index costs — the concrete instance of the rule above, not a hypothetical. This is exactly the asymmetry `## §F3` is later asked to price: `VT-1` pays no LLM extraction at index time whatsoever, while `GR-1` pays a full extraction pass over the same corpus. [inference] [CONTEXT D-11] [CATALOG §T]

### §RUN.3 — Fan-out semantics

The fan-out maps onto `§2`'s `fanout` structural kind: arity is either static or taken from an upstream node's output socket, and N arms fan out from one comparison request under exactly that socket kind, with no new structural kind invented for the rig's own use. [docs-verified] [CONTRACT §2]

Budget accounting under the fan-out is multiplicative by construction, per `§9`'s fan-out rule: an N-way fan-out's total spend is the sum of N independently-budgeted branches, never a shared pool one branch could overrun into a sibling's allocation. [docs-verified] [CONTRACT §9]

Each arm's realised branch share is stamped on the run record per `§9`'s merge-side apportionment repair (D4) — the same `realised_budget_share` field `## §TR.1` already publishes, the instrument `§5`'s eleventh refusal condition reads. [docs-verified] [CONTRACT §9] [PARTS-01 D4]

The degenerate widths are stated explicitly, so no width is undefined. [inference] [new-synthesis]

- **Zero arms.** A comparison request naming no arms is a refusal, not an empty success. None of `§5`'s eleven refusal conditions is phrased over an empty arm set — every one of the eleven speaks of "arms under comparison" already populated — so this is not that gate's refusal to return. It is instead a request-validation refusal at the seam, extending `§18.1`'s own "refusal, never silent drop" rule (there stated for a query object member no fitted modality can consume) to the equivalent case of a comparison request naming no member the rig can compare at all: the request is refused, naming the empty `arms` field as the unconsumable member, before any run is attempted. No `## §R` row is added for this reading — it assembles `§18.1`'s existing pattern by inference rather than exposing a gap that pattern does not already cover. [inference] [CONTRACT §18.1]
- **Exactly one arm.** A one-arm fan-out is a valid *run* and never a valid *comparison*: `§5`'s policy computes a paired statistic across the arms under comparison, and one arm has no pair to compute one against. The gate returns none of its eight verdicts in this case — a verdict presupposes a comparison, and there is none — and the rig instead returns exactly what the `run` verb of `§5`'s own five-verb ladder already returns for any single arm: a trace (`## §TR`) and a score, with no gate verdict attached. [docs-verified] [CONTRACT §5]
- **N arms against one shared baseline.** This is D-08's batch shape, which `## §F3` prices and `## §AA` corrects the promotion floor for. Named here as the rig's normative operating mode: N+1 arm-runs (N candidates plus the one shared baseline), never 2N pairwise runs, applying `§9`'s multiplicative fan-out accounting once across the whole batch rather than once per pair. The batch's own two hazards — the multiple-comparisons correction to the A/A floor, and the non-additive-winners rule — are forward-fenced to `## §AA`, not resolved here. [docs-verified] [CONTEXT D-08] [CONTRACT §9]

The process model, the scheduler and the storage-keying scheme are **not** designed in this section, in `PARTS.md ## §P`'s own "named here, not designed here" wording. `N11` — intra-node concurrency's home in `§9`'s budget shape — remains open at this section's close and is **Phase 6's**, per `CATALOG.md ## §R`'s own row naming it so; descending to a runner here would force `N11` closed on thin evidence, which this section refuses to do. [inference] [CONTEXT D-12] [PARTS §R] [CATALOG §R]

### §RUN.4 — Side-by-side comparison, ordering, and failure handling

What the rig produces when the arms return is a per-arm output set aligned on the eval bundle's own question order (`## §EV`'s own instrument, forward-cited here), so the same question's outputs from every arm sit beside each other rather than in whatever order each arm happened to finish. [inference] [CONTRACT §10]

Where two arms compare equal on the metric under inspection, the tie-break is stated and deterministic rather than left to run order: ascending `arm_id` — a simple, stable ordering that is sufficient because it needs only to be *reproducible*, not meaningful in its own right. [inference] [new-synthesis]

The `arm_execution_order` stamp `§5`'s D7 repair already requires on the run record (`## §TR.1`'s own field) is what makes a run-order-dependent result diagnosable from the trace alone, rather than merely suspected: a reader comparing two runs of the same arm set sees whether execution order differed and can attribute a divergent result to that fact instead of guessing. [docs-verified] [CONTRACT §5] [PARTS-04 D7]

Failure and partial-result handling at the *comparison* level is stated here, distinct from the run level `## §LC` owns: an arm that fails records its `cross_process_failure_cause` per `## §TR.1` and `§3`'s placement-and-cause requirement, and the comparison proceeds with the surviving arms only where doing so does not itself trigger one of `§5`'s eleven refusal conditions checked against whatever arms remain — a mismatched determinism or concurrency setting, differing resolved artifact ids, or any of the other conditions on the list, evaluated over the survivors, never over the failed arm. Where a failed arm's removal leaves fewer than two arms, the comparison reduces to `## §RUN.3`'s own zero- or one-arm case above, and that case's stated outcome governs rather than a new rule minted here. [inference] [CONTRACT §5] [CONTRACT §3]

Comparison as **inspection** is always available even where adjudication is not: reading two arms' traces side by side costs nothing beyond the runs themselves and is unaffected by `## §F3`'s default posture, per **D-05**'s own enumerated survivor list ("the entire parallel-run model... comparison as inspection is free — only adjudication costs"). [docs-verified] [CONTEXT D-05]

This is stated as satisfied in this one tagged clause; no `## §R` row is added, since satisfying a scope fence is not a defect. [docs-verified] [CATALOG §C.4] [CONTRACT §8]

Three load-bearing reasons for the split, none of them cosmetic. [inference] [CONTEXT D-14]

1. It is what makes the three token moments `## §CM` will state (index extraction / query generation / eval judging) separable in the trace record, rather than one number a reader must guess the composition of. [inference] [CONTEXT D-14]
2. It is what lets `## §CM`'s cost model be checked against reality once a build exists — a model stated once and never reconciled against a measured trace is exactly the kind of unverified claim `PROJECT.md`'s evidence standard forbids. [inference] [CONTEXT D-14]
3. It is the only way `§14.3`'s `prompt_cache` capability flag can prove itself: a cached read prices differently from a fresh call, and a single aggregated token count could not distinguish the two even in principle. [docs-verified] [CONTRACT §14.3] [CONTEXT D-14]

### §CM.1 — The three token moments

A reader who has not read the red-team pass needs one plain map before any table: a run spends tokens at exactly three moments, never more. [inference] [new-synthesis]

n = [z_(1-α/2)·√(p01+p10) + z_(1-β)·√(p01+p10-(p01-p10)²)]² / (p10-p01)²

### §AA.1 — The procedure, per `(bundle@v, tier, metric)`

`§5` already freezes the rule this sub-section specifies against, assembled rather than restated: **the gate MUST calibrate a per-`(bundle@v, tier, metric)` A/A null and set its promotion floor at that null's p95, never at a policy constant.** [docs-verified] [CONTRACT §5] **The scheduler's concurrency setting is a gate-admission condition and keys the A/A null the promotion gate calibrates against; two runs under different concurrency settings MUST NOT be pooled under the same A/A null.** [docs-verified] [CONTRACT §4] What `§5` deliberately left blank — how many replicates a calibration needs, what invalidates a calibrated null, and which way a boundary delta resolves — is this sub-section's own job to specify. [inference] [new-synthesis]

**The triple's scope.** One A/A null exists per `(bundle@v, tier, metric)` triple, and per `§4`'s pooling-key rule that triple is inseparable from the run's own declared concurrency and determinism setting: a null calibrated under a sequential setting and a null calibrated under a concurrent setting are two different nulls, never one null read under two labels. The practical consequence, stated so a builder does not have to infer it: the concurrency/determinism setting is part of the null's own identity, exactly as `(bundle@v, tier, metric)` already is, and a comparison run under a differing setting from the one its candidate floor was calibrated under cannot borrow that floor — it either calibrates its own, or the comparison is refused below. [inference] [CONTRACT §4]

**What invalidates a null.** Four events, each named because a builder must not have to discover any of them by trial: a `bundle@v` change, per `## §EV.1`'s own versioning rule — a new bundle version invalidates every null calibrated under the old triple; a tier change; a metric change; and a concurrency or determinism setting change, per the triple's scope stated just above. **The staleness link to `§5`'s own refusal list is direct, not analogical**: `§5`'s **fourth** refusal condition is "a stale A/A null for the artifact set under comparison," and every one of the four invalidating events above is exactly what makes a null stale under that condition's own wording — an invalidated null does not silently keep serving as a floor; it produces a refusal under the fourth condition, the same refusal every other stale-evidence case in this document already resolves to. [docs-verified] [CONTRACT §5]

**The replicate design, with the naive answer named and rejected.** A crude empirical p95 estimated directly from N raw full-arm-run replicates needs a fairly large N for a stable quantile read — the standard error of an empirical quantile scales as `√(p(1-p)/(N·f(q)²))`, where `f` is the density at the quantile — practically, dozens to 100+ replicate arm-runs for a tight p95 estimated this way. [inference] [05-RESEARCH] Each such replicate is not a cheap unit: it is a **full arm-run**, priced at whichever of `## §CM.2`'s own per-class anchors the calibration's own class is measured against — from the retrieval-side class's estimated 1-5% of the full bill up through the answer-level class's ~5.1-5.2M tokens per adjudicated decision, cited from `## §CM.2` rather than restated as a new figure here. Dozens of full arm-runs priced at the answer-level anchor alone would spend several times a single decision's own ~5.1-5.2M-token bill before a single real comparison has even run — this is why the naive approach is not this document's recommended default: not because it is wrong, but because it is needlessly expensive against a cheaper design that reuses machinery `§5` already specifies. [inference] [05-RESEARCH]

**Specified instead:** one A/A run at n questions produces n *paired per-question* differences between the two runs of the same arm under one fixed `(bundle@v, tier, metric)` triple and one fixed concurrency/determinism setting — the arm is run against itself, twice, and each of the n questions yields one paired difference. Bootstrap-resample those n paired differences — with replacement, the ordinary nonparametric bootstrap — to build the null distribution, and take that resampled distribution's p95 as the calibrated floor. **This reuses the paired-bootstrap machinery `§5` already specifies for continuous-metric gating** — "paired bootstrap for a continuous one," `§5`'s own policy clause — applied to the null itself rather than to a real comparison: no new statistical apparatus is minted, and the same instrument that gates a real promotion decision is the instrument that calibrates the floor that decision is later gated against. [docs-verified] [CONTRACT §5] [inference] [05-RESEARCH]

**When the naive full-replicate approach is nonetheless warranted, stated so the cheaper default reads as a reasoned choice rather than a shortcut.** At the retrieval-side class, whose own `### §F3.1` disposition prices a full arm-run at an estimated 1-5% of the full per-decision bill, running several dozen full replicates alongside the bootstrap read — as a cross-check on the resampled null's own p95 — costs little against that class's own budget, and a class this cheap can afford the belt as well as the suspenders. At the answer-level and index-side classes, where `### §F3.1` already prices a single decision or a single recipe-version mutation in the millions of tokens, the naive approach is never warranted inside this document's own default posture: the bootstrap read is not merely cheaper there, it is the only affordable one. [inference] [new-synthesis]

**The floor comparison at the boundary.** A measured delta landing **exactly** on the calibrated p95 floor does **not** promote. The floor is a one-tailed critical value at the null's own 95th percentile, and the conventional resolution of a one-tailed test at that boundary is that the observed statistic must **exceed** the critical value, not merely reach it — a delta sitting exactly at the p95 mark is itself a value the null distribution already produces 5% of the time by chance, and treating it as sufficient to promote would be treating the null's own upper tail as if it already lay outside the null. A delta strictly above the floor promotes, subject to every other condition `§5` already states; a delta at or below the floor does not. This is the one genuine boundary this document's own flagged-assumption reading names as RIG-06's edge surface, resolved here in one unambiguous clause rather than left for a builder to guess. [inference] [new-synthesis]

**Where the null lives and who reads it.** `BOARD` (`ANATOMY.md` entry 23) holds the pooled run rows under `§4`'s own pooling key; `GATE` (entry 24) calibrates the per-`(bundle@v, tier, metric)` null from those pooled rows and sets the promotion floor at its p95. Per `§11`'s own control-channel-is-a-read rule, the scoreboard is read at load and never queried mid-run — a running arm cannot see or react to the calibrated floor its own comparison will later be judged against. This sub-section cites the two `ANATOMY.md` boxes that already carry this responsibility rather than redrawing either box. [docs-verified] [CONTRACT §11] [ANATOMY §D entry 23] [ANATOMY §D entry 24]

### §AA.2 — The cache-bypass precondition and where variance actually comes from

**Cache bypass as a hard precondition.** A genuine A/A calibration run **MUST** bypass the response cache — per `§5`'s own D7 repair, which already states that a determinism re-run MUST be performed with the node's cache bypassed, and that a cache-served re-run MUST NOT support a `T3` stamp. [docs-verified] [CONTRACT §5] The mechanism and the consequence sit in the same clause because a reader must not be able to separate them: a cache-served re-run returns the stored response byte-identically and short-circuits the underlying call entirely, so a cache-hit-heavy calibration run measures a **near-zero** variance — not merely a small one, since a cached response cannot differ from itself — and a promotion floor derived from that near-zero null is **too permissive**: real noise, on a genuine cache-bypassed run, would exceed a floor calibrated this thin, and the gate would promote it as if it were signal. This is stated plainly as a **correctness risk specific to calibration, not a cost-efficiency concern** — the failure mode is a floor that *looks* fine (tight, well-behaved, cheap to have calibrated) and is not. [docs-verified] [CONTRACT §5] [inference] [05-RESEARCH]

**Made checkable, not merely stated.** A calibration run's cache-bypass status is recorded alongside the null it produces — `## §TR.1`'s own `cache_hit` field, per node, is the trace evidence this claim already has a home for. **A null whose bypass status is unknown is not usable as a floor**: the gate refuses to calibrate against it, exactly as it refuses any other input it cannot verify, rather than trusting an unstamped null on the assumption it was probably run correctly. [docs-verified] [inference] [new-synthesis]

**One fact grounds both rules, not two.** The connection to `§5`'s existing rule that a cache-served re-run cannot support a `T3` stamp is not incidental — it is the same underlying fact (a cache-served call returns a stored value and proves nothing about the call it stands in for) read twice, once for a single node's determinism claim and once for a calibration run's aggregate variance claim. **Where genuine A/A variance actually comes from, with the cache bypassed.** Three sources, each named and tagged rather than left as one unexamined "noise" term. **LLM sampling nondeterminism at temperature above zero** — the same call, bypassing the cache, MAY return a different completion each time a sampling temperature above zero is in effect. ### §AA.3 — Correcting the floor for batch width

**The hazard, stated quantitatively before any remedy.** `§5`'s promotion floor is calibrated for **one** comparison — the per-`(bundle@v, tier, metric)` null `### §AA.1` states is priced and read exactly once per comparison decision. `## §RUN.3`'s own D-08 batch shape makes batch operation the rig's **normative** operating mode: N candidate arms tested against one shared baseline, N+1 arm-runs, never 2N pairwise runs. **Testing N mutations against one A/A band at p95 expects roughly N/20 false promotions per batch** — a batch of twenty candidates run against an uncorrected single-comparison floor expects, on average, one candidate to clear the floor on noise alone, and the same ratio scales to any other batch width. Uncorrected, the batch **is** the noise-promoting random walk `SELECTION.md`'s own Falsifier 3 framing names, now running at the higher throughput D-08's batch shape was adopted to provide — the correction below exists because the hazard is real at exactly the operating mode this document adopts as normal, not as a hypothetical edge case. [docs-verified] [CONTEXT D-08] [SELECTION §Falsifiers 3]

**A two-tier correction, matching D-08's own two-tier batch design** — not a menu of four equally-weighted options, but a reasoned assignment of the two tiers D-08 already names to the two correction schemes that fit each one's own cost/error-rate trade-off. [inference] [CONTEXT D-08]

- **Retrieval-side bulk-screening tier — Benjamini-Hochberg (BH) FDR.** BH's own adjusted-p-value procedure is applied against the calibrated floor at the screening stage: it controls the **expected proportion of false discoveries among rejections**, not the family-wise error rate a stricter correction would target — exactly the right trade at a cheap screening stage, because D-08's own design puts a second, expensive filter downstream of it. A false positive that survives BH-FDR screening costs an **escalation** to the answer-level tier, not a promotion; the answer-level tier's own gate is what actually protects the promotion decision, so the screening tier can afford to run looser. [inference] [05-RESEARCH]
- **Answer-level escalated-survivor tier — Dunnett-style, or Holm step-down if a Dunnett implementation is impractical.** Dunnett's test is purpose-built for exactly D-08's own shape — many candidate treatments against one shared control — and it exploits the shared-control correlation structure for extra statistical power rather than discarding it, the way a correction assuming independence would. The practical route to a Dunnett-style correction without a new statistical library: `### §AA.1`'s own resampling-based A/A null construction already builds a null distribution by bootstrap-resampling paired per-question differences, and that same resampling machinery is a natural vehicle for a Dunnett-style resampling approximation over the batch's N candidates against the one shared baseline, rather than requiring a multivariate-t reference distribution this project's own no-runs, no-benchmarks posture would otherwise have to import. Where a Dunnett implementation — resampling or otherwise — proves impractical, **Holm step-down** is the stated fallback: uniformly more powerful than Bonferroni, and still a strict family-wise error rate control, at the cost of not exploiting the shared-control correlation Dunnett's own design captures. **Bonferroni is named and not recommended**, for a stated reason rather than by omission: it ignores exactly the shared-control correlation structure D-08's many-vs-one shape provides for free, spending statistical power neither a purpose-built nor a step-down correction has to spend. [inference] [05-RESEARCH]

**Reconciling with `§5`'s existing epoch-level FDR rule.** `§5` already requires the gate to apply an epoch-level false-discovery-rate correction **across the promotion decisions made within an epoch**, not per-decision in isolation. [docs-verified] [CONTRACT §5] This is a **different granularity from the batch-width correction above, not a competing mechanism for the same one** — stated explicitly here because an unreconciled pair of corrections is worse than either alone. The batch-width correction operates **within** one batch's own N-vs-1 comparison, across the N candidate arms tested against the shared baseline, and its own output is at most one promotion decision per batch, per `### §PR.4`'s one-winner-or-composite-re-run rule. `§5`'s epoch-level correction then operates **across** every promotion decision an epoch accumulates — one batch's own already-corrected decision is one input to that epoch-level correction, alongside every other batch's own decision the same epoch produced. The two are **nested, not double-counting**: the batch-width correction narrows N candidate comparisons down to at most one decision per batch, and the epoch-level correction then corrects across the resulting set of per-batch decisions the epoch accumulates — each correction operates on a distinct population (arms-within-a-batch versus decisions-within-an-epoch), and neither corrects the same comparison twice. [inference] [CONTRACT §5]

**The boundary to the sibling batch hazard, drawn and left there.** `### §PR.4` owns D-08's **second** batch hazard, concerning whether candidates that each separately beat the baseline may be promoted as a set without a further measurement. This sub-section states no rule of its own on that question; a reader needing that mechanism is pointed to `### §PR.4` by name, once, and the two hazards answer different questions — how many arms may be tested against one control, versus whether separately-winning candidates may be promoted together — each answered in exactly one place. [docs-verified] [CONTEXT D-08]

**The boundary to `### §F3.3` rung 3, restated so the two read as non-conflicting from either side.** Early stopping (`### §F3.3` rung 3 — a group-sequential spending function or SPRT) applies **within** a batch run's own question sequence: when to stop asking one arm further questions once its own effect is unambiguous. ### §LC.1 — How a run stops

**Budget-halt**, per `§9`'s enclosure over the whole execution including ingest — an indexing run is not exempt from a budget halt merely because it precedes any query. [docs-verified] [CONTRACT §9]

The threshold behaviour is stated explicitly at all three points, because a builder must not have to guess any of them: a spend that leaves cumulative spend one unit under capacity **continues** — the budget is not consumed early out of caution. [inference] [CONTRACT §9] A spend that brings cumulative spend **exactly equal to capacity** also **continues**: capacity is the ceiling a spend must not exceed, and landing on it, not past it, has not exceeded it — this resolves the boundary explicitly in the completer's favour rather than leaving its direction to be discovered at build time. [inference] [new-synthesis] The first spend that **would exceed** capacity halts before that spend is made, never after — the spend that would have breached the cap is never actually charged, so a run's recorded spend never exceeds its declared capacity. [docs-verified] [CONTRACT §9]

The resulting `stop_reason` value is `budget_halt`, and `budget_state` on every completed node (`within_budget` / `halted` / `degraded`, per `## §TR.1`) already carries the running position, so the halt point is reconstructable from the trace alone without a separate ledger of spend over time. [docs-verified] [CONTRACT §9]

**Watchdog**, on a declared wall-clock ceiling. The ceiling's unit is the one `wall_clock_ms` (`## §TR.1`) already declares — milliseconds — so a watchdog comparison never rests on an unstated unit conversion. [docs-verified] [CONTRACT §8] The ceiling is declared **per-arm**: `§3` already states an arm is always its own confined process regardless of `execution_mode`, and this clause enforces the watchdog at exactly the granularity `§3` already draws the process boundary at, rather than inventing a second, narrower boundary neither `§3` nor `§9` itself fixes. [inference] [CONTRACT §3] [new-synthesis] This is distinct from, and does not replace, `§8` condition 4's own per-node wall-clock ceiling declared for an opaque node's own admission — that ceiling governs whether the opaque node is admitted at all, a load-time question, while the arm-level watchdog this clause states governs whether a run already in progress is stopped, a run-time question; the two MAY both apply to the same opaque node without conflict. [docs-verified] [CONTRACT §8] The resulting `stop_reason` value is `watchdog_timeout`. [inference] [new-synthesis]

**Manual stop**, operator-initiated. A manual stop is as first-class as the other two: it uses the same `stop_reason` vocabulary (`manual_stop`) and the same partial-run labelling `## §LC.2` states below, never a special case producing a differently-shaped record. [inference] [CONTRACT §9]

### §LC.2 — How a partial run is scored and labelled

Per `§9`'s first-class-partial-run rule, a partial run is a result, not a failure — it MUST be traced, scored, and tier-labeled exactly as a completed run is. [docs-verified] [CONTRACT §9]

### §LC.3 — Resume semantics: the `checkpoint?` flag decided

[docs-verified] [CONTEXT D-13] [CONTRACT §5]

The rule is made mechanical rather than left as a slogan. [inference] [CONTEXT D-13]

[inference] [CONTEXT D-13]

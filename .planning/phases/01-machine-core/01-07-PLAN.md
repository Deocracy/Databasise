    wiring can produce different `arm_execution_order` values and a reader comparing them cannot
    tell a real divergence from a scheduling accident. Record the sort in the module docstring as
    the stated tie-break: when nodes become ready together, order is by node id ascending.

    `config.max_concurrency`, defaulting to 1 when the field is absent. Refuse a declared value

    discarded with it; no semaphore is shared between two nodes and none outlives the run.

  <action>
    Write `databasise/runner/budget.py` implementing CONTRACT §9's budget as a splittable capability
    token, metered only at each node's declared boundary and never as a process-wide gate.

    Represent an allowance as an integer token count. Decide and record the split contract, which is
    Claude's Discretion within §9's multiplicative rule: a fan-out of width N over an allowance A
    allocates `A // N` to each branch and assigns the remainder `A % N` to the lexicographically
    first branch id, so the allocations sum to exactly A with no float arithmetic anywhere in the
    allocation path. State this tie-break explicitly in the module docstring — a split that does not
    state its tie-break is a split whose result depends on dict iteration order.

    `realised_budget_share` is a number in the closed interval `[0, 1]` per the trace schema, and it
    is computed as spent over allowance **at report time only**. It is never an input to an
    allocation. Keeping the ratio out of the allocation path is what keeps the allocation exact.

    Implement merge-side apportionment per §9's D4 repair: the node holding the allowance declares
    its apportionment policy, that policy enters **its own** `config_hash` under §1 and never the
    spending node's, and the run record stamps each contributing branch's realised share. Before
    this repair no schema existed for an arm's merge-patch to set an apportionment field on, so make
    the field explicit on the node config rather than implicit.

    Meter at the node's declared boundary, driven by its declared `effects[]`: a node declaring
    `calls_llm` accrues LLM tokens; a node declaring none of the calling effects accrues none. A
    downstream consumer of an expensive node's output accrues nothing from it — the cost belongs to
    the node that declared the boundary it crossed.

    Populate the five `TokenAccounting` members separately on every node — `prompt_tokens`,
    `completion_tokens`, `cached_read_tokens`, `call_count` and `counted_by` — never as one
    aggregate. A cached read prices differently from a fresh call, and a single aggregated count
    could not distinguish the two even in principle.

    A budget halt is a first-class outcome, not an error: the run is traced, scored and labelled
    exactly as a completed run would be, with `partial` true and a `stop_reason` naming the budget.
    A halted run is never discarded and never reported as clean.

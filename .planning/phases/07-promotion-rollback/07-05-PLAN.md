## The mechanism, and why this one

**Chosen: a SQLite `BEGIN IMMEDIATE` transaction spanning read-derive-append, plus a UNIQUE index
on `(alias, minted_version)`. Rejected: the `asyncio.Lock` keyed by alias that `07-REVIEW.md`
WR-01 suggested as its fix.**

The lock was rejected on correctness, not size. An `asyncio.Lock` serializes only callers sharing
one `Databasise` instance on one event loop. It does nothing about a second `Databasise` over the
same `store_root`, a second process, or the REST layer under more than one worker — all of which
reach the same `ledger.db`. `BEGIN IMMEDIATE` serializes at the file, so every writer is covered
regardless of which object, thread, loop or process it came from. It is also the smaller diff: one
context manager in `ledger.py` and one `with` line in each of three sync bodies.

**This is verified, not assumed.** The planner ran the proposed mechanism against both reproduction
harnesses by rebinding the `Ledger` name in the engine module namespace (engine.py constructs
`Ledger` at exactly three sites — the three `_*_sync` bodies — each as the body's first statement,
with every guard read after it and `append()` last, so the rebinding wraps exactly the span the fix
must make atomic and nothing else). Results, 40 trials each:

| race | before | after |
|---|---|---|
| `retire(v)` vs `rollback(v)`, 2 concurrent | ~68% of trials accept a post-tombstone rollback | **0/40**; every trial → `('ok', 'TombstonedGenerationError')` |
| 6 concurrent `promote()` | ~10% of trials mint a duplicate semver | **0/40**; 6 distinct versions every trial, zero exceptions |

**Consequence for the seam surface: no new refusal is needed.** The loser either waits and then
proceeds correctly on freshly-committed state (the promote case — pure serialization, all six
succeed), or waits, re-reads, and refuses through the *already-shipped* `TombstonedGenerationError`
(the retire/rollback case). Neither adds a `SeamRefusalError` subclass, so `COVERAGE.md`'s ladder of
ten-plus-one refusals is unchanged and no three-transport parity test is needed for a new name.

## Four facts the planner verified against SQLite 3.53.1 — do not re-derive, do not assume otherwise

1. **NULLs stay distinct in a UNIQUE index.** Two rows with `minted_version` NULL on the same alias
   are accepted under a plain `UNIQUE INDEX(alias, minted_version)`. A plain unique index is
   therefore safe for tombstones; a `WHERE ... IS NOT NULL` partial index also works but is not
   needed — take the plain one.
2. **`CREATE UNIQUE INDEX IF NOT EXISTS <name>` over an existing plain index of that name is a
   SILENT NO-OP.** Verified: `sqlite_master.sql` still reads `CREATE INDEX`, and duplicates are
   still accepted. Any developer machine holding a `ledger.db` from an earlier run would get a
   no-op "fix". This is the single most likely way to ship a fix that does nothing.
3. **`BEGIN IMMEDIATE` works under the module's current `isolation_level=""` default.** No
   `isolation_level` change is needed; Python's legacy implicit-transaction mode does not re-open a
   transaction while one is explicitly open, and `conn.commit()` closes it.
4. **An unreleased write transaction locks out readers.** `Ledger.__init__` calls `_create_schema()`,
   which issues `CREATE TABLE/INDEX/TRIGGER IF NOT EXISTS` — DDL, which needs the write lock — on
   *every* construction, including a pure read. The planner's first prototype relied on refcounting
   to release and a refusal path held the transaction open: the next `Ledger()` stalled the full
   5000 ms busy timeout and raised `database is locked`. The `try/finally` in the context manager is
   therefore load-bearing, not stylistic.
</mechanism_decision>

| operator → seam (`promote`/`rollback`/`retire`) | Concurrent mutating calls from one or many operators cross here; the REST transport is unauthenticated by inherited position (Phase 4 T-04-25/T-04-26, disposition `transfer`) |
| seam → `ledger.db` | Multiple connections, threads and potentially processes write one append-only SQLite file; the ledger is the system of record and "the ledger append **is** the decision" (CONTRACT §6) |

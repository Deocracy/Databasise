Facts this plan relies on (HEAD after 10-05, verified while planning):
- `resolve_evidence` (`engine.py` about 1273-1290) validates the namespace, checks that the directory exists, builds only `MultiNamespaceVectorStore`, and calls `resolve_evidence_ref(ref, vector)`, which runs `vector.select(ns).get_by_id(ref.ref)` (`seam/evidence.py:138-149`). It already never builds kv or graph (Phase 9 D-05). `select` constructs a `FaissVectorStore`, whose `__init__` mkdirs (a no-op here, since the directory exists) and then reads and hashes the committed files through `_read_committed` (factored in 10-05).
- Every writer path clones the index (`faiss.clone_index`) and copies the entries dict before changing them (`vector.py` flush and `delete_by_ids`), so a cached snapshot can be shared read-only. `_persist`/`_commit_staged` uses `os.replace`, which gives the replaced file a new inode, so an in-process flush invalidates the stat key with no hook (D-05). `commit_prepared` must not put the new state into the cache, so the next reader loads it from disk.
- The two renames are not atomic together, so a reader between them sees a new index with an old sidecar (research Pitfall 4). Stat, read, stat again, and retry once before reporting corruption.
- `VectorStoreCorruptedError(index_path, expected, actual)` (`vector.py:68-86`) is checksum-shaped. A missing file reuses it as `expected=None, actual="<missing vector.meta.json>"` or `"<missing vector.faiss>"` (research Pitfall 15).
- `hold_graph_in_subprocess` is in `databasise.tests.stores.test_graph_lock` (10-01).
- Executor rules from 10-01-PLAN.md `<context>` apply.
</context>

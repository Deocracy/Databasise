Facts this plan relies on:
- POST /documents and POST /documents/upload return `{job_id, enqueued, seam_events[]}` only after the commit. The fetch is in flight for the whole write, so the InFlight entry of kind `ingest` is exactly the write window. DELETE /documents/{id} takes an optional `{"selector": ...}` body and returns `{document_id, status, message, seam_events[]}`. A HippoRAG document deleted with no selector returns `not_found`.
- GET /jobs/{job_id}?limit&offset returns `{job_id, documents[{document_id, status, updated_at, error_message}], counts{}, next_offset}`, with no `offset` and no `total`. HippoRAG jobs answer from the jobs record.
- In the harness, a LightRAG ingest or delete goes through the RUN-10 stub parts and updates `LiveApp.corpus`. A HippoRAG ingest with the stub clients is real and offline. `LiveApp.hold("ingest")` and `LiveApp.hold("delete_document")` keep a write in flight. Both routes call these engine methods (rest.py:443-506): `POST /documents` and `POST /documents/upload` call `engine.ingest`, and `DELETE /documents/{document_id}` calls `engine.delete_document`; `GET /jobs/{job_id}` calls `engine.get_job_status`.
- Upload multipart fields: `file`, `document_id`, and `selector` as a JSON string. A blank or `null` selector means none (rest.py:447-489).
- Ids: `documents.paste.*` (text with `data-field-loc="body.document.text"`, document-id, submit), `documents.upload.*` (file, document-id, progress, submit), `documents.state.in-flight`, `documents.result.*`, `documents.delete.*`, `documents.jobs.*` (drawer, close, job-id with `data-field-loc="path.job_id"`, load, all, list, select-N, documents, prev, next, counts, refresh, poll, page-size), `documents.pipeline.*`, and `shell.dialog.delete`, `shell.dialog.delete-cancel`, `shell.dialog.delete-confirm`.

Because the mock strips are gone, each screen starts with its Display title, then its first panel, with the 32 px `xl` gap of 17-UI-SPEC. No empty strip is left.

### Header health (LIVE-01, 18 D-13)

The header badge text stays exactly `stores openable / v1 reachable`. The state lives in `data-state` and the sibling state word, using the four states already in the source:

| `data-state` | State word | Glyph | When | Extra |
|--------------|-----------|-------|------|-------|
| `loading` | `checking` | spinner | From page load until `GET /health` answers. Maximum 60 seconds. | Corpus & Health shows `Checking stores and the v1 engine. This can take up to 60 seconds.` |
| `ok` | `ok` | check | `GET /health` returned `status: "ok"` | none |
| `degraded` | `degraded` | warning | `GET /health` returned `status: "degraded"` | The Corpus & Health stores table lists the cause. |
| `error` | `unreachable` | cross | The fetch was rejected (server down, connection reset), the response was 5xx, or no answer arrived within 60 seconds | `title` on the badge holds the cause, for example `No response from the server.` or `Health check timed out after 60 seconds.` |

`Health details` keeps its behaviour (opens Corpus & Health). Health is fetched once on page load. After that it is fetched only by `Refresh health` or by the poll (see Polling).

### Header store-busy chips (18 D-13)

The header carries the store-busy field. It is a new id `shell.live.busy`, a `role="status"` group of chips placed between the health badge and `shell.instance.chip` in the header's right-hand group (below 768 px it wraps onto the health row). It is filled from `GET /info` with each health load (page load, `Refresh health`, poll tick):

| Field | Chip text | Shown when |
|-------|-----------|------------|
| `write_in_flight` | `write in flight` | true |
| `graph_busy` | `graph in use` | true |

When both are false the group is empty and takes no space. When `GET /info` is absent from `/openapi.json` the group is hidden and no chip appears. It uses the status chip tokens of 17-UI-SPEC (`warn` tint, glyph plus words) and adds no color. `corpus.health.busy` stays as a mirror of the same two chips inside the Corpus & Health panel, with its `operator route` badge handled by the normal badge rule. Writes by other clients are not predicted: the chips report the server's value at the last health load only.

### Instance chip

`shell.instance.chip` reads `version <v> · workspace <w>` from `GET /info` when that route is in `/openapi.json`. When it is absent the chip reads `version — · workspace —` and keeps its `operator route` badge. It never shows fixture values.

### Badges at run time (18 D-08, D-09, LIVE-09)

The badge text, glyph, colors, titles and wrapper structure are exactly those of 17-UI-SPEC (Needs-backend Registry). Only the lifecycle changes.

1. At start-up the console fetches `GET /openapi.json` once.
2. For each element carrying `data-needs-backend`, the method and path template in the value are matched against `paths`. Path parameter names are ignored (`/jobs/{job_id}/cancel` matches `/jobs/{x}/cancel`).
3. A value with a qualifier in parentheses (`GET /corpus (status, sort, search)`) matches only if every named parameter appears in that operation's `parameters`.
4. If the operation is present and the control is wired: remove `data-needs-backend`, `data-backend-state`, the wrapper `title` and the badge element. Enable the controls. The wrapper element itself stays so its ids stay. No animation, no announcement.
5. If `/openapi.json` fails to load, every badge stays. No visible notice is added (the badges staying is the signal); the failure is written to the browser console.
6. A control whose route is absent stays visible with its badge. It is natively `disabled` with `aria-disabled="true"`, and a visible muted line under it reads `Needs <METHOD /path>.` (for example `Needs POST /graph/node/attrs.`). Its wrapper `title` keeps the 17-UI-SPEC wording. It never shows fixture data.
7. Exceptions with a client-side fallback (next section) are not disabled.

## Slot Overflow (live data is larger than the mockup's slots)

The mockup holds a fixed number of literal control slots (evidence `open-1..5`, jobs rows `1..5`, corpus rows `1..6`, node list `1..8`, edges `1..6`, chunks `1..8`, timeline `1..5`, trace picker `1..6`, history `1..3`). Real responses can be longer, and silently dropping rows is not acceptable.

Rule (discretion): rows `1..N` use the literal slots of the source. A row `N+1` and above is cloned at runtime from the last literal slot, and its control ids take the next numeric suffix (`query.evidence.open-6`). No data row is ever dropped or truncated. The frozen literal ids stay in the source, so the id check is unaffected. Clones are removed and rebuilt on each render.

| Region | Rule for long results |
|--------|-----------------------|
| Evidence, token, seam tables, compare columns | All rows render. Each table stays inside `.table-scroll`. |
| Paged tables (jobs documents, corpus, node list, edges, chunks, timeline) | One page at a time, page size 1 to 100, paging by `next_offset` as in 17-UI-SPEC. |
| Query history, ledger trace picker | The list shows all stored entries (stored cap 50, newest first) inside a container with `max-height: 240px; overflow-y: auto`. |

## Request States (all live calls)

Every screen follows the same loading and cancellation rules. These replace the mockup's `setTimeout` simulation.

| Situation | Contract |
|-----------|----------|
| A read is in flight (list, table, inspector) | The owning panel sets `aria-busy="true"`; a spinner with the visible word `Loading` sits in the panel heading line; previous rows stay on screen; the panel's Previous, Next and refresh controls are `disabled`. |
| A read is superseded or its screen is left | It is aborted. Nothing is shown for an aborted request: no error, no banner. The spinner clears, and an opener button that read `Opening` returns to `Open` (IN-JSB-08). |
| A write is in flight (ingest, upload, delete, promote, rollback, retire, retry) | Never aborted once sent. The confirm or submit button is `disabled` and `aria-busy`, a spinner and the text `Sending. A request that has been sent cannot be cancelled.` appear next to it. Delete, Promote, Roll back and Retire dialogs stay open with both buttons disabled and Escape ignored until the response arrives, then close and render the result or banner in the owning screen (E14). |
| A dialog's dismiss button or Escape before Confirm | Sends nothing and changes nothing (WR-JSB-02, IN-JSC-04). |
| Rejected fetch (server down, reset) | Generic error view with the unreachable copy below; header health becomes `error` / `unreachable`. |
| Response with a body that is neither a refusal, a validation list nor JSON | Generic error view (rule 4 of `classifyResponse`). |
| Real HTTP status | The refusal footer prints the real status: `HTTP 404`, `HTTP 409` or `HTTP 422` (IN-JSA-09). |

### Live-only error copy

| State | Copy |
|-------|------|
| Server unreachable (generic view, status 0) | Label `Server error`. Text `Server unreachable. No response from the server. Check that databasise-rest is running at this address, then try again.` No response body block is shown. |
| Generic 5xx with `GET /log` mounted | Same generic view as 17-UI-SPEC, and the `<screen>.error.server-log` region below it loads `GET /log?limit=200` into a mono block, `max-height: 240px`, scrolling. Caption `Last 200 log lines. Lines are redacted.` If that request fails: `The server log could not be loaded. Select Refresh log in Corpus & Health to try again.` The `Open server log` link scrolls to this region. |

## Query & Compare (live)

Region ids and layout are unchanged. This section lists the live behaviour the mockup did not have.

**Streaming (`Stream the response` on).**

| Moment | Visible result |
|--------|----------------|
| Request sent | `query.state.running` with `Running. A full run waits for the model; no progress is available.` |
| Response is not `text/event-stream` or not `ok` | The JSON body goes through `classifyResponse`; the matching error shape appears. Nothing is parsed as events. |
| `evidence` event | One row is appended to the evidence table; rank is the arrival position from 1. The answer panel shows `Receiving evidence` in muted text until `final`. |
| Lines starting with `:` (for example `: ping`) | Ignored. No visible change. |
| `final` event | The final fields fill the answer, badges, tokens and seam table. The notice strip shows `Run complete.` `Promote` and `promote from this result` become enabled (if the result is not partial and has a `trace_token`). `Open trace` becomes enabled. |
| Stream ends with no `final` | `q-stream-disconnected` state. Generic view text `The stream closed before the final event.` followed by `Evidence received so far is shown below; the run is not complete. Run again to retry.` Rows already received stay visible. `Promote`, `promote from this result` and `Open trace` stay disabled with the visible reason `The run did not finish.` No history row is added. |

Before `final`, the string `Run complete.` is not in the DOM as visible text and Promote is disabled (WR-JSA-05).

**Non-streaming.** `Run` calls `POST /query`; the success notice strip shows `Run complete.` when the response is 2xx.

**Compare.** One selector in the builder renders a single result in the normal result layout (the `One selector runs as a plain query` info message stays). Two or more render one column per key from the keyed map, each with its own `trace_token` for `Open trace` and `Promote this arm` (WR-JSA-06). A key the server returns that the console did not send is appended as an extra column (discretion; the column count is not capped for rendering, the builder cap stays 4).

**Run blockers (all live conditions).**

| Condition | Query mode | Compare mode | Visible reason (`query.run.message`) |
|-----------|-----------|--------------|--------------------------------------|
| Existing 17 blockers (empty text, empty capability set, hash-shaped alias, bad raw JSON, duplicate key, zero rows) | Run clickable, inline message on click (blocking style, unchanged) | Run `disabled`, warning list (unchanged) | 17-UI-SPEC messages, verbatim |
| Own request in flight | Run `disabled` with spinner | Run `disabled` with spinner | `Running.` plus the loading copy |
| An ingest, upload or delete is in flight (LIVE-05) | Run `disabled` (native `disabled` and `aria-disabled`), with the reason shown (amended 2026-10-31, plan-check ruling: LIVE-05 governs; see 18-CONTEXT D-13) | Run `disabled` | `A document write is in progress. Queries are unavailable until the ingest or delete finishes.` The message clears when the write ends. |

`Compare.run` re-checks every blocker before it sends, even if the button was enabled by a stale state (WR-JSA-02).

**Absorbed behaviour fixes** (18 D-17; live source only):

| Finding | Contract |
|---------|----------|
| WR-JSA-01 | Raw selector JSON accepts only `alias` (string), `capability` (array of strings) and `harness` (string). Anything else shows `Raw selector JSON is not valid JSON.` (the existing text) and Run sends nothing. |
| WR-JSA-03 | Query state views never render beside compare columns. In compare mode `showState` does not touch Run, and the single-result layout is hidden while columns show. Exactly one state view is visible. |
| WR-JSA-04 | A mode switch, a new Run, or leaving the screen aborts the pending query and compare reads. A superseded run adds no history row. |
| IN-JSA-07 | A promote event from Query or Compare replaces the Ledger trace preselection; earlier selections are cleared. |
| IN-JSA-08 | `Promote this arm` and `promote from this result` are `disabled` when `trace_token` is `null`, with the visible reason `No trace token on this result.` |
| IN-JSA-09 | The refusal footer prints the real status (404, 409 or 422). |
| WR-JSA-05 | See Streaming. |
| WR-JSA-06 | See Compare. |

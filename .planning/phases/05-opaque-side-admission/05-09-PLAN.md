## Scope decision — one planner-discovered item, deferred with its evidence

**IN-02 (planner-discovered, not in 05-VERIFICATION.md): `IngestDocument(...)` construction inside
a transport body is the same wrapped-`ValidationError` escape, and REST has it too.**

While grounding this plan's fix, a third instance of the identical failure class turned up:
`IngestToolArgs.to_ingest_document()` (`databasise/mcp/tools.py`) constructs `IngestDocument(...)`,
whose `model_validator` raises `AmbiguousIngestPayloadError` (neither or both of `text`/`raw` set)
or `OversizedDocumentError` (payload over `MAX_DOCUMENT_BYTES`). Both are `SeamRefusalError`
subclasses, both get wrapped by pydantic v2 into a `pydantic.ValidationError` at the construction
call site, and both therefore escape `_refusal_mapped` as `UnexpectedToolError` — reachable by
calling the `ingest` tool with no arguments at all.

**Deferred, for a reason the evidence supports rather than for difficulty.** This is not a
transport-parity divergence: `databasise/seam/rest.py`'s own `POST /documents/upload` route
constructs `IngestDocument(...)` in its route body the same way (rest.py:238-243), so an oversized
multipart upload over REST produces the same unmatched `pydantic.ValidationError` — Starlette
matches handlers by `type(exc).__mro__` against the registered `SeamRefusalError` handler, and
`pydantic.ValidationError` is not in that hierarchy. **Both transports mishandle it identically**,
so closing it is a both-transports change to `rest.py` and `mcp/tools.py`, not a parity repair, and
it is outside gap G-05-2's mandate (whose whole subject is a *divergence* between the two).

The shared root cause of all three instances is worth recording where the next person will find it:
`SeamRefusalError` subclasses `ValueError`, and `ValueError` is precisely the class pydantic v2
converts into a `ValidationError` when raised inside a validator. Every refusal raised in a
validator therefore loses its own exception object — which is why `PageSizeExceededError` and
`AmbiguousIngestPayloadError` both embed their own class name in their message text as a
documented workaround. Changing that base class would fix the class outright but touches every
refusal call site and every `except ValueError` in the seam, which is a phase-scale decision, not a
gap-closure one.

**Trigger to close:** raise it as its own item in the Phase 6 review, or the next time either
transport's ingest path is opened — whichever comes first. Do not close it inside this plan.

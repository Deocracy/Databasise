<flagged_assumptions>
- **FA-04 (RESEARCH A1 / Open Question 1, unresolved — carried as a flagged assumption per the
  orchestrator's direction).** §18.4 names "a declared capability or capability set" but CONTRACT
  freezes no capability vocabulary beyond §14.1's statement that `effects[]` is "the base
  capability vocabulary" and §14.2's store sub-capability tables. This plan defines capability
  matching over the 17-member `Effect` vocabulary `databasise/parts/schema.py` already freezes,
  because inventing a parallel taxonomy the contract does not name would be worse than using a
  thin one it does. **This is thin.** A consumer asking for "graph retrieval" must name
  `reads_graph`, which is a machine-facing word, not a consumer-facing one. It is sufficient to
  distinguish the five Phase 3 arms — they differ from each other exactly in which effects their
  nodes declare — and therefore sufficient for the §18.5 falsifier. It is not asserted to be the
  right long-term ergonomics. Record this verbatim in `selectors.py`'s module docstring so the
  next reader inherits the open question rather than the appearance of a settled design.
- **FA-05 (RESEARCH Pitfall 2, resolved by fixture, limitation declared).** No production wiring
  in this repository declares a harness: the LightRAG base wiring's `harnesses` array is empty and
  nothing in `parts_core` implements one. The harness selector is therefore built and tested
  against a fixture wiring document that declares one. No production wiring exercises this path
  yet, and the test docstring must say so plainly.
- **FA-06 (RESEARCH Pitfall 3 / A2, scoped by the orchestrator).** The ledger has no `alias`
  field; `LedgerRecord` carries `mutation_id` and no alias column. Minting a promoted alias is
  §6/Phase 7's promote-rollback scope. This plan builds the alias selector's **read** path against
  a defined registry shape and refuses cleanly when the registry is empty or the alias is absent.
  An empty registry that correctly refuses every alias is this phase's legitimate end state.
</flagged_assumptions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| consumer → selector | The selector is untrusted input that chooses which machine content answers; §18.4 makes it a closed set precisely to keep internal identity off the input path |
| seam → ledger | The seam reads the append-only promotion ledger and must never write to it |
| refusal → consumer | A refusal message crosses outward and is the most overlooked disclosure channel in the phase |

| T-04-13 | Information Disclosure | selector refusal messages | high | mitigate | No refusal enumerates known aliases, arms, capabilities, harnesses or node positions; empty-registry and absent-alias raise the identical refusal so the two are indistinguishable (Tasks 1-2); asserted against `resolve_arm`'s real node id sets at test time |

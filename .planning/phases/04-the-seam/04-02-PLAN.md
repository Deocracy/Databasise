<objective>
Fill two of the envelope's declared-but-empty fields with real values: the evidence references
every answer must carry (API-05) and the token accounting every number in which must carry its own
`counted_by` (API-11).

Purpose: these are the two fields the research found have no existing implementation to wrap.
No `ScoredItem`, `ChunkRef` or `Ref` type exists anywhere in the codebase, and per-node
`TokenAccounting.counted_by` values legitimately disagree within one run — so both are new code,
sized as new code, not as plumbing.

Output: `databasise/seam/evidence.py` and `databasise/seam/tokens.py`, wired into envelope
assembly, with tests that assert real values from real runs.
</objective>

<flagged_assumptions>
- **FA-03 (RESEARCH Pitfall 4, partially unresolved).** §4's `ChunkRef` is specified as
  `(corpus_id, recipe@version, ordinal, content_hash)`. At the point the seam sees a retrieved
  item, only the store's own `doc_id`, its score and its metadata are in hand; the recipe identity
  and the content hash are not plumbed to that position. This plan mints a reference carrying the
  members that are genuinely available and records the unpopulated members explicitly as a named,
  declared limitation in the module docstring rather than shipping a reference that only looks
  like a `ChunkRef`. Closing the gap requires plumbing recipe identity to the retrieval position,
  which is not in this phase's requirement set.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| seam → consumer (evidence) | An evidence reference crosses outward and must be resolvable without revealing the machine's namespace derivation, instance identity or node positions |
| consumer → seam (deref) | An evidence reference handed back for resolution is untrusted input that names a store record |
| run record → envelope (tokens) | Per-node accounting crosses the redaction boundary as an aggregate; the aggregation itself can misattribute |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-07 | Information Disclosure | `databasise/seam/evidence.py` | high | mitigate | `EvidenceRef` inherits the envelope's strict base and carries only the store record id, namespace, kind, score and tier — no instance hash, node position or wiring identifier; the behavioral leak gate in 04-04 proves it over a real serialized envelope |
| T-04-08 | Tampering | `Databasise.resolve_evidence` | high | mitigate | A reference the store does not hold raises the named refusal rather than resolving to nothing; the namespace member is used as a lookup key against the seam's own store set, never joined into a filesystem path by the caller |
| T-04-09 | Repudiation | `databasise/seam/tokens.py` | high | mitigate | One breakdown entry per distinct `counted_by`, values copied verbatim from `TokenAccounting`; no merged scalar total, so a run's spend cannot be attributed to a tokenizer that did not count it |
| T-04-10 | Spoofing | `databasise/seam/tokens.py` | medium | mitigate | An `unbudgetable` participant raises rather than yielding a substituted number — a plausible-looking fabricated count is the worst outcome because it reads as measured |
| T-04-11 | Information Disclosure | evidence score values | low | accept | Retrieval scores are values, not identities; §18.3 permits values to vary with the fitted modality while the field set does not. Recorded so the inclusion is a decision, not an oversight |
</threat_model>

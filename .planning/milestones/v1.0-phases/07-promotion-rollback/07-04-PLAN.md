## The design tension, resolved here rather than at execution time

`07-VERIFICATION.md`'s `missing:` list can be satisfied two ways, and they are not equivalent.

**Rejected: constrain `PromoteRequest.verb` / `PromoteToolArgs.verb` to the `PromotionVerb`
`Literal` so Pydantic rejects a bad value before the engine is reached.** This produces a 422 over
REST, but from FastAPI's own request-validation handler, whose body is a `detail` array and carries
**no `refusal_type` key at all**. `tests/seam/test_dual_transport.py::test_refusal_parity_across_three_transports`
and `tests/mcp/test_dual_transport_parity.py` both assert transports agree on `refusal_type`; routing
the verb through Pydantic would make the verb the one refusal in the system whose name differs per
transport. It fixes a divergence by introducing a new one.

**Chosen: one named refusal, one mechanism, three transports.** The transport DTOs keep `verb: str`
and stay deserialization-only — the *identical deliberate rule* `PromoteRequest`'s own docstring
already states for `change_origin`: the absent/invalid value is allowed to reach
`Databasise.promote()`, which raises the named refusal itself. The engine guards the verb against
`typing.get_args(PromotionVerb)` before anything else runs, and the existing, already-tested refusal
plumbing — `rest.py`'s single `add_exception_handler(SeamRefusalError, ...)` and `mcp/server.py`'s
`_refusal_mapped` — carries it to both public transports with no transport code change at all.

**Pinned observable outcome per transport** (mechanism is not the contract; these are):

| Transport | Input | Observable outcome |
|-----------|-------|--------------------|
| in-process | `await engine.promote(alias, [trace_id], "human_edit", verb="promote_next_typo")` | raises `UnrecognisedPromotionVerbError`; `type(exc).__name__` is exactly that string |
| REST | `POST /promote` with `{"alias": ..., "trace_ids": [...], "change_origin": "human_edit", "verb": "promote_next_typo"}` | HTTP **422**; response body's `refusal_type` is `"UnrecognisedPromotionVerbError"` |
| MCP | `call_tool("promote", {"args": {... "verb": "promote_next_typo"}})` | raises `ToolError`; its JSON detail's `refusal_type` is `"UnrecognisedPromotionVerbError"` |
| all three | any of the above | ledger holds **0** rows afterward |

`PromotionVerb` still becomes `promote()`'s `verb` annotation — the typing half 07-01-PLAN.md Task 3
demanded. It is a static-typing statement of the closed enum (this project runs ruff, no type
checker, so `Literal` is documentation for a reader and a checker); the **runtime** enforcement is
the named refusal, which is where a public-input-reachable value must be enforced anyway.

  <name>Task 1: Component naming convention for the fifteen new LightRAG components</name>
  <decision>How the fifteen new LightRAG component names are minted, and therefore what every
  recorded instance identity in this phase is keyed to.</decision>
  <context>
    `docs/system-model/wirings/lightrag-base.json` publishes every component name with **no** version
    suffix (`lightrag/keyword-extractor`, `lightrag/embedder-query`, ...), and its own status note
    says why: CONTRACT §0's version-minting rule states that an experiment arm MUST NOT mint a
    version and that a semver is minted only at promotion. None of these fifteen components has been
    promoted.

    The three declaration-only entries already in this repo use the opposite convention —
    `lightrag/query-side@0.1.0`, `lightrag/full-ingest@0.1.0`, `codebase-memory-mcp@0.1.0` — and the
    committed Falsifier 2 evidence (`databasise/evidence/FALSIFIER-2-EVIDENCE.md` plus
    `wirings/w1-lightrag-query-side.json` and `w3-lightrag-half-decomposed.json`) references
    `lightrag/query-side@0.1.0` by that exact string.

    This is `one-way` because component instance identity is the frozen tuple
    `(name@version, config_hash, resolved_dependency_ids)`. Every `instance_hash` stamped into every
    run record and every parity number this phase records is keyed to the name string chosen here.
    Changing it after evidence is recorded voids that evidence rather than editing it.
  </context>
  <options>
    <option id="unversioned">
      <name>Register all fifteen unversioned, exactly as the published wiring JSON names them</name>
      <pros>CONTRACT §0 compliant — no version is minted for an unpromoted component. The registered
      wiring's `component` strings are byte-identical to the already-mechanically-checked published
      base, so the arm patches apply without editing any node's component string. Phase 7's promotion
      ledger is then the thing that mints versions, which is what §0 says it is for.</pros>
      <cons>The registry's field is named `name_at_version` and will hold strings with no version,
      which reads oddly until Phase 7. Two naming conventions coexist in the registry (the three
      Phase 1 stubs keep their `@0.1.0`) until those stubs are retired.</cons>
    </option>
    <option id="versioned">
      <name>Register all fifteen with an `@0.1.0` suffix, matching the existing stubs</name>
      <pros>One convention across the whole registry; `name_at_version` holds what its name says.</pros>
      <cons>Mints a version for fifteen unpromoted components, which CONTRACT §0 forbids in as many
      words. Requires editing the `component` string of every node in the base wiring and in all five
      arm patches away from the published, already-checked content — the exact re-derivation
      03-RESEARCH.md names as an anti-pattern.</cons>
    </option>
  </options>
  <resume-signal>Select: `unversioned` (recommended — CONTRACT §0's own rule, and it keeps the wiring
  content byte-identical to the published table) or `versioned`.</resume-signal>
</task>

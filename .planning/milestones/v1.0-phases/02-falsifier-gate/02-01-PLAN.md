<assumption_delta_decision>
**Signals reviewed:** `pluralization` on "alongside" (the §19.10 boundary enumeration recorded
alongside the node set) and on "fallback" (a fallback-ladder run labelled `degraded` with its
`degradation_reason`).

**Noun now primary:** unchanged — the wiring node keyed by its resolved part's `name@version`
identity remains the primary identity; the run record keyed by its run identity remains the primary
run.

**Decision: `no-change`.** Both signals are false positives for this phase. "Recorded alongside the
node set" is provenance authored onto an existing identity — the §19.10 candidate boundary set is a
property *of* the recorded node set, not a second identity competing with it, which is why
`boundary_knobs` is a top-level sibling of `nodes` in one wiring document rather than a second
document. "Fallback-ladder run labelled degraded" is a flag pair on the one `RunRecord` identity —
`databasise/runner/trace.py` already models `partial`/`degraded`/`stop_reason`/`degradation_reason`
as a required-together field set on a single record, not as a second record kind.

**What would force a later promote:** if a boundary set ever needs its own version and lifecycle
independent of the node set it describes — for example, a second author publishing a competing
candidate set against the same wiring under §19.10's own falsifier — then "boundary enumeration"

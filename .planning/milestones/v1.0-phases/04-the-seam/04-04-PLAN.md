<objective>
Fill the envelope's last two declared-but-empty fields with real values, then prove the whole thing
leaks nothing.

Purpose: the opaque trace reference (D-06, API-10) has nothing to key into today — nothing in the
codebase persists a `RunRecord` — so this phase builds run-record persistence, sized honestly as
new work. MACH-11's seam-level event likewise has no source signal today; the scheduler's existing
`TouchRecorder` hook is the one place the out-of-`deps` case is observable. With both fields
carrying real values, the behavioral half of D-05 finally has a complete envelope to assert over.

Output: `databasise/seam/trace_store.py`, `databasise/seam/redact.py`, the MACH-11 detection wired
into envelope assembly, and the two-tier leak gate.
</objective>

<flagged_assumptions>
- **FA-07 (edge probe, API-10 unclassified — unresolved).** The deterministic edge probe classified
  API-10 as `unclassified`: it produced no boundary, ordering, encoding, precision, empty or
  adjacency edge for "caller retrieves the node-by-node execution trace through the trace
  reference." That is a genuine classification gap, not a signal that the requirement is edge-free
  — a trace reference plainly has boundary behaviour (unknown token, expired token, concurrent
  runs). The unknown-token case is covered by a truth above; expiry and concurrency are not
  addressed by any requirement in this phase and are carried forward unresolved rather than
  invented here.
- **FA-08 (RESEARCH Pitfall 6, resolved by fixture with a named mechanism).** Nothing in the
  scheduler currently distinguishes a `mutates_store` call inside a wiring's `deps` graph from one
  outside it, and no registered part exercises the outside case. The detection mechanism this plan
  uses is the scheduler's existing `TouchRecorder` hook (D-15,
  `databasise/runner/scheduler.py` line 148), which already reports `(node_id, kind, key)` for
  every scoped store touch. The correlation rule — a store touch by a `mutates_store` node whose
  own declared `deps` do not account for the touched store key — is defined by this plan and is
  not stated in CONTRACT. It is the narrowest rule that makes the case observable with the
  instrumentation the machine already has; a later phase that introduces a real out-of-`deps`
  mutating part should re-check the rule against it.
</flagged_assumptions>

test-only code because 04-05's REST transport must assert against the same gate rather than a

and low-entropy values as two separate collections. High entropy: the run's
`wiring_instance_hash` and every node's `instance_hash` — 64-hex-char SHA-256 digests, safe to

by a node position than to leak that word into free text, so the structural check is where the
real signal is.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| envelope → consumer | The last and widest disclosure surface: a complete envelope carrying evidence, tokens, a trace reference and seam events |
| consumer → trace store | An opaque token handed back is untrusted input selecting a stored run record that contains full internal identity |
| node body → store | A `mutates_store` participant acting outside the declared dataflow — the case MACH-11 exists to make visible |

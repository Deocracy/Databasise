enforce it.

authoring a node, and the boundary erodes one convenient edit at a time. ROADMAP criterion 1
therefore requires not just an admitted opaque core but "a written inside-vs-across-boundary change
rule that a compat test enforces."
Output: one rule document and one compat test.

  <action>
Write `databasise/parts_core/lightrag/OPAQUE-BOUNDARY-RULE.md`, addressed to a future contributor
who has not read this plan.

Required sections:

1. **What this rule is for.** One short paragraph naming the failure: new capability added by
   editing inside the opaque core rather than by authoring a fitted node. State that the rule is
   build-added discipline, not a CONTRACT clause — CONTRACT §8 says what admission requires; this
   document says what may change afterwards without re-admission.

2. **Across the boundary — a change here requires a version bump and re-admission.** An explicit,
   enumerated list, each item naming the exact identifier and the file it lives in:
   - `Part.name_at_version`, `kind`, `structural_depth`, `effects[]`, `upstream_ref`, `artifact_scope`
     for each of the two corpus-side parts.
   - Every field of the part's `AdmissionRecord`: `storage`, `wall_clock_ceiling_seconds`,
     `feed_tier`, `ttl_days`, `network_namespace`, `environment_hash`, `manifest_source`, and the
     eleven `ConditionVerdict` entries.
   - The driver script's stdin key set and stdout key set, per operation.
   - The set of operations the driver dispatches on.
   State the obligation plainly: changing any of these means minting a new `name@version` per
   CONTRACT §0 and re-running admission, never a same-version edit.

3. **Inside the boundary — free to change.** Equally explicit: everything inside the subprocess and
   inside v1's own venv. Name concrete examples so the permission is unambiguous — v1's facade
   construction, the chunking strategy, the extraction prompt, the storage backends v1 selects, its
   internal concurrency, its own dependency versions. State that a change here needs no version
   bump and no re-admission, and that this is the whole point of admitting the core opaque.

4. **The one thing that is neither.** Adding a *new capability* — a new document format, a new
   retrieval behaviour, a new mutation surface — is not an internal change even when the diff lands
   inside the subprocess, because it widens what the node does without widening what it declared.
   State the required response: author a fitted node, or make it a new declared operation on a new
   port with its own effects and its own admission — never a quiet widening of an existing port.
   Name the §8 framing this rests on: every restriction is a capability not yet earned, lifted by
   decomposition per §6, never by exception or override.

5. **How this is enforced.** Name `databasise/tests/parts_core/lightrag/test_full_ingest_compat.py`
   and state what it pins and what it deliberately does not. State that the test failing is the
   intended signal, not an obstacle: a red compat test means a boundary value moved and the
   version bump is owed.

6. **Warning signs.** The two `05-RESEARCH.md` names — a diff that touches a part's declared
   `effects`/`artifact_scope` with no version bump, and a new document-format handler added inside
   the ~1,786-line core rather than as a node.

  <action>
Write `databasise/tests/parts_core/lightrag/test_full_ingest_compat.py`.

**A. Module docstring.** State what the file is: the enforcement half of
`databasise/parts_core/lightrag/OPAQUE-BOUNDARY-RULE.md`. State the intended failure mode — this
test going red means a published boundary value moved and a version bump per CONTRACT §0 is owed —
and state explicitly that it is not a lint, so silencing it by updating the pin without bumping the
version defeats its whole purpose.

**B. `PINNED_INGEST_BOUNDARY` and `PINNED_DELETE_BOUNDARY`.** Literal dictionaries carrying every
across-boundary value the rule document enumerates for each part: the six `Part` fields and every
`AdmissionRecord` field, with the eleven condition verdicts pinned by `(condition, verdict)` pairs
rather than by their prose evidence, so rewording an evidence string is an internal edit while
changing a verdict is not. Assert each against the live entry from `default_registry()` by equality
on the whole dictionary, so a *new* field added to `AdmissionRecord` also fails until it is
classified — an unclassified new boundary field is exactly the silent widening this test exists to
catch.

**C. `PINNED_DRIVER_PROTOCOL`.** A literal mapping from operation name to
`{"stdin": frozenset(...), "stdout": frozenset(...)}` for every operation the driver dispatches.
Derive the live values by walking `databasise/foreign/v1_corpus_driver_script.py`'s AST — the same
technique `check_import_boundary.py` uses and for the same reason: a text scan misses a renamed key
reached through a variable. Collect the operation names from the dispatch construct and the key
sets from the subscript and literal-dict nodes inside each branch. Where the AST walk cannot
determine a key statically, the test must fail loudly naming the branch rather than skipping it —
a protocol field the check cannot see is a hole in the boundary, not an acceptable gap.

**D. `test_rule_document_and_check_agree`.** Assert `OPAQUE-BOUNDARY-RULE.md` exists, that it names
both parts, that it names this test file, and that every identifier in `PINNED_INGEST_BOUNDARY`'s
key set appears somewhere in the document. This is the anti-drift assertion: a value pinned by the
check but absent from the prose is a rule nobody can read.

**E. Negative control.** One test that mutates a copy of the live `Part` (never the registry entry
itself) and asserts the comparison helper reports a difference — proving the check has teeth rather
than comparing something to itself.

Do not import anything from `v1/` or `lightrag` in this file.

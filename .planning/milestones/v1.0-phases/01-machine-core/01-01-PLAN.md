<decisions_recorded_here>
Two items CONTEXT.md left to Claude's Discretion, and both Open Questions 01-RESEARCH.md raised, are
decided in this plan and written into the package itself so no later plan re-opens them. The two
remaining discretion items — the structured-concurrency mechanism and the name of the node config
field carrying D-09's semaphore size — are decided in plan 01-02, where they are implemented.

- **Python floor: `requires-python = ">=3.11"`.** `databasise/` sets its own floor, higher than
  `v1/pyproject.toml`'s `>=3.10`, so the runner can use stdlib `asyncio.TaskGroup` rather than
  adding `anyio` as a dependency purely to preserve a 3.10 floor nothing in this phase needs. This
  is legitimate precisely because D-14 makes `databasise/` a separate package that need not inherit
  v1's floor. (01-RESEARCH.md Open Question 1.)
- **Build config: `databasise/` is a fully independent package, not a `uv` workspace member shared
  with `v1/`.** Its own `databasise/pyproject.toml` and its own lock file. Rationale: D-14 forbids
  any import path from `databasise/` to `v1/`, and a shared workspace would put v1's server-backed
  dependency set (Neo4j, Milvus, Qdrant, asyncpg, OpenSearch, the React build chain) on
  `databasise/`'s resolution graph — making EMBED-01's "no external DB servers" claim a property of
  a resolver decision rather than a property of the dependency list. Independent means the
  dependency list is itself the proof. (01-RESEARCH.md Open Question 2.)
- **RFC 8785 canonicalisation: `rfc8785==0.1.4`.**
</decisions_recorded_here>

  <decision>
    What exactly does the environment digest folded into every `config_hash` cover? D-12 already
    fixes the answer (machine-computed resolved closure, read from `importlib.metadata` at runtime).
    This gate exists because CONTEXT.md rates D-12 **one-way**: the digest is an input to every
    `config_hash` ever computed, so changing what feeds it re-hashes byte-identical input and
    destroys any in-flight A/B baseline — the exact failure CONTRACT §1 names by name.
  </decision>
  <context>
    Plan 01-02 implements `databasise/identity/env.py` in the very next wave. Once it runs and stores
    a single artifact registry row or ledger record, the digest's input set is load-bearing on-disk
    state, not a refactor. Confirm the door before walking through it.
  </context>
  <options>
    <option id="option-a">
      <name>D-12 as written: resolved closure from importlib.metadata (RECOMMENDED — this is the locked decision)</name>
      <pros>Hashes what is actually installed, never what a lockfile declares. CONTRACT §1 names the declared-closure alternative as the exact skew the environment hash exists to kill. Covers the whole resolved runtime closure, which §1 requires for opaque nodes specifically. Nix store paths are excluded per spike 004 (Nix is substrate-only).</pros>
      <cons>Two machines with identical lockfiles but different resolved wheels produce different identities — which is the intended behaviour, but it means a CI machine and a dev machine do not share a cache partition unless their closures match byte for byte.</cons>
    </option>
    <option id="option-b">
      <name>Narrow it: Python version and platform only, no distribution set</name>
      <pros>Stable across machines; cache partitions shared more widely.</pros>
      <cons>Rejected by D-12 and by CONTRACT §1 — a narrower hash lets two differently-provisioned instances collide on identity, which for an opaque node is precisely the collision §1 forbids.</cons>
    </option>
    <option id="option-c">
      <name>Widen it: include the lock file digest as well as the resolved closure</name>
      <pros>Records the declared intent alongside the resolved reality.</pros>
      <cons>Reintroduces the declared-closure input §1 rejects; a lockfile edit that changes no installed byte would still re-hash every wiring.</cons>

  <decision>
    Does the per-node concurrency cap live inside the node's own `config` object — and therefore
    inside `config_hash` — or outside it as runner-level state? D-09 fixes the answer (inside, via
    a `config.max_concurrency` field). This gate exists because CONTEXT.md rates D-09 **one-way**
    for the same reason as D-12: it is an input to `config_hash`, so changing it later invalidates
    every identity computed under the old rule and any in-flight A/B baseline.
  </decision>
  <context>
    RIG §AA.1 makes the concurrency setting part of the A/A null's identity and forbids pooling two
    runs under different settings. Putting the cap inside `config` makes that automatic; putting it
    outside makes it something a later step must remember to record. D-09 goes beyond CONTRACT §9's
    V-7 minimum deliberately for exactly that reason. Plan 01-02 implements this in the next wave;
    every `config_hash` computed from that commit forward carries it.
  </context>
  <options>
    <option id="option-a">
      <name>D-09 as written: config.max_concurrency inside the node config (RECOMMENDED — this is the locked decision)</name>
      <pros>Enters config_hash by construction, with no special case. Two nodes differing only in their cap are two identities, so RIG §AA.1's no-pooling rule is enforced by the hash rather than by a later reviewer's memory. Per-node scope directly rejects D-11's process-wide cap: one arm's fan-out can never throttle an unrelated arm.</pros>
      <cons>Retuning a node's cap for performance changes its identity and invalidates its cache partition — deliberate, but it means capacity tuning is a versioned change, not a knob.</cons>
    </option>
    <option id="option-b">
      <name>Runner-level setting outside config_hash, stamped only on the run record</name>
      <pros>Capacity can be retuned without changing identity.</pros>
      <cons>Rejected by D-09. RIG §AA.1's pooling prohibition then depends on a downstream reader checking the stamp, and CONTRACT §9's V-7 minimum is the floor rather than the target.</cons>
    </option>
    <option id="option-c">
      <name>A process-wide concurrency limit shared across all nodes</name>
      <pros>Simplest to implement; mirrors what v1 already does.</pros>
      <cons>Explicitly forbidden by D-11 — this is the v1 shared_storage singleton shape, and one arm's fan-out would throttle an unrelated arm beside it, contaminating Phase 6's side-by-side comparison. Not a live option; listed so the rejection is on the record.</cons>
    </option>

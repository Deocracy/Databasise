    Write `databasise/tools/check_import_boundary.py` as a standalone runnable checker exposing a
    `main()` that returns a process exit status, so it works both as a pytest assertion and as a
    standalone command without pytest.

    Define the forbidden reference patterns once as module-level constants and scan every Python
    source file under the package except this checker's own source. Excluding the checker matters:
    the tool necessarily holds the strings it forbids as data, and a scan counting its own constants
    would report a permanent false positive and train a reader to ignore the check. The two
    forbidden reference forms are enumerated in this task's acceptance criteria — read them from
    there rather than from this paragraph.

    Detect Python-level references by walking the abstract syntax tree rather than by matching text:
    an import node, a from-import node, and a call to the dynamic import machinery whose argument is
    a string literal naming the forbidden package. Walking the tree is what makes the aliased and
    dynamic forms detectable at all — a text scan catches the first two forms and misses the other
    two. Separately, scan string literals for a relative path segment reaching into the sibling
    directory.

    Report each violation as a file path, a line number and the offending reference, and return a
    non-zero status when any violation exists. Print nothing and return zero when clean.

    Add the provenance check to the same tool: for every module under the stores package declaring a
    class-level `upstream_ref`, assert the referenced path exists on disk. D-14 requires copied code
    to carry its provenance, and a record pointing at a path that does not resolve is not a record.
    Report a missing target as its own violation category so the two failure kinds are
    distinguishable in the output.

    In `test_import_boundary.py`, drive the checker over the real tree and over a temporary fixture
    tree built inside the pytest temporary directory containing one deliberately-violating module
    per syntactic form.

    - Criterion 1 — library startup with no external server: the package imports and runs a wiring
      that touches all three embedded engines, with no child process and no listening socket. This
      overlaps Task 1 deliberately: Task 1 tests the property in isolation, this test asserts it
      holds during a real end-to-end run.
    - Criterion 2 — the runner executes to completion with metered spend: a multi-node wiring
      including a fan-out and a join runs to completion under structured concurrency, every node's
      `NodeTrace` carries a `budget_state` and a `realised_budget_share`, and the run record's
      `concurrency_setting` records the intra-node mechanism the run used. The emitted record
      validates against the frozen trace schema.
    - Criterion 3 — identity stability and separation: the same component wired twice with
      byte-identical config produces one `instance_hash` and one cache-partition key across the two
      positions; mutating one byte of one position's config produces a different `config_hash`, a
      different `instance_hash`, and a different cache-partition key; and neither identity function
      will accept a node id, asserted over their signatures.
    - Criterion 4 — quarantined isolation and visible namespace separation: a wiring arm containing
      an `opaque` node runs; its artifact write lands at scope `quarantined`; an attempt by that
      same arm to write scope `shared` is refused with the node named; a discovery query issued
      without a pin does not return the quarantined artifact; and after the run the store root
      contains one directory per namespace whose scope is readable in the directory name, with the
      opaque arm's graph and vector namespaces separate from the transparent arm's.
  </behavior>
  <action>
    Write `databasise/tests/test_phase_success_criteria.py` as the phase's acceptance module. Every
    test drives `databasise.run_wiring` — the seam a consumer calls — rather than reaching into an
    internal helper, so a refactor that breaks the public path fails here even if every unit test
    still passes.

    Build two fixture wirings. The first is a transparent multi-node wiring exercising a fan-out and
    a join over the reference parts, used for criteria 1, 2 and 3. The second contains an `opaque`
    node built from a declaration-only registry entry with an executable stand-in body, used for
    criterion 4; it produces one arm whose effective depth is `opaque` throughout and one
    transparent arm beside it, so the namespace separation the criterion names is observable in one
    run rather than across two.

    For criterion 4's directory-separation assertion, list the store root and assert on the entry
    names directly rather than on internal state. The point of D-07's one-directory-per-namespace
    layout is that separation is inspectable from outside the process, so the test should look from
    outside the process too. Assert that the scope is readable in the directory name, that the two
    arms' graph namespaces are distinct directories, that their vector namespaces are distinct
    directories, and that garbage-collecting the quarantined instance removes exactly its directory
    and leaves the transparent arm's intact.

    Cross-reference each test to the ROADMAP criterion number in its docstring, so a reader
    verifying the phase can map assertions to criteria without reading the plan set.

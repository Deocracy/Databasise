# Lane 7 findings: Code graphs as a store

Scope: which node/edge schema code-graph systems converge on, whether the graph is parser-built or LLM-built, what evidence shows graph retrieval beating embeddings on code, how a small model queries the graph, and whether the code graph should be a separate store from the general knowledge graph. Screened 23 candidates; admitted 18 (10 papers, 8 systems); 1 refutation; 4 abstentions. All arXiv metadata below was opened at the primary abs page; all repo facts were fetched from the GitHub API on 2026-09-13 unless noted.

## Admitted items

**RepoGraph (arXiv:2410.14684, Ouyang et al., ICLR 2025).** A plug-in repository-level code graph whose nodes are individual code lines and whose edges are definition/reference dependencies extracted by parsing, with ego-graphs retrieved around issue keywords and fused into both procedural (Agentless) and agent (SWE-agent, via a `search_repo` action) frameworks. What MelodyScribe should take: the parser-built, line-grain def-ref graph plus retrieve-a-subgraph-never-the-graph pattern is the closest published analog to a separate code store, and it delivered an average relative improvement of 32.8% across four SWE-bench methods plus transfer to CrossCodeEval. Be careful: full-repo construction is slow (the authors ship cached structures for SWE-bench rather than building on the fly), so MelodyScribe must budget graph build/refresh as bulk background work, not on the real-time path.

**CodexGraph (arXiv:2408.03910, Liu et al., NAACL 2025).** A task-agnostic code-graph database built by static analysis with node types MODULE, CLASS, FUNCTION (plus meta-information) and edges CONTAINS, INHERITS, USES, exposed to the LLM agent through graph queries produced by a two-step write-then-translate pipeline (primary agent writes a natural-language query, a translation agent emits executable Cypher) inside an iterative ReAct-style loop, evaluated on CrossCodeEval, SWE-bench (22.96% Pass@1 with GPT-4o, matching AutoCodeRover), and EvoCodeBench plus five shipped applications. What MelodyScribe should take: the fixed schema plus the two-agent split, so the small model never has to emit raw graph-query syntax — it emits intent, and a constrained translator compiles it. Be careful: query generation was only ever tested with large models (GPT-4o, DeepSeek-Coder-V2, Qwen2-72B), so there is no evidence a 1-3B model can write usable Cypher; and on reasoning-heavy SWE-bench work a single query beat multiple queries (22.96% vs 17.90%), so hop count must be budgeted, not maximized.

**GraphCoder (arXiv:2406.07003, Liu et al., ASE 2024).** A statement-level code-context graph (CCG: control-flow plus data- and control-dependence edges) built with tree-sitter, used in a coarse-to-fine retrieval pipeline (cheap sequence filter, then decay-with-distance subgraph-edit-distance re-rank), evaluated over 8000 completion tasks in 20 repositories across 5 LLMs with +6.06 code-match and +6.23 identifier-match EM over RAG bases at lower time and space. What MelodyScribe should take: structural similarity as a re-ranker on top of a cheap candidate filter, and tree-sitter as sufficient substrate for dependence edges without a compiler. Be careful: the task grain is next-statement completion, not issue localisation, and per-query CCG slicing plus graph edit distance is CPU-side work of exactly the kind spike 009 already flags as the ingest bottleneck — price it before putting it on the hot path.

**CodeRAG-Bench (arXiv:2406.14497, Wang et al., NAACL Findings 2025).** A holistic retrieval-augmented code-generation benchmark: ~9k tasks across basic, open-domain, repository-level, and code-retrieval categories with a 25M-document store from five sources, evaluated over 10 retrievers and 10 LMs, finding that canonical (gold) context gives large gains (e.g. GPT-4o +27.4% on SWE-bench) while off-the-shelf retrievers struggle precisely where lexical overlap is low and generators fail to exploit longer contexts. What MelodyScribe should take: adopt its canonical-vs-open retrieval split and its separate scoring of retriever vs generator as the harness-evaluation template, since it isolates exactly MelodyScribe's failure surface (routing/recall vs frontier-model use). Be careful: treat its model numbers as benchmark references, not independent results, and note its verdict cuts against any blanket graph-beats-vector claim (see refutation R2).

**RepoBench (arXiv:2306.03091, Liu et al., ICLR 2024).** A repository-level auto-completion benchmark in Python and Java explicitly factored into three tasks — RepoBench-R (retrieve the relevant cross-file snippet), RepoBench-C (complete the next line given context), Pipeline (end to end) — maintained live with a v1.1 refresh on the Hugging Face Hub. What MelodyScribe should take: the R/C/P factorisation as the harness-side metric design, so code-graph recall (RepoBench-R style) is scored independently of generation quality. Be careful: granularity is next-line completion, which under-measures the multi-hop navigation MelodyScribe needs; pair it with an issue-level benchmark.

**RepoCoder and RepoEval (arXiv:2303.12570, Zhang et al., EMNLP 2023).** An iterative retrieval-generation framework (retrieve with the unfinished code, generate a draft, re-retrieve with the draft, generate again) that beats in-file completion by over 10% in all settings and beats single-shot RAG, plus the RepoEval benchmark of recent high-quality repositories at line, API-invocation, and function-body grains with unit-test-checked function tasks. What MelodyScribe should take: generation-guided re-retrieval as the recall-loop pattern — the draft is the query for the second hop — which composes directly with a code graph (draft symbols become ego-graph centers). Be careful: its retriever is pure similarity (sparse/dense sliding windows), so its gains prove the loop matters independently of the store, not that similarity suffices.

**CrossCodeEval (arXiv:2310.11248, Ding et al., NeurIPS 2023 Datasets and Benchmarks).** A cross-file completion benchmark of ~10k examples from ~1k permissively-licensed repositories in Python, Java, TypeScript, and C#, where examples are admitted only if static analysis shows the completion strictly requires cross-file context, with leakage/memorisation filtering. What MelodyScribe should take: the cross-file-necessity admission criterion as the filter for any code-graph test set — every harness test case should be unpassable from the current file alone — plus its multilingual spread. Be careful: same completion-grain caveat as RepoBench; it measures snippet retrieval, not agent navigation.

**SWE-bench (arXiv:2310.06770, Jimenez et al., ICLR 2024).** The execution-verified issue-resolution benchmark (2,294 GitHub issue-PR pairs across 12 Python repositories, with 300-instance Lite and 500-instance Verified subsets), on which the strongest baseline at publication (Claude 2 with BM25) resolved only 1.96%. What MelodyScribe should take: SWE-bench Lite/Verified as the end-to-end localisation metric, since both RepoGraph's +32.8% relative lift and CodexGraph's 22.96% Pass@1 are reported on it and are therefore comparable. Be careful: it is Python-only, and secondary literature alleges weak-test/plausible-patch inflation on Lite and Verified — track the SWE-bench+ critique as an open caveat (secondary source, not verified here) rather than treating a Lite score as absolute.

**GraphCodeAgent (arXiv:2504.10046, Li et al., preprint v2 Nov 2025).** A dual-graph agent harness coupling a Requirement Graph (relations between the target requirement and repository requirements) with a Structural-Semantic Code Graph (repository code dependencies), over which an LLM agent does multi-hop tool-assisted reasoning to retrieve supportive snippets including implicit ones never named in the requirement, evaluated on DevEval and CoderEval across GPT-4o, Gemini-1.5-Pro, and QwQ-32B with significant gains over baselines. What MelodyScribe should take: the requirement-to-code anchor map is the nearest published analog of MelodyScribe's Score-to-ops routing — an explicit intent-side graph joined to a code-side graph — so any MelodyScribe "this is code / this is a date" router should be designed as edges between requirement nodes and store nodes, not as a classifier bolted on. Be careful: the paper was retitled between versions (v1 appeared under a CodeRAG title), no code or data artefact could be found, and the large relative-gain figures circulate only in secondary summaries, so cite only the primary's directional claim.

**Repoformer (arXiv:2403.10059, Wu et al., ICML 2024).** A selective-RAG code LM trained with self-supervision to predict whether retrieval will help before retrieving, reaching state of the art on RepoEval, CrossCodeEval, and the new CrossCodeLongEval while abstaining on most queries (abstention precision ~0.8) for up to 70% inference speedup in online serving, and transferring as a plug-in policy to larger generators. What MelodyScribe should take: a learned retrieval gate in front of every store pull, and note that its 1B policy over 7B/16B generators is the only admitted evidence that a ~1B model can usefully steer repository retrieval. Be careful: the gate is trained per base LM with self-supervised retrieval-outcome labels, so MelodyScribe must plan the same fine-tuning step (consistent with the owner's harness-first thesis); thresholds need calibration per store.

**Aider repo map (Aider-AI/aider, Apache-2.0; primary: aider.chat repo-map docs, 2023-10-22 tree-sitter article, aider/repomap.py).** A whole-repository signature map (files plus key classes/functions with defining lines) extracted with tree-sitter def/reference queries, ranked with a PageRank-style algorithm over the file-reference graph down to a default ~1,000-token budget, shipped after migrating off ctags. What MelodyScribe should take: the always-on ranked signature map as the cheapest code context — a deterministic prefix fitting the small-model budget that lets the model name the files it needs before any retrieval runs. Be careful: it carries signatures only, no call or data-flow edges, and its ranking is a heuristic with no published recall numbers; it is a prefix, not a store.

**SCIP (scip-code/scip, Apache-2.0; primary: README, announcement post, scip.proto).** A language-agnostic protobuf index format (documents, occurrences, string symbol IDs) produced by compiler-backed per-language indexers (TypeScript, Java, Rust via rust-analyzer, C++, Python, C#, and others) that powers precise go-to-definition, find-references, and cross-repository navigation. What MelodyScribe should take: SCIP-compatible symbol identity for def-use edges rather than an invented scheme, and where available consume existing indexers (e.g. scip-python) instead of writing a resolver. Be careful: per-language indexer maturity varies, and compiled-language extraction monitors the build process, which is a sandboxing liability (see security).

**tree-sitter (tree-sitter/tree-sitter, MIT).** An incremental concrete-syntax-tree parser generator with a dependency-free C runtime and a broad per-language grammar ecosystem, underlying the Aider map, GraphCoder's CCG, and CocoIndex chunking. What MelodyScribe should take: standardise on tree-sitter as the single parsing substrate for chunking, symbol extraction, and dependence slicing, so all three code paths share one grammar dependency. Be careful: grammars give syntax without name binding or types, so def-use and call edges need a resolver or LSP layer on top, and grammar quality differs by language.

**CocoIndex (cocoindex-io/cocoindex, Apache-2.0; primary: indexing docs and codebase-indexing example).** A declarative indexing engine whose codebase flow walks a repository, splits each file along its syntax tree with Tree-sitter (RecursiveSplitter), embeds each chunk with a shared embedder, upserts into Postgres/pgvector, and thereafter re-embeds only changed chunks with live filesystem watch — a complete ~100-line indexing-plus-query path. What MelodyScribe should take: the incremental delta-only re-embed plus live-watch pattern for keeping the code index fresh under bulk ingest without full re-indexing. Be careful: the example builds a chunk vector store, not a graph (no call/import edges), and its freshness/efficiency claims are vendor documentation, not measured results.

**Potpie (potpie-ai/potpie, Apache-2.0; primary: README and architecture docs).** An open-source codebase agent stack that parses a repository into a Neo4j property graph (files, functions, classes, imports, call relationships, plus an enrichment pass anchoring nodes to file/line spans) and serves agents through a tool service (code search, file fetch, graph queries) with prebuilt debugging, Q&A, and code-generation agents. What MelodyScribe should take: the property-graph code schema plus the tool-service separation — agents call functions, never the database — as the harness integration pattern. Be careful: a Neo4j server is heavyweight for a single 16 GB card next to the model, and Potpie's headline SWE-bench-Lite figure circulates only on its wiki, so it is not cited here.

**GitNexus (abhigyanpatwari/GitNexus, README states PolyForm Noncommercial; primary: README and tool docs via fetched pages).** A Tree-sitter plus KuzuDB (native and WASM) code-intelligence engine pairing hybrid BM25-plus-semantic-plus-RRF search grouped by execution flows with MCP tools (query, 360-degree symbol context, blast-radius impact, git-diff detect_changes, coordinated rename, raw cypher) and agent skills plus hooks that reindex after commits. What MelodyScribe should take: its MCP tool taxonomy as the template for code-graph access — scoped read tools over a raw query escape hatch — and its stale-index hooks as the cache-invalidation pattern. Be careful: the raw `cypher` tool lets the model author arbitrary graph queries (injection and runaway-query risk), and the non-commercial license needs legal review before any commercial Databasise distribution.

**codebase-memory-mcp (DeusData/codebase-memory-mcp, MIT; primary: README via fetched pages).** A single-binary MCP server combining tree-sitter AST analysis across many languages with hybrid LSP semantic type resolution, persisting functions, classes, call chains, routes, and cross-service links in SQLite (WAL) and serving them through a dozen-plus MCP tools (search_graph, trace_path, Cypher query_graph) with task-specific skills that steer the client toward graph tools and a compressed shareable graph snapshot. What MelodyScribe should take: the tool-first architecture — no built-in LLM, the model client is the query translator — with per-symbol degree and complexity metadata guiding small-model queries, which maps directly onto MelodyScribe's one-model-plus-harness split. Be careful: its README speed, scale (Linux kernel in 3 minutes), and token-ratio claims are vendor-reported with no independent measurement admitted here, and the cited preprint (arXiv:2603.27277) was never opened.

**CodeQL (github/codeql, MIT for libraries/queries; primary: CodeQL overview docs).** A semantic code-analysis engine that extracts each language into a relational database containing the AST, data-flow graph, and control-flow graph behind per-language schemas, queried with the QL language, with databases for 200,000+ open-source repositories downloadable for offline work. What MelodyScribe should take: its schemas as the reference design for the high-precision end of a code store, and its downloadable databases as an offline corpus for calibrating MelodyScribe's own extractor. Be careful: extraction is heavyweight (per-language extractors, build monitoring for compiled languages), its license restricts automated analysis/CI use to open-source, research, and narrow cases, and hand-writing QL is not small-model-feasible — the harness must pre-author and parameterise every query.

## Refutations

R1 — Against unconditional pull-from-all-stores recall (brief section 1, Recall requirement): Repoformer (2403.10059) shows invariable retrieval is frequently unhelpful or actively harmful to code LMs, and a learned abstention policy matches or exceeds always-retrieve accuracy while skipping most retrievals with up to 70% serving speedup. A harness that pulls from every store every cycle is therefore refuted as a default; every store pull needs a gate.

R2 — Against any blanket "graph retrieval beats embeddings on code" reading: nothing admitted establishes it. CodeRAG-Bench (2406.14497) finds dense embedding retrievers frequently beating BM25 and locates failures in low-lexical-overlap retrieval and generator context use, while the admitted graph wins are mechanism-specific (RepoGraph ego-graphs, +32.8% relative; GraphCoder structural re-rank, +6 EM) rather than graph-vs-vector wins. The supported claim is narrower: structure-aware retrieval with a measured mechanism beats similarity-only baselines on the measured task.

R3 — Against the brief's candidate label "CodeGraph" as a code-store system: the primary source for the only such-titled paper (Cai et al., 2408.13863, opened at https://arxiv.org/abs/2408.13863) is a prompting method that encodes graph-theory problems as executable code evaluated on GraphQA. It is graph-reasoning-via-code, not a repository code graph, and is dispositioned refute for the naming assumption only; the paper itself is not criticised.

Revisit by re-querying the API and pinning license, push date, and artefact list.
U2 — CodexGraph standalone repository: the paper points only at a demo subdirectory inside modelscope-agent; no standalone repo, stars, or license could be recorded. Revisit by checking whether a dedicated repository has since appeared.
U3 — Repoformer code, model, and CrossCodeLongEval release: the paper promises all three at repoformer.github.io but the release was never verified open. Revisit by fetching the site and recording commit-independent facts.
U4 — GraphCodeAgent artefact: no repository, data, or demo link was found; the v1-to-v2 retitle (CodeRAG to GraphCodeAgent) further advises citing the version explicitly. Revisit with a targeted repository search.
U5 — codebase-memory-mcp preprint (arXiv:2603.27277): mentioned in the project README but never opened; its design and benchmark claims are therefore vendor-reported only. Revisit by opening the abs page and screening it as a paper candidate.
U6 — GitNexus canonical repository: several same-named owners exist (twothinkinc, digitalapplied, nxpatterns, tsingke, acme-architecture forks/mirrors); the admitted row uses the search-top-ranked abhigyanpatwari owner and its license reads PolyForm Noncommercial in the README against a NOASSERTION API field. Revisit by identifying upstream and confirming license intent.
U7 — Small-model graph-query generation: every admitted query-writing result (CodexGraph, GraphCodeAgent) uses large models; the only ~1B evidence is Repoformer's retrieval gate, not query synthesis. Whether a 1-3B model can emit constrained graph queries — or must always go through intent-plus-translator — is unanswered by this lane's literature.
U8 — Per-language parser quality: a secondary source reports uneven tree-sitter binding quality (working Python, poor Kotlin), which was not verified at a primary source. Revisit only if MelodyScribe commits to languages beyond Python.

## Security findings (stated as requirements)

S1 — The code-graph query surface must be read-only by construction: scope model access to pre-authored parameterised tools (GitNexus-style query/context/impact) and either remove raw query escapes (raw `cypher`, open Cypher/QL endpoints) or gate them behind an allowlist plus query-cost ceiling, because model-authored graph queries are an injection and denial-of-service vector.
S2 — Repository ingestion must treat indexed content as untrusted: docstrings, comments, identifier names, and commit metadata flow into ranking (Aider-style reference counts) and retrieval text, so a malicious repository can poison symbol importance and retrieved context; require source-attribution on every retrieved span and quarantine third-party code from persistent memory writes.
S3 — Extraction that monitors builds (CodeQL compiled-language extractors, SCIP compiler-backed indexers) executes repository build steps and must run sandboxed with no network and no credential access; prefer tree-sitter/LSP-read-only extraction wherever fidelity allows.
S4 — Grammar and indexer supply chain must be pinned: tree-sitter grammars compile and execute native code at build time, so MelodyScribe must pin grammar revisions by hash and never fetch grammars at ingest time.
S5 — Index staleness must be handled as a correctness and a safety property: serve the graph version that matches the checked-out commit (GitNexus-style post-commit reindex hooks plus version checks on read), and fail closed with a staleness flag rather than silently answering from a stale graph.

## Harness implications

1. Keep the code graph a separate store from the general knowledge graph, built by a parser rather than the model: every admitted system (RepoGraph line def-ref graphs [2410.14684], CodexGraph MODULE/CLASS/FUNCTION plus CONTAINS/INHERITS/USES [2408.03910], Potpie and GitNexus property graphs, SCIP indexes) constructs code structure deterministically and reserves the LLM for querying, while the knowledge graph owns LLM-extracted entities and verbatim-quote evidence.
2. Converge the code schema on files, symbols (module/class/function/method), and CONTAINS, CALLS/USES, INHERITS/IMPLEMENTS, and IMPORTS edges with file/line-span anchors (CodexGraph [2408.03910], Potpie, GitNexus, SCIP occurrences), because cross-system portability of harness queries depends on a fixed, small edge vocabulary.
3. Never show the model the whole graph: serve a ranked signature map as the always-on prefix (Aider repo map, ~1k-token PageRank-ranked budget) and retrieve subgraphs per query (RepoGraph ego-graphs [2410.14684]; GraphCoder coarse-to-fine [2406.07003]), since full-repo graphs run to tens of thousands of edges.
4. Gate every store pull with a learned retrieval decision in the Repoformer style [2403.10059] (abstention precision ~0.8, up to 70% speedup), because unconditional multi-store recall is refuted by R1 and flat always-retrieve fusion is already known-bad on this rig (spike 010).
5. Route the small model through intent-plus-translator rather than raw graph-query authorship (CodexGraph write-then-translate [2408.03910]), since no admitted evidence shows a 1-3B model writing usable Cypher/QL (U7), and keep a raw-query escape hatch closed or allowlisted per S1.
6. Build all code parsing on tree-sitter as the single substrate for chunking, symbol extraction, and dependence slicing (Aider, GraphCoder [2406.07003], CocoIndex), layered with an LSP or SCIP-backed resolver for name binding that tree-sitter cannot provide.
7. Adopt incremental delta-only re-indexing with live watch for the code store (CocoIndex) plus commit-pinned freshness checks and post-commit reindex hooks (GitNexus), because bulk ingest and real-time serving share one GPU and full re-indexes cannot sit on the hot path.
8. Evaluate the code store with the R/C/P factorisation (RepoBench [2306.03091]) on cross-file-necessary cases (CrossCodeEval criterion [2310.11248]), canonical-vs-open retrieval scoring (CodeRAG-Bench [2406.14497]), and SWE-bench Lite/Verified end-to-end (SWE-bench [2310.06770]) — and require each mechanism win to name its number the way RepoGraph (+32.8% relative [2410.14684]) and GraphCoder (+6 EM [2406.07003]) do.
